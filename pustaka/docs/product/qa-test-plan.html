QA test plan

Answers OQ-13 — who runs the acceptance tests and how often — and enumerates every test scenario that follows from it: one hundred and eight cases, positive and negative, across the two deploy automations and the two Go test packages that actually run today, plus the three business acceptance tests BRD §4.1 specifies but nothing has ever executed. Since D-039 this register is also the project's definition of success: GAOS is done when every case here passes, positive and negative alike, and no numeric outcome target stands beside it.

How to read this register

Every row is a TC-nnn. Kind is Positive (the invariant holds, or the action succeeds) or Negative (the invariant is violated, or the action is refused) — both are listed for almost every scenario, because a check that never fails is unverified, not passing. Status is Implemented (the automation exists and this page describes its real, current behaviour, re-read from deploy/check-stacks.sh and deploy/rebuild-restart.sh at the time this page was written) or Not implemented (a forward specification for a test the design commits to but nothing in the repository can run yet).

Who runs these tests, and how often

GAOS has no CI configuration anywhere in the repository — these automations only run when a human or agent invokes them by hand. BRD §5.1 names four internal roles — product owner, platform operator, fleet operator, record author — and notes they are currently one person. That person is the runner for everything below, whether they invoke deploy/rebuild-restart.sh directly or through the gaos-deploy subagent, which exists precisely so the same deterministic script runs the same way every time instead of a free-handed docker compose command drifting between invocations.

Test scenarios — implemented automations

Everything below runs today, in deploy/check-stacks.sh, deploy/rebuild-restart.sh and the two Go test packages, dashboard/ and pustaka/. Every expected message is quoted from the script or the test that produces it, not paraphrased.

check-stacks.sh — tier network & database isolation (TC-001, TC-002)

The script's own header names this the expensive check: a dev stack pointed at the production database starts cleanly, passes every smoke test, and is invisible at runtime. Positive (TC-001): the compose files as committed — compose.dev.yaml joins master-compose-ai-dev-net and points at http://arcadedb-master-dev:2480; compose.prod.yaml joins master-compose-ai-net and points at http://arcadedb-master:2480; neither file names the other's network or database string — produces eight ok lines. Negative (TC-002): edit either file to reference the other tier's network or database string — the matching hasnt assertion prints FAIL with the exact label (e.g. dev does not point at the PROD database), fails increments, final exit code is 1.

check-stacks.sh — tunnel-only publish binding (TC-003, TC-004)

Without the 10.10.0.2 prefix a ports: mapping binds every interface the host has, including the LAN — and nothing at runtime says so. Positive (TC-003): dev publishes "10.10.0.2:19301:80", prod publishes "10.10.0.2:18301:80", each file has exactly one ports: mapping. Negative (TC-004): drop the address prefix ("19301:80") or add a second mapping — FAIL unexpected bind or FAIL n ports: mappings, want 1.

check-stacks.sh — infra-network exclusivity (TC-005, TC-006)

Least privilege as topology: only the dashboard has a reason to resolve a neighbouring product's database, queue or cache. Positive (TC-005): exactly one networks: [internal, infra] line per compose file. Negative (TC-006): add that line to a second service (e.g. traefik) — FAIL 2 services on the infra network, want 1.

check-stacks.sh — distinct project identity (TC-007, TC-008)

Positive (TC-007): name: gaos-dev / 172.30.13.0/24 and name: gaos-prod / 172.30.12.0/24, neither reusing 172.30.10.0/24 or 172.30.11.0/24 (the neighbouring product's range). Negative (TC-008): set prod's subnet to 172.30.10.0/24 — FAIL prod does not reuse a neighbour's subnet.

check-stacks.sh — cross-tier parity (TC-009, TC-010)

The Secure cookie flag is env-driven, never scheme-derived — both tiers sit behind real TLS at the edge and see plain HTTP inside the tunnel, per D-023. Positive (TC-009): both files carry GAOS_COOKIE_SECURE: "1" and GAOS_ARCADE_DB: "gaos". Negative (TC-010): turn dev's flag off "because it's dev" — FAIL dev keeps Secure cookies on — exactly the bug D-023 exists to prevent.

check-stacks.sh — no Docker socket on the proxy (TC-011, TC-012)

Positive (TC-011): no compose file mounts /var/run/docker.sock, and deploy/stacks/traefik.yml uses the file provider, not docker:. Negative (TC-012): mount the socket into a Traefik service — FAIL dev traefik has no Docker socket.

check-stacks.sh — no committed secret (TC-013, TC-014)

Positive (TC-013): no deploy/stacks/*.env file other than *.example is tracked by git, and neither compose file bakes a literal PASSWORD: "…". Negative (TC-014): git add a real docs.env — git ls-files --error-unmatch succeeds, so the check prints FAIL deploy/stacks/docs.env is tracked by git.

check-stacks.sh — trailing-slash redirects (TC-015, TC-016)

Without these the <base href> resolves one level up and every asset 404s, while the document itself still answers 200 — silent, browser-side, invisible to any status-code check. Positive (TC-015): deploy/traefik/dynamic.yml defines the /app and /docs redirect rules, and the landing catch-all has priority: 1. Negative (TC-016): remove the /docs$ rule — FAIL the /docs trailing-slash redirect is present.

rebuild-restart.sh — the status action (TC-017)

Positive: rebuild-restart.sh dev status prints docker compose ps plus one healthz probe over SSH through the tunnel, mutates nothing, and always exits 0 — including when the SSH probe itself fails or times out, since status returns before the pre-flight section runs at all and has no verification contract, only a report. There is no negative case in the usual sense: a broken tunnel shows up as raw error text in the output, not a nonzero exit.

rebuild-restart.sh — argument validation (TC-018, TC-019, TC-020)

All three are refused before any git, Docker or SSH call. TC-018: rebuild-restart.sh dev (no action) or rebuild-restart.sh deploy (no environment) prints usage() and exits 2. TC-019: rebuild-restart.sh dev deploy bogus-service prints unknown service 'bogus-service' -- valid: traefik landing dashboard docs, exits 2. TC-020: rebuild-restart.sh dev prod deploy prints environment given twice, exits 2 — the same path catches an action given twice.

rebuild-restart.sh — the check-stacks.sh gate (TC-021, TC-022)

Applies identically to deploy and restart, both tiers. Positive (TC-021): check-stacks.sh exits 0 → ok "check-stacks.sh passed", the action proceeds. Negative (TC-022): any TC-002/TC-004/etc. mutation is present → bad "check-stacks.sh failed -- refusing to $ACTION", exit 1, before Docker is touched — dev and prod are blocked equally.

rebuild-restart.sh — the prod dirty-tree gate (TC-023, TC-024, TC-025)

Prod builds from the working tree directly — there is no separate worktree yet (see deploy/STACKS.md, "Known gaps"). Negative (TC-023): git status --porcelain is non-empty on a prod action without --allow-dirty → refuses, prints the dirty file list, exit 1. Positive (TC-024): same dirty tree with --allow-dirty → proceeds, echoing "working tree is dirty -- proceeding, --allow-dirty was passed" and the file list. Positive, informational (TC-025): dev with a dirty tree — the dirty check is wrapped in if [ "$ENVIRON" = prod ], so dev is structurally exempt; there is no violation to demonstrate.

rebuild-restart.sh — the deploy test gate (TC-026, TC-027, TC-028, TC-029)

Runs only inside if [ "$ACTION" = deploy ] — restart has no test gate at all. Three checks run in order and stop at the first failure: TC-026: dashboard go test ./... fails → bad "dashboard tests failed", exit 1, pustaka's tests never run. TC-027: pustaka go test ./... fails → bad "pustaka tests failed", exit 1. TC-028: pustaka check ./docs fails (a broken internal link, a missing page-meta field, a stale registry entry) → bad "pustaka docs check failed", exit 1. TC-029, positive: all three pass → proceeds to docker compose build.

rebuild-restart.sh — build and up (TC-030, TC-031, TC-032)

Positive (TC-030): docker compose build $SERVICE and up -d $SERVICE both exit 0, the container list prints, verification begins. Negative (TC-031): the build fails (a broken Dockerfile, a missing build context) → bad "build failed", exit 1, up -d never runs. Negative (TC-032): up -d fails (e.g. a port collision with a stray container) → bad "up -d failed", exit 1.

rebuild-restart.sh — the restart action (TC-033, TC-034)

Positive (TC-033): docker compose restart $SERVICE exits 0 — no build step ever runs for this action — verification begins. Negative (TC-034): restart fails (e.g. the named service isn't currently running) → bad "restart failed", exit 1.

rebuild-restart.sh — single-service scope (TC-035)

Positive: rebuild-restart.sh dev deploy dashboard builds, ups, or restarts only the dashboard service — traefik, landing and docs are untouched, visible in the printed dc ps line as the only service with a fresh timestamp.

rebuild-restart.sh — verification: bind address (TC-036, TC-037)

Positive: ss -ltn shows the port bound to 10.10.0.2:$PORT only → vok "bound to $TUNNEL:$PORT only". Negative: a compose or Traefik regression drops the tunnel prefix, or the entrypoint binds 0.0.0.0 → vbad "unexpected bind: …".

rebuild-restart.sh — verification: healthz (TC-038, TC-039)

Positive: curl through the SSH tunnel with the right Host: header returns a body containing "ok":true → vok "healthz ok:true". Negative: the dashboard is crash-looping or Host: routing is misconfigured → vbad "healthz did not report ok:true".

rebuild-restart.sh — verification: route status codes (TC-040, TC-041)

Positive: / → 200, /app → 301, /docs → 301, /app/ → 200 — all four vok. Negative: any one path returns the wrong code (e.g. the /app redirect regressed to TC-016's failure mode) → vbad "$path -> $got, want $want" for that path only; the other three still pass independently.

rebuild-restart.sh — verification: base href survival (TC-042, TC-043)

Positive: GET /app/ contains exactly <base href="/app/"> → vok. Negative: the base href is stripped, wrong, or absent — a template regression, or a downstream effect of TC-041's redirect failure — → vbad "base href: '…', want '<base href=\"/app/\">'".

rebuild-restart.sh — verification: --full-verify checks (TC-044, TC-045, TC-046, TC-047)

Only run when --full-verify is passed. TC-044, positive: a request carrying X-Forwarded-For: 203.0.113.9 produces a Traefik access-log line for /api/healthz whose ClientHost is 203.0.113.9 → vok. TC-045, negative: Traefik's trusted-proxy list doesn't include the tunnel hop, so the header is ignored and the log shows the tunnel's own address instead → vbad "ClientHost not 203.0.113.9: …". TC-046, positive: curl https://$HOST/api/healthz from the public edge returns "ok":true within 15 seconds → vok. TC-047, negative: the public path is down — edge nginx misconfigured, an expired certificate, the WireGuard tunnel down — → curl times out or returns a non-JSON body → vbad "public healthz did not report ok:true".

The rest of this section is the two Go test packages. They differ from the shell automations in one way worth stating: a shell check prints ok or FAIL and keeps going, while a Go test fails with a message written for whoever has to fix it. Those messages are what is quoted below — copied from dashboard/main_test.go and pustaka/main_test.go, not reconstructed. One TC- per func Test…, because that is the unit go test -run can actually select; several of them are table-driven and carry both a positive and a negative half, and where that happens both halves are described.

dashboard — routes and rendering (TC-054, TC-055, TC-056, TC-057)

The file's own header explains why these exist: a dashboard has almost no assertions of its own, so a wrong template renders a page that looks fine. Positive (TC-054): TestEveryRouteAnswers walks 33 method/path cases with a back-office cookie — the floor fragments, the documented surface, the back office, the wizard — and the negative half of the same table asks for GET /products/nope and requires a 404; a mismatch prints %s %s = %d, want %d followed by body: %s. Negative (TC-055): four surfaces are fetched and the body must not contain template error — %s rendered a template error. Negative (TC-056): the style-attribute trap. html/template refuses to interpolate a plain string into a style="" context and substitutes the literal ZgotmplZ; the page still renders and has silently lost every colour, width and role tint, so seven surfaces are checked and the failure is %s emitted ZgotmplZ -- a computed style lost its template.CSS type. Negative (TC-057): X-Forwarded-Prefix is attacker-controlled on an unproxied request and its value lands in browser-visible output. Three valid values must produce <base href="/app/"> or <base href="/">; eight hostile ones — https://evil.example, //evil.example, a bare app, a backslash, a quote, a newline, and a 200-character path — must each be refused back to <base href="/"> rather than sanitised into something plausible, or prefix %q: want %s.

dashboard — health (TC-058, TC-059)

Positive (TC-058): with no database configured, /healthz parses as JSON, ok is true and store is memory — that is the local stack, and the failure says so: an unconfigured database must stay a 200: that is the local stack. Negative (TC-059): pointing Arcade at http://127.0.0.1:1 reproduces the failure the deploy check exists to catch — wrong network name, wrong alias, wrong password — and must give a 503: status = %d, want 503, then database = %v, want unreachable.

dashboard — the auth boundary (TC-060, TC-061, TC-062)

The check behind this boundary is a placeholder (see M6.4); its shape is not, and that is what these pin. Negative (TC-060): the test walks all nine guarded routes rather than sampling them, because a route that quietly never had a check is exactly what it exists to find — %s %s = %d, want 401. Negative (TC-061): a login value that is not an email is a 422 carrying Enter the email, or status = %d, want 422 and the error message did not reach the form. Positive (TC-062): the tenant label contains a middle dot, and net/http drops invalid bytes from a cookie value silently, so an unescaped value is a truncated header rather than an error; the cookie must round-trip to loop-eng · a@b.c, or no tenant cookie was set / round-trip = %q.

dashboard — floor mutations and their guards (TC-063, TC-064, TC-065)

Test scenarios — not yet implemented

The three tests BRD §4.1 names as the only honest proof the system works. Each is written here as a forward specification — Given / When / Then — so the target exists in writing before the code that would satisfy it. None can run today: domains C (planning), D (execution), E (review, scoring & retry) and H (replay & audit) are all Designed, not Built, per BRD §2.1.

The unsatisfiable task (TC-048, TC-049)

Given a task whose acceptance criterion contradicts a domain rule (the shape BR-07 and BR-14 describe), when it is dispatched through the scheduler and runner, then (TC-048, positive) the system stops within the six guard limits (BR-17: 3 retries, 2 escalations, 2 identical failure signatures, budget cap) and leaves a human-queue item carrying a recorded reason code (BR-18). TC-049, negative: if it instead loops past the guard limits, or stops without a reason code, the test has failed — in the design's own words, "looping or failing silently means the retry loop is not finished." Blocked by: domains C, D, E — none built.

The fold test (TC-050, TC-051)

Given an event stream from genesis, when it is periodically folded (H-1) and compared against the fold from the nearest snapshot (read-only, per H-3), then (TC-050, positive) the two states are identical. TC-051, negative: if they diverge, per §4.1 this is a release blocker, not a warning: "divergence proves the event model is incomplete." Blocked by: domain H — no DDL has ever been applied and no fold has ever run.

The second run, a week apart (TC-052, TC-053)

Given the same objective run twice on the same product a week apart, when the second run completes, then (TC-052, positive) it needs fewer retries and less human intervention than the first (§1.4). TC-053, negative: if it needs the same or more, then "the extraction step is decorative and everything above it is expensive theatre" — a product-viability signal that should trigger review of domain G (memory & learning), not an automatic block. Blocked by: the entire control loop, domains C–H, and by the fact that this run is also how the numeric baseline gets set for the first time — the one thing D-039 defers until it exists.
