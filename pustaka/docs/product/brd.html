How to read this document

The section structure mirrors a standard enterprise BRD table of contents, adapted to GAOS's actual scale — a design-complete, largely unbuilt project with one owner. Every claim is either grounded, meaning it points at a real artifact section, a real file, or real git history, or it is decided, meaning a product-owner ruling in the decision log put it there, or it is explicitly marked open, meaning it is a business decision this document will not invent on the owner's behalf. No numeric target, customer name or date appears here unless it already exists somewhere in the repository. There is exactly one exception, and it is labelled as one: the rate card in §8.11.1 contains proposed prices the owner asked for and has not yet confirmed, which is why every figure in it is marked proposed and carries OQ-21.

The framing, stated once and not repeated

Version 0.1 of this document was written on the instruction that GAOS was a commercial multi-tenant SaaS, and said plainly that the framing had no evidence in the repository. On 2026-08-08 the owner replaced it. GAOS is open core, self-hosted: this repository is given away and is a complete working system on its own, private submodules may add capability but may never be required for it to run, and revenue comes from installation, support and licensed add-ons rather than from hosting anything (D-026). Domain K below is therefore a requirement set now, not an agenda.

What that changes downstream is worth naming once: the tenant boundary is no longer a wall between paying strangers. The structural multi-tenancy stays exactly as designed — Tenant still carries plan, maxConcurrentTasks and budgetCapUsd, every vertex still carries tenantId, database-per-tenant is still the data model's default — but it now separates colleagues inside one operator's deployment. That lowers how strong authentication must be on day one (OQ-11) without removing the need for it, and it moves the cost, the uptime and the residency of everything onto the operator's side of the line (D-030, D-031, D-034).

1. Executive summary

1.1 Vision statement

Drafted from the project's own words — open for the owner to confirm or rewrite:

An operating system for software agents in which the graph, not the prompt, is the primitive: work is scheduled by traversal, every change is an event, the orchestrator holds nothing, and any moment in a product's history can be reconstructed and explained.

1.2 Business summary

GAOS coordinates fleets of software agents against a product master record — a business brief, user stories, acceptance criteria, diagrams and an indexed repository — stored as a graph in ArcadeDB. The record is scored for completeness before any work is dispatched; the planner refuses to plan against a brief that is too thin. Work is decomposed into an acyclic task graph, routed to a role and a model tier by capability and risk rather than cost, executed one turn at a time in the product's workspace through ai-manager, scored on five weighted dimensions, retried under explicit guard limits, and gated by a human where the risk demands it. Everything that happens is written to an append-only event stream, which is simultaneously the recovery path, the audit trail, and the replay source.

1.3 Background

There is no public release and no user. The design is complete and written down in three self-contained documents committed on 2026-08-02 under artifacts/v1/; the repository README calls them "the design — the source of truth". What is built, as of v0.1.0, is the operator surface and the path a browser request takes to reach it. The README states the position plainly: "this release is v0.1.0 and it is a deployment, not an agent OS."

1.4 Definition of project success

The design supplies exactly one success measurement, and it is a good one because it cannot be faked by a demo. From the architecture document's closing paragraph:

Run the same objective on the same product twice, a week apart. If the second run needs fewer retries and less human intervention, knowledge is accumulating and the loop closes. If it does not, the extraction step is decorative and everything above it is expensive theatre.

Decided — success is conformance, and the targets are binary

D-039 answers OQ-08. GAOS succeeds when the system as developed builds and runs without issue and passes every acceptance criterion and every scenario in the QA test plan — positive and negative alike, every case in the register — together with the three acceptance tests in §4.1. That is the target in full, and it is pass/fail on purpose.

Numeric outcome targets remain deliberately unset. The reason has not changed: there is no operational baseline — no users, no tenants, no run has ever executed against a real model, and the measurement above has never been performed — so a percentage written here would measure whoever chose it. Numbers become settable once the second-run measurement has been performed at least once against a real model, which after D-026 depends on an operator volunteering it. D-025 names who runs the checks meanwhile.

2.2 Operational challenges

  • Nothing past the operator surface exists. The scheduler, the runner, the review engine and the ArcadeDB schema are all specified in full and implemented in none. The dashboard reads fixtures behind an interface.
  • No model has ever been called. The role-to-model map in the prototype names claude-opus-5, claude-sonnet-5 and claude-haiku-4.5, but no model gateway is built and no run has ever produced a real token.
  • The DDL has been applied to a scratch database, and to nothing else. The data model document warned in its own words that the ArcadeDB SQL dialect moves between releases and that the schema should be run against the target version in a scratch database first. That happened on 2026-08-16, against the 26.7.2 that D-043 pins, and it was worth doing: 53 of 314 statements failed, one of them because of an error in the data model rather than a difference between versions (D-045, D-046). The schema now exists as ten runnable files under dashboard/schema/, and since 2026-08-17 both tiers carry it and store_arcade.go reads and writes it. A third amendment came out of that first write (D-047).
  • Authentication is absent, not partial. The back office is reachable and its login checks nothing — acceptable for a prototype, disqualifying for a tenant boundary.
  • Single-node infrastructure. One public edge machine (clino, 1 vCPU / 957 MiB, no Docker) fronts one private VM. High availability is discussed in the data model and deferred.

2.3 Opportunity

The gap GAOS aims at is not "run an agent" — that is commodity — but account for what an agent did. Because every prompt is reconstructible from ContextSlice and its USES_CONTEXT edges, and every state change is an event, GAOS can answer "why does this code exist?" by walking from a commit back through a run, a task, an issue and a requirement to a sentence someone wrote in the back office. Systems that keep their state in a conversation cannot answer that question at all.

Who that is worth something to is now decided (D-027): researchers, small companies, and individual experts inside and outside IT. For a researcher the same mechanism has a second name — reproducibility. A run that can be folded back from its event stream, with the exact context each attempt received, is the difference between a result that can be published and a transcript that cannot be defended. That is the same capability an enterprise would buy as governance, sold to a buyer who does not need a compliance certificate to justify it.

4.1 Evaluation method

The design specifies three acceptance tests that double as the evaluation method, and they are reproduced here as business commitments rather than engineering trivia, because each one is the only honest proof that an objective was met:

  • The unsatisfiable task. Run a task whose acceptance criterion contradicts a domain rule. A correct system stops within the guard limits, records a reason code, and leaves a human queue item. Looping or failing silently means the retry loop is not finished.
  • The fold test. Periodically fold the event stream from genesis and compare against the fold from the nearest snapshot. Divergence proves the event model is incomplete.
  • The second run. The same objective on the same product, a week apart.

Review cadence for these — who runs them, how often, and what happens when one fails — is OQ-13.

6. Current business process (as-is)

What actually happens today, end to end, with nothing implied:

  1. An operator opens Mission Control at /app/. The home page is the list of products; each product has its record, its Blueprint and a board, and the back office and the create-workflow wizard sit beside them, all rendered server-side from Go templates over HTMX. The engineering floor, its inspector, meeting room and timeline strip, and the simulation that moved them, were deleted in v0.29.0.
  2. Work runs as turns through ai-manager. When the runner is switched on, the scheduler picks a ready task, egress screens its brief, and GAOS records a TaskRun with a request id before sending one turn to ai-manager, which runs it in the product's workspace — one live turn per product. The reply's handoff moves the task, and after the turn GAOS compares the workspace with the pinned Blueprint; drift refuses the next dispatch. Nothing reviews the result yet. With the runner set to manual the scheduler only moves work to ready, and a turn is sent when the operator moves one ready card to working (D-080).
  3. The board moves only when a task does. Every task status change writes a TaskMoved event, so the board is a fold of the stream like everything else, and the vendored sisflow board reads the same API.
  4. The back office accepts a login and checks nothing. Any value opens it. It then shows product records, a readiness checklist, a graph projection count and story coverage. What it writes is persisted and survives a restart; the world it starts from is still the fixtures in dashboard/fixtures.go.
  5. Events are written to the graph, and the stream is the whole record. dashboard/store_arcade.go appends every event as an Event document before its mutation commits, and rebuilds state from ArcadeDB on boot, then polls every open turn by its request id; dashboard/store_mem.go remains the in-memory double the conformance suite runs the same cases against. The 160-entry ring came out in v0.11.0 — the stream is unbounded and append-only as BR-04 asks, an event carries the delta a reducer folds rather than a photograph of the whole state, and replay is a fold from the nearest snapshot forward.
  6. The stacks serve four paths from one origin — / landing, /app/ Mission Control, /docs/ this site, /api/ the health endpoint — behind a per-product Traefik on the private VM, fronted by nginx on clino, which terminates TLS and forwards plain HTTP over WireGuard.

The distance between §6 and §7 has a single shape, and it is the opposite of the usual one: the specification is ahead of the implementation, not behind it. 7.3 Happy path

An operator creates a product record and pastes in a brief, four stories with two acceptance criteria each, a sequence diagram and a repository URL. Injection parses it and indexes the code; readiness scores 78, which is the Working band, so planning is allowed with gates only on risk signals. The operator states an objective and a gate policy. The planner produces an acyclic graph of eleven tasks with roles attached. The scheduler finds four tasks whose prerequisites are all satisfied and dispatches them one turn at a time — one live turn per product — through ai-manager into the product's workspace. Each run assembles a context slice from the master record, calls a model, writes a diff, and is scored. Nine tasks score above 85 and are accepted. One scores 61 and is retried with a widened context slice; the second attempt scores 88. One touches a schema migration, so it carries a security reviewer and an approval gate; the operator approves it. The workflow closes, three lessons are extracted as Knowledge, linked back to the product, and the readiness score rises.

7.4 Where autonomy actually begins

Autonomy is not a switch. It starts at the moment the scheduler can find a ready task without a human naming it, which requires five things to already be true at once: the dependency graph is acyclic, a capable agent exists for the role, the product has no live turn (BR-38), the readiness gate has passed, and the budget guard is in its normal zone (§8.10.1). Miss any one and the board looks idle for reasons nobody can explain. All five must be surfaced in the UI as the blocking reason — this is a business requirement, not a nicety, because an unexplained idle board is indistinguishable from a broken product.

7.6 How a task reaches a model — two modes, one contract

Superseded by §7.7 on 2026-11-02 and deleted in v0.29.0 — kept as the record

GAOS no longer runs a model tool itself (D-055). This section and §7.6.1–§7.6.3 describe the CLI adapter, the packet on disk and the handoff file that the dashboard shipped until M14 replaced them; M14.7 deleted them in v0.29.0. The successor is §7.7. Two things carry over unchanged: the handoff is still a contract rather than a convention, and the invocation is still recorded and never branched on.

The design says "model gateway · adapters, routing, cost and token accounting" and does not say how the gateway talks to a provider. It is now decided that there are two supported ways, and they are interchangeable (D-036):

  • CLI mode — spawn the provider's command-line tool as a subprocess. No API key is configured and no HTTP request is made; the operator's existing subscription is what pays for the work.
  • API mode — call the provider's HTTP API with a key the operator supplies, metered per token.

Development starts with CLI mode (D-033) because it reaches a first real run without anyone configuring a key, which is the arrangement D-030 requires — GAOS never holds somebody else's provider credential in either mode, but in CLI mode there is nothing to hold. API mode is not a later replacement for it; it is the second adapter behind the same seam, and the deployment picks.

What makes them interchangeable is a single rule: the contract is the mode-independent part. Both modes freeze a task packet, both must produce a handoff document in the same shape at the same path, and both record the same evidence. Nothing above the adapter — not the scheduler, not the reviewer, not the fold — may behave differently depending on which one ran (BR-33). The mode is recorded on the attempt as TaskRun.invocation, so a replay can tell you how a result was produced without any other part of the system having known.

The handoff document deserves its own sentence, because it exists for CLI mode's sake and is kept in API mode deliberately. An API call returns a value to the caller; a CLI invocation returns an exit code and leaves its work on disk. So every agent must be instructed to produce a document, and that document is what the next agent reads. Without it a chain of CLI-invoked agents can pass nothing but the files it happened to edit, and the graph loses the reasoning entirely. Requiring the same document in API mode costs a few tokens and buys one identical evidence trail instead of two.

7.6.1 The master configuration

Which mode runs is a deployment decision held in one place, not a per-call choice scattered through the code. One file, read at boot, and every routing decision resolves against it:

config/model.yaml
# The one place that decides how GAOS reaches a model.
mode: cli                  # cli | api | auto   ← the master switch
fallback: none             # none | cli | api   (used only when mode: auto)

# mode: auto is compatibility mode. Prefer `primary`, fall back when the
# preferred adapter is unavailable or cannot serve a required capability.
# A fallback is an event (ModeFellBack), never a silent substitution, and
# the mode that actually ran is recorded on the attempt.

providers:
  anthropic:
    tiers:   { low: haiku, mid: sonnet, top: opus }
    cli:
      command:     claude
      pin:         ">=2.0.0 <3.0.0"   # smoke-tested at boot; refuse to start if it drifts
      reports_usage: false            # drives costBasis — see D-11
    api:
      key_env:     ANTHROPIC_API_KEY  # the OPERATOR's key. Never GAOS's, never a customer's.
      reports_usage: true

accounting:
  price_table:   config/prices.yaml   # estimation input when reports_usage is false
  on_unknown_model: refuse            # the only permitted value — BR-37. Never zero, never a guess.

egress:                               # domain L applies in BOTH modes, identically
  redact:        [secrets, credentials, env-files]
  allow_paths:   ["src/**", "tests/**"]
  local_only:    false                # true = no-egress mode (L-6)

Three properties of this file are requirements rather than conveniences. One switch, deployment-wide — a per-task mode override is deliberately not offered, because it would make two attempts at the same task incomparable and quietly break the fourth replay scope in H-4. The key is always the operator's, read from their environment, in a self-hosted deployment they own (BR-29). And the egress block is not per-mode: the pre-dispatch check in L-4 runs identically whether a subprocess or an HTTP request is about to carry the slice out.

The vendor is per product, and that is not a mode override. Since D-067 each product chooses which of the gateway's session vendors runs its tasks — Claude CLI only, the Antigravity pool only, or both, chosen by the task's role — and the Antigravity model. Every attempt still goes through the same gateway in the same mode, so the property above is untouched: two attempts at one task are comparable because a task's vendor changes only when a new session opens, and the run records which vendor it went to (BR-45).

Two of those blocks are shaped by decisions taken after this file was first written, and neither needs it rewritten. providers is a map with one entry rather than a single provider because D-041 makes the gateway multi-provider — a second vendor is a new entry, and its tiers line is where it maps into the gateway's normalised low/mid/top vocabulary rather than exposing its own model names (BR-36). on_unknown_model: refuse is now the only permitted value: D-044 and BR-37 forbid reporting an unpriceable model as zero, because a zero is a figure the budget guard will let through.

7.7 How a task reaches a model — through the gateway

GAOS stops being the thing that runs a model. It becomes the thing that decides what a model is asked to do, inside which product, under which standing rules (D-055). The product owner's layering is the whole design: ai-claude-cli works the task with context; ai-manager shapes it with a workspace; GAOS shapes it with the product, the task details and the product's Blueprint.

  • One product, its own workspaces. ai-manager's workspace is a folder on the worker that Claude Code runs in. GAOS provisions one per product through an upstream API (D-059) and names it by id, never by path (BR-42). A product has two: the one its own turns run in, and the one its reviews run in — the same standing files in a second root, so a reviewer cannot reach the author's files (D-071).
  • The Blueprint is the standing layer. The product's BRD, technical and coding policies and knowledge sources are rendered into CLAUDE.md and .claude/rules/, which Claude Code loads on every turn. A published version is immutable, and every attempt pins one (D-058, Blueprint).
  • The brief is the per-task layer. The prompt carries the task, its criteria, the cited handoffs and the last review — and nothing that is true for the whole product.
  • One session per task. A retry resumes it; an escalation, a lost session or age opens a new one (D-056). The session is transport: GAOS stores the prompt, the reply and the handoff itself (BR-41).
  • The handoff travels in the reply, as one fenced gaos-handoff block that must echo the current run id (D-057).
  • One live turn per workspace, and recovery is a poll by request id with a deadline rather than a process to adopt or kill (D-060, BR-38).

8.5 Domain E — Review, scoring & retry

The most dangerous loop in the system. Every path through it must terminate and every termination must record a reason code.

scoring
final = 0.45·correctness + 0.20·completeness + 0.15·safety + 0.10·quality + 0.10·efficiency

correctness   tests pass, rule checks, reviewer verdict against acceptance criteria
completeness  every criterion addressed; no silently skipped file
safety        no secret leakage, no unsafe command, no out-of-scope change
quality       complexity, duplication, coverage delta

8.10.1 The budget guard — pacing, deferral and the hard stop

R-05 is the highest-consequence unbuilt guard in the system, and after D-030 the money it protects belongs to the operator rather than to this project. budgetCapUsd on its own is not enough to protect it: one number with one behaviour at the limit gives no warning, no smoothing and no graceful path. This section defines what the guard actually is (D-037).

The new variables. Five additions to Tenant, with defaults that make a fresh install safe rather than permissive. Every one is deployment-tunable configuration, not a commercial parameter:

PropertyDefaultWhat it controls
budgetCapUsd (exists)500.0The hard ceiling for one budget period
budgetPeriodmonthlydaily · weekly · monthly · total. When the window rolls over, spend resets and deferred work resumes on its own
budgetThrottlePct80The percentage of the cap at which the throttled zone begins. New dispatch stops here — not at 100

Workflow carries its own budgetCapUsd as the design already specifies; a workflow cap is checked in addition to the tenant's and never overrides it. The stricter of the two always applies.

The three zones. The zone is computed before every dispatch decision, from spend in the current period including estimated figures at full weight — because a cap that ignores estimates is no cap at all in CLI mode, where most figures are estimates:

budget zones

Why deferral rather than failure — the part worth being explicit about, because the naive implementation of a budget cap is to fail the task, and that is the expensive choice. Failing costs the money already spent on the attempt, unwinds nothing, and then invites a retry that spends more of the budget that just ran out. Deferring costs a delay. The work is still ready, its dependencies are still satisfied, its lease is released for someone else, and it starts the moment there is budget for it. That is what "delay work to stay inside the usage you have" means mechanically, and it is why J-12 keeps deferral out of the retry accounting entirely: a task deferred four times across a slow month has not failed four times, and must not arrive at max_retry_count having never been attempted.

This adds four names to a closed catalog

BudgetThresholdReached, BudgetCapReached, TaskDeferred and TaskResumed do not exist in the event catalog, and BR-05 says the catalog is closed — a new event type is a schema change to the fold, not a free addition. So this is one change in three places that land together: the catalog in gaos-arcadedb-model.html §08, the Go constants in dashboard/events.go, and the reducer that folds them. deferred is likewise a new task state and needs its transitions declared in the state machine before the scheduler can produce it. None of that is done, and none of it should be done piecemeal.

8.12 Domain L — Data protection, egress and residency

The owner's instruction on this domain was to treat it as a production-readiness question rather than a marketing paragraph, so it is written as one. Two facts frame everything below. First, after D-026 the GAOS project holds no customer data at all — there is no service, no database, no backup, nothing to have a residency policy about. Second, that answers the easy half. The hard half is that GAOS moves data on the operator's behalf: every attempt sends a slice of somebody's repository to a model provider, and that egress is continuous, automatic, and invisible unless the product makes it visible.

9.7 The design gate

The design gate is the review step between a design and its implementation: a fresh reviewer with no memory of the conversation that produced the design reads the design alone and attacks it. It is not the design review of §7.5 and §8.5 — that is a meeting after a failure, and it records a Decision. The gate runs before anything is built. D-068 is the ruling that put the gate in the product, and D-069 is the ruling that made it possible: it answers OQ-32 by fixing the isolation boundary at the packet rather than the workspace. The milestone is M17 and the forward specifications are TC-359…TC-379. The rules below are binding on M17 and on any later change to the gate; they are built as of v0.35.0, and D-070 records how they landed.

IDRule
BR-46Every story's implementation task has a design artifact and a review. Neither is optional, and the review happens before the first dispatch. A plan that does not wire the gate is refused, and the operator's dispatch route refuses a task whose review has not resolved. (D-068, D-070)
BR-47A reviewer sees the design artifact and the rubric, and nothing else from the desk: not the brief, not the goal, not the previous handoff, not the failure lesson, not the operator's answer, not the stories or acceptance criteria. It records path and line, never the matched text. It runs in the product's own reviewer workspace, which holds the published Blueprint whole and nothing else, so the reviewer's packet, its standing files and its own folder hold none of the author's files. The two folders are siblings under one managed root, and the gateway documents a write boundary rather than a read boundary between them. The standing files still carry the product's stories and its decisions, so the isolation the gate provides is over the packet and the workspace, not over the standing layer. (D-068, D-069, D-070, D-071)
BR-48An open Blocker stops the dispatch and holds the review in the operator's queue. The operator resolves it by sending the design back (BR-58); nothing clears the gate without a fresh review. The send-back records the signed-in account that made it, as the archive, prune and answer actions do (D-082, D-083); the other board moves are not attributed yet, and neither is the cancel that ends a loop at the cap. The operator's former power to clear the gate directly is replaced on purpose by the contested send-back and a fresh review. (D-068, D-070, D-079, D-084)
BR-49The isolation boundary is the packet and the workspace. The reviewer's workspace is the product's own reviewer workspace, a second root holding the published Blueprint whole — the standing files are the rubric, and a reduced set would be drift under BR-39 — and it is reset before every review turn, so it holds none of the author's files. What is withheld from the packet is the author's session state: the previous handoff, the failure lesson and the operator's answer. (D-069, D-071)
BR-50A design reaches a reviewer only as a GAOS-held artifact in the packet, because there is no other route: GAOS reads no folder, and its allowlist admits only the instruction files. The findings travel back the same way, as context. The gate is the planner's own DEPENDS_ON edge and BLOCKED status, and its record is an artifact — not the score-band Review vertex, which stays with the review engine that owns it. (D-069)
BR-58A design the review blocked goes back to its author only by an operator's send-back, at most three times per design; then the work is canceled. The design re-opens to ready with its own previous version, the review's findings and the operator's optional triage — one of CONTEST, ESCALATE, PROPOSE FIX or DECLINE and a note per finding — in its packet, in its own session where the session survives; the review waits in backlog on its dependency and, when the revision is delivered, runs on a fresh session that sees the new design and the rubric only. The revision is told to state its reasons as properties of the design without referring to the review; whether it does is not checked, so the revised design may carry the author's reading of the review to the fresh reviewer, and the reviewer's workspace has no read boundary to the author's (BR-47). A review blocked by its own verdict is never re-run on a design that was not delivered again — not by hand, not by a Blueprint sync, not through an approval of a design that delivered nothing; a revision that changes little is a new design, and the cap, not an identity check, bounds how often the gate is re-sampled. The operator's triage notes are not stripped as BR-53 strips external text: the operator is the trusted party, and the notes reach only the author, quoted. (D-084)

9.8 The QA catalog and the QA sync API

The QA catalog is a per-product register of test cases, and the QA tools reach it over a REST API (D-072, D-073). The rules bound what a machine caller may write. They are built as of v0.37.0, they rely on the design gate (BR-46) and the closed event catalog (BR-05) and amend neither, and the contract itself is published at The QA sync API. The question of who may edit a case's decision is OQ-34.

IDRule
BR-51Every field of a QA case has one writer. The planning half belongs to GAOS and changes only through the admin catalog endpoint or a seed re-run; the automation half belongs to the QA tools. Inside the automation half the run record (result, runAt, runRef) is written as one: an item that writes any of them must carry runAt, is refused stale when a newer run is stored, future when runAt is more than 300 seconds ahead, and run-incomplete when it carries a result without a time, so the newest run wins; only the admin token may force past stale. The QA side is create-only: it may add a case that does not exist and may never change, park, retire or delete one that does. (D-072, D-073)
BR-52The machine API answers only a bearer token read from a file, and fails closed. With no token configured every route is 503; a missing or wrong token is 401; a QA token on an admin route is 403; two equal admin, QA or outbound tokens, or a token that is short or lacks the gaos_ prefix, disable the API; a client from the clients file whose token equals any principal's, or whose token file others can read, is not loaded, and such a client reaches only the inbox routes of its own products; a request through /app is 404. The QA token reaches only the products named by id in GAOS_API_QA_PRODUCTS — any other product is 404 and an unset list reaches nothing — and only one write per token is in flight. A token is never logged or echoed. One route is the stated exception: POST /v1/products/{id}/staging answers HTTP Basic, one credential per product from a file, and a credential valid for another product is 404 (D-088); it is registered with the bearer routes, so BR-55 still holds. (D-072, D-074, D-075, D-083, D-088)
BR-53Every batch is bounded: at most 200 items and 1 MiB per request, strictly decoded, and over the bound nothing is applied. So is what a QA token can add: at most 5 new epics per request, 100 epics and 5,000 cases per product. Every text field of a request is screened for secrets and stripped of backticks, angle brackets and line breaks before it can reach an agent's prompt. The defect route adds a per-product limit of 50 new defect keys a day. (D-072, D-073, D-075, D-091)
BR-54QA data never moves a task. No result, case or sync changes the status or block reason of any existing task. The single write it may cause to the task graph is to add one card for a new epic, in the product's current workflow, born BLOCKED with the reason qa-epic-added and released only by an operator's board move, so a QA token can never create dispatchable agent work. (D-073, D-076, D-091)
BR-55A back-office session is verified, never inferred. A request is signed in only when its cookie's MAC verifies under the deployment's key and label, it has not expired (12 hours, absolute), its account still exists and the account's credential fingerprint still matches. Every route is refused without that unless it is on a fixed public list or is a bearer route, so a route nobody classified is refused. Sign-in fails closed: with no accounts, or in prod with no deployment label, nobody signs in. (D-079)
BR-57Every answer records where it came from — the back office with its deployment label and the signed-in account, or a machine client with its registered name, kind and origin — derived on the server. The origin is the client's registered host, not an observed address. Only the client's actor handle is taken from the request; it is recorded and shown as the client reported it, kept with the event for as long as the event (indefinitely, BR-04), and it may not name the operator. The machine API returns a back-office answer's actor as operator, never the account. A machine client asks, reads and answers only its own inbox items; an id another client uses is refused, the open-item cap counts per client, and a client name is never reused. The first answer wins; an identical retry by the same client is accepted again and writes nothing. The QA tool receives every decision on its own items, whatever answered them; the webhook is a notification and carries no source, so a decision counts as the operator's only when its source.kind is gaos. Any other client polls. (D-083, D-078)

12. Out of scope

Deliberate non-goals. Each is a decision with a reason, not an omission.

  • High availability and replication. Discussed in the data model and deferred; the event stream is the designated second recovery path.
  • Cross-tenant analytics as a default capability. Database-per-tenant makes it a separate pipeline, on purpose rather than by accident.
  • Snapshots as a source of truth. Explicitly rejected: if the UI can only replay from stored snapshots, any moment between two is unreachable and any snapshot-writing bug is invisible.
  • A generic edge type with a discriminator property. Explicitly rejected as the single biggest performance mistake available in this model.
  • Abstracting the database. The model is ArcadeDB-specific by choice.
  • Owning the tenant's repository or performing the merge. GAOS indexes and proposes; the gate is where its authority stops.
  • Building further UI before the loops exist. The build order puts Mission Control at step 9 and warns explicitly against starting with the visual layer — the warning is now retrospective, and the correction is to stop adding to it.
  • Hosting GAOS for anybody. D-026. No managed tier, no trial environment, no shared instance — which is also what makes L-1's "the project holds nothing" true rather than aspirational.
  • Billing, metering and usage-based pricing. There is nothing to meter after D-030, and no signup to bill against after D-032. The quota properties stay; the commerce they implied does not.
  • Reselling model capacity. Explicitly rejected in BR-29, not merely unbuilt.

FoldReducing an ordered event stream into state. The same operation serves recovery, audit and replay.

TenantThe isolation root and quota holder: a plan, a concurrency limit, a budget cap, and — by default — its own database.
Product slotThe convention by which several products share the private VM; GAOS is slot 03, giving it tunnel ports 18301 and 19301.
OperatorThe person or company that runs a GAOS deployment on their own machines, pays the model provider, and owns the data. The only party GAOS has a commercial relationship with. Distinct from a tenant, which is a compartment inside their deployment.
Open coreA complete, freely licensed product, with optional paid components that add capability and are never required for it to work (BR-27).
Task packetThe frozen context slice written to the workspace as files, which is what a CLI-invoked agent is given instead of a request body.
Handoff documentThe structured document every agent must produce at a declared path. Stored as an Artifact, it is how one agent's output becomes the next agent's input (§7.6).
Cost basisWhether a recorded cost was measured — reported by the provider — or estimated by GAOS from a local token count and a price table. Never dropped in aggregation.
Execution modeWhether the gateway reaches a provider by spawning its command-line tool (cli) or calling its HTTP API (api). One deployment-wide setting; recorded per attempt, never branched on.
PacingSmoothing spend across a budget period, so the ceiling in force at any moment tracks how much of the period has elapsed. Prevents a month's budget being spent in an afternoon.
DeferralA ready task held back because the budget guard is throttled. It keeps its place in the graph, resumes automatically, and counts as neither a retry nor a failure.
BlueprintA product's standing knowledge — its BRD, technical and coding policies and knowledge sources — rendered into its workspace and versioned. See Blueprint.
BriefThe per-task layer of what a model is given: the task, its criteria, cited handoffs and the last review. It is the prompt, and what the context slice freezes.
Gatewayai-manager, the one service GAOS sends model work to. It owns sessions and workspaces; ai-claude-cli behind it runs the model.
Product workspaceThe one folder on the worker that every session of a product runs in, named gaos-<tenant>-<product>.
Sessionai-manager's stored conversation. GAOS opens one per task and treats it as transport, never as the record.
TurnOne prompt and one reply inside a session — one attempt at a task.
EgressData leaving the operator's host. In GAOS it means the context slice: product record excerpts and source code, selected by traversal, sent to a model provider on every attempt.
