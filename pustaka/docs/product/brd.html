How to read this document

The section structure mirrors a standard enterprise BRD table of contents, adapted to GAOS's actual scale — a design-complete, largely unbuilt project with one owner. Every claim is either grounded, meaning it points at a real artifact section, a real file, or real git history, or it is explicitly marked open, meaning it is a business decision this document will not invent on the owner's behalf. No numeric target, customer name, price, or date appears here unless it already exists somewhere in the repository.

The framing caveat, stated once and not repeated

This BRD is written on the owner's instruction that GAOS is a commercial multi-tenant SaaS. That framing has no evidence in the repository. What does exist is structural multi-tenancy: Tenant carries plan, maxConcurrentTasks and budgetCapUsd; every vertex carries tenantId; database-per-tenant is the data model's stated default; the prototype ships two tenants, loop-eng and loop-labs; and budget caps are specified per workflow and per tenant. There is no price, plan definition, customer, contract, SLA, support model, or onboarding flow anywhere. Section 8 domain K therefore holds the commercial requirements as an agenda, with each row pointing at the open question that must be answered before it can be written as a requirement.

1. Executive summary

1.1 Vision statement

Drafted from the project's own words — open for the owner to confirm or rewrite:

An operating system for software agents in which the graph, not the prompt, is the primitive: work is scheduled by traversal, every change is an event, the orchestrator holds nothing, and any moment in a product's history can be reconstructed and explained.

1.2 Business summary

GAOS coordinates fleets of software agents against a product master record — a business brief, user stories, acceptance criteria, diagrams and an indexed repository — stored as a graph in ArcadeDB. The record is scored for completeness before any work is dispatched; the planner refuses to plan against a brief that is too thin. Work is decomposed into an acyclic task graph, routed to a role and a model tier by capability and risk rather than cost, executed by detached runners holding workspace leases, scored on five weighted dimensions, retried under explicit guard limits, and gated by a human where the risk demands it. Everything that happens is written to an append-only event stream, which is simultaneously the recovery path, the audit trail, and the replay source.

1.3 Background

There is no public release and no user. The design is complete and written down in three self-contained documents committed on 2026-08-02 under artifacts/v1/; the repository README calls them "the design — the source of truth". What is built, as of v0.1.0, is the operator surface and the path a browser request takes to reach it. The README states the position plainly: "this release is v0.1.0 and it is a deployment, not an agent OS."

1.4 Definition of project success

The design supplies exactly one success measurement, and it is a good one because it cannot be faked by a demo. From the architecture document's closing paragraph:

Run the same objective on the same product twice, a week apart. If the second run needs fewer retries and less human intervention, knowledge is accumulating and the loop closes. If it does not, the extraction step is decorative and everything above it is expensive theatre.

Open — no measurable business targets exist

A standard BRD requires numeric success criteria. GAOS has no operational baseline from which to set one: no users, no tenants, no run has ever executed against a real model, and the measurement above has never been performed. Setting numbers here would be fabrication. See OQ-08.

2.2 Operational challenges

  • Nothing past the operator surface exists. The scheduler, the runner, the review engine and the ArcadeDB schema are all specified in full and implemented in none. The dashboard reads fixtures behind an interface.
  • No model has ever been called. The role-to-model map in the prototype names claude-opus-5, claude-sonnet-5 and claude-haiku-4.5, but no model gateway is built and no run has ever produced a real token.
  • No DDL has ever been applied. The data model document warns in its own words that the ArcadeDB SQL dialect moves between releases and that the schema should be run against the target version in a scratch database first. That has not happened.
  • Authentication is absent, not partial. The back office is reachable and its login checks nothing — acceptable for a prototype, disqualifying for a tenant boundary.
  • Single-node infrastructure. One public edge machine (clino, 1 vCPU / 957 MiB, no Docker) fronts one private VM. High availability is discussed in the data model and deferred.

2.3 Opportunity

The gap GAOS aims at is not "run an agent" — that is commodity — but account for what an agent did. Because every prompt is reconstructible from ContextSlice and its USES_CONTEXT edges, and every state change is an event, GAOS can answer "why does this code exist?" by walking from a commit back through a run, a task, an issue and a requirement to a sentence someone wrote in the back office. Systems that keep their state in a conversation cannot answer that question at all. Whether that auditability is something teams will pay for is OQ-02.

3. Problem statement

Six problems, each named explicitly in the design material rather than inferred here.

#ProblemConsequence if unaddressed
P-1A prompt chain has no addressable intermediate state.Nothing can be scheduled, queried, or impact-analysed; the only way to find out what the system thinks is to run it again.
P-2Orchestrators that hold state in memory lose it on restart.A crash mid-run silently invents a new version of the truth; recovery is guesswork.
P-3Agents are given briefs that are too thin to work from, and nobody notices until the output is wrong.Retries grind against a missing specification. The model is blamed for a gap in the brief.
P-4Record rot: a team fills in the product record once and never updates it, while the codebase moves.Knowledge decays silently. A record scored 92 six months ago describes software that no longer exists.
P-5Retry loops have no termination condition and no cost ceiling.One runaway task consumes a month of spend, or walks up the model tiers reproducing the same wrong answer more expensively.
P-6Model output is unauditable — you can see that a task failed, never why the model believed what it believed.No post-mortem is possible, no model-routing decision can be evidence-based, and no regulated buyer can accept the system.

4.1 Evaluation method

The design specifies three acceptance tests that double as the evaluation method, and they are reproduced here as business commitments rather than engineering trivia, because each one is the only honest proof that an objective was met:

  • The unsatisfiable task. Run a task whose acceptance criterion contradicts a domain rule. A correct system stops within the guard limits, records a reason code, and leaves a human queue item. Looping or failing silently means the retry loop is not finished.
  • The fold test. Periodically fold the event stream from genesis and compare against the fold from the nearest snapshot. Divergence proves the event model is incomplete.
  • The second run. The same objective on the same product, a week apart.

Review cadence for these — who runs them, how often, and what happens when one fails — is OQ-13.

6. Current business process (as-is)

What actually happens today, end to end, with nothing implied:

  1. An operator opens Mission Control at /app/. The floor, the inspector, the timeline with its replay scrub, the meeting overlay, the back office and the create-workflow wizard all render server-side from Go templates over HTMX.
  2. The floor animates a simulation. Desks advance through planning → architecture → coding → testing → review → deployment because dashboard/sim.go advances them. No task is dispatched, no process is spawned, no model is called.
  3. The back office accepts a login and checks nothing. Any value opens it. It then shows product records, a readiness checklist, a graph projection count and story coverage — computed from fixtures in dashboard/fixtures.go.
  4. Events are emitted into an in-memory store. dashboard/store_mem.go holds them; dashboard/store.go is the interface that ArcadeDB will implement. dashboard/arcade.go reaches the database only for the health probe.
  5. The stacks serve four paths from one origin — / landing, /app/ Mission Control, /docs/ this site, /api/ the health endpoint — behind a per-product Traefik on the private VM, fronted by nginx on clino, which terminates TLS and forwards plain HTTP over WireGuard.

6.1 Root cause of the gap

The distance between §6 and §7 has a single shape, and it is the opposite of the usual one: the specification is ahead of the implementation, not behind it. Every control loop below is written down to the level of thresholds, guard limits and index definitions. What is missing is the code, and the build order that produces it already exists as a ten-step sequence in the architecture document — with an explicit warning not to start with the visual layer, which is precisely the step that has already been done.

7.3 Happy path

An operator creates a product record and pastes in a brief, four stories with two acceptance criteria each, a sequence diagram and a repository URL. Injection parses it and indexes the code; readiness scores 78, which is the Working band, so planning is allowed with gates only on risk signals. The operator states an objective and a gate policy. The planner produces an acyclic graph of eleven tasks with roles attached. The scheduler finds four tasks whose prerequisites are all satisfied, acquires a workspace lease for each, and dispatches them to detached runners. Each run assembles a context slice from the master record, calls a model, writes a diff, and is scored. Nine tasks score above 85 and are accepted. One scores 61 and is retried with a widened context slice; the second attempt scores 88. One touches a schema migration, so it carries a security reviewer and an approval gate; the operator approves it. The workflow closes, three lessons are extracted as Knowledge, linked back to the product, and the readiness score rises.

7.4 Where autonomy actually begins

Autonomy is not a switch. It starts at the moment the scheduler can find a ready task without a human naming it, which requires four things to already be true at once: the dependency graph is acyclic, a capable agent exists for the role, a workspace lease can be acquired, and the readiness gate has passed. Miss any one and the floor looks idle for reasons nobody can explain. All four must be surfaced in the UI as the blocking reason — this is a business requirement, not a nicety, because an unexplained idle floor is indistinguishable from a broken product.

8.5 Domain E — Review, scoring & retry

The most dangerous loop in the system. Every path through it must terminate and every termination must record a reason code.

scoring
final = 0.45·correctness + 0.20·completeness + 0.15·safety + 0.10·quality + 0.10·efficiency

correctness   tests pass, rule checks, reviewer verdict against acceptance criteria
completeness  every criterion addressed; no silently skipped file
safety        no secret leakage, no unsafe command, no out-of-scope change
quality       complexity, duplication, coverage delta
efficiency    tokens, latency, retries consumed

Correctness dominates deliberately: a beautiful implementation of the wrong behaviour should score below an ugly implementation of the right one, because the second is cheap to improve and the first is expensive to discover.

The failure signature is what makes retries intelligent rather than superstitious. Hash the normalised error — failing test name, error class, offending file — and compare across attempts. A changed signature means progress: the model fixed one thing and hit the next, so retry. An identical signature twice means the approach itself is wrong; escalating a tier will usually reproduce the same wrong answer more expensively, so it routes to a design review instead.

9. Business rules

Twenty-six rules, each one traceable to an artifact section or to committed code. These are the statements a reviewer — human or agent — can score an implementation against. They are the reason domain rules are worth 12 points in the readiness rubric.

9.1 Core invariants

IDRule
BR-01State lives in the graph. The orchestrator holds no authoritative state; anything cached in memory must be reconstructible.
BR-02Every change emits an event. An event that was never written is a state change that never happened.
BR-03Events reference the business id, never the physical RID — otherwise a restore into different buckets breaks the history.
BR-04The event stream is append-only and never updated. It is the only type whose retention policy differs from everything else.
BR-05The event catalog is closed. A new event type is a schema change to the fold, not a free addition.
BR-06Every mutation returns either the new state or a rejection reason, never a bare 200.

9.2 Readiness and planning

IDRule
BR-07Below an effective readiness of 45 the planner refuses to plan and returns the list of what is missing. Nothing is dispatched.
BR-08Band gates are mandatory, not advisory: Minimum caps the model at mid tier and forbids auto-merge; Complete still gates money, auth and schema.
BR-09effective = raw − drift_penalty, with the penalty capped at 25.
BR-10Crossing a band boundary downward emits ReadinessDropped and applies the stricter band immediately.
BR-11A task is atomic only if it has one concern, one workspace, and at least one acceptance criterion.
BR-12Role and model selection is ordered capability → risk → cost. Capability is a hard filter; risk overrides cost; cost decides only between already-acceptable options.

9.3 Scoring, retry and gates

IDRule
BR-13The final score is fixed at 0.45·correctness + 0.20·completeness + 0.15·safety + 0.10·quality + 0.10·efficiency.
BR-14Safety is a veto evaluated before anything else: below 60 the work stops regardless of the total.
BR-15A retry runs one model tier above the last attempt, and a second retry carries a senior reviewer.
BR-16An identical failure signature twice routes to a design review, not to a tier escalation.
BR-17The six guard limits are hard: 3 retries, 2 escalations, 2 identical signatures, capped exponential backoff, per-workflow and per-tenant budget caps, and human intervention at 2 escalations or any safety veto.
BR-18Every termination records a reason code. A silent stop is a defect.
BR-19A gated task cannot merge through any path, including the API.

9.4 Data and replay

IDRule
BR-20Replay reads through a read-only store handle. Never a flag.
BR-21The reducer is pure, total and order-stable. Snapshots are an optimisation and never a source of truth.
BR-22Task and TaskRun are separate records so per-attempt evidence survives a retry.
BR-23USES_CONTEXT hangs off ContextSlice, not Task, because the slice differs per attempt.
BR-24One edge type per relationship. No generic edge with a type property — traversal by edge type is index-free adjacency; filtering a generic edge is a scan of every neighbour.
BR-25Heavy payloads — prompt bodies, diffs, log blobs — are stored EXTERNAL or by reference to object storage, never inline on a vertex the scheduler traverses.
BR-26Tenancy is a database boundary first and a property second. tenantId is declared and indexed either way.

10. Scope

10.1 In scope

  • The six-layer system: UI, API gateway, orchestration, execution, model gateway, ArcadeDB.
  • The five control loops: schedule, score-and-retry, readiness, gate, learn.
  • The full graph schema — 25 vertex types, 3 document types, 32 edge types — with its indexes, invariants, retention and migration policy.
  • Mission Control as the operator surface, and the back office as the record-author surface.
  • Multi-tenancy as an isolation and capacity mechanism.
  • Both deployment tiers on product slot 03 behind the WireGuard tunnel.

The boundary is drawn where responsibility ends, not where the network does. GAOS reads a tenant's repository and writes to a branch, but it never owns either — which is why the merge is gated rather than performed. It calls a model provider but must never leak provider-specific shapes upward, which is what keeps the provider replaceable.

12. Out of scope

Deliberate non-goals. Each is a decision with a reason, not an omission.

  • High availability and replication. Discussed in the data model and deferred; the event stream is the designated second recovery path.
  • Cross-tenant analytics as a default capability. Database-per-tenant makes it a separate pipeline, on purpose rather than by accident.
  • Snapshots as a source of truth. Explicitly rejected: if the UI can only replay from stored snapshots, any moment between two is unreachable and any snapshot-writing bug is invisible.
  • A generic edge type with a discriminator property. Explicitly rejected as the single biggest performance mistake available in this model.
  • Abstracting the database. The model is ArcadeDB-specific by choice.
  • Owning the tenant's repository or performing the merge. GAOS indexes and proposes; the gate is where its authority stops.
  • Building further UI before the loops exist. The build order puts Mission Control at step 9 and warns explicitly against starting with the visual layer — the warning is now retrospective, and the correction is to stop adding to it.

Appendix C — Document notes

The section structure is adapted from the BRD in the sibling Cubiq repository, which in turn adapted an external enterprise template. Sections that did not survive the adaptation are worth naming so their absence is a decision rather than an oversight: there is no formal review board, no signature block, no organisational chart, and no "PO versus Berita Acara" decision matrix — §16 keeps the name and replaces the content with the design choices that are genuinely open.

Two structural departures from the reference: the decision log and the consolidated open questions are separate pages rather than trailing sections, because both are registers that will be edited far more often than the body of this document, and because answering a question should move a row from one page to the other. Sections 14 and the closing pointer below are therefore short by design.

This document is extensible by design: a new business concept is added as a new h2 following the pattern of the closest existing section — usually Business requirements §8 for a new capability, or Business rules §9 for a new constraint — without changing the file layout or the ToC registration.
