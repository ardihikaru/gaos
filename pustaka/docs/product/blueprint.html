Product

Blueprint

A product's Blueprint is everything a model must know about the product before it is told about a task: the business requirements, the technical and coding policies, and the repositories whose patterns it must follow. GAOS writes it into the product's workspace, versions it, and pins every attempt to the version it ran under.

Designed, not built

Decided by D-058; built by M14.3 and M14.4. Today the dashboard holds the BRD part only, and nothing reaches a workspace.

What a Blueprint is, and is not

The product record already answers what the product must do: problem, goals, scope, rules, stories, acceptance criteria, decisions. It does not answer how the product is built — which language conventions, which folder layout, which error-handling style, which shared library must be reused rather than rewritten. Without that, two tasks on one product produce code that works and does not belong together.

The Blueprint is both halves, as one versioned unit. It is standing knowledge: it is true for every task of the product, and it changes deliberately. What is true for one task only — its acceptance criteria, the handoffs it depends on, why its last attempt was rejected — is the brief, and travels separately.

A Policy is {key, kind, title, body, order, scope}. body is Markdown. scope is an optional file glob for later, when a rule should load only for the files it governs; the first version writes every rule unscoped, so every rule always loads.

Knowledge sources

A knowledge source is a repository the product must learn from — for a Go service, a Go template repository that fixes the layout, the interfaces and the reusable functions. It is recorded as {kind: git-repo, url, ref, purpose, note}:

  • url is https only and may not contain credentials.
  • ref is a tag or a commit SHA, never a branch: an attempt must be reproducible, and a branch is a moving target.
  • purpose is one of style, structure, interfaces, reference, so the model knows whether to copy, conform to, call, or merely consult it.

The first version records and lists knowledge sources; it does not fetch them. Placing a repository inside the workspace needs an upstream capability beyond the instruction-file allowlist, and raises questions of licence and size that are not yet answered (OQ-28).

What lands in the workspace

Claude Code loads CLAUDE.md and .claude/rules/*.md from its working folder on every turn, including a resumed one — ai-manager measured this. That makes the workspace the right place for standing knowledge and the prompt the wrong one: the prompt is capped at 256 KB, and is fixed at the start of a session.

workspace
gaos-t1-p5/
├── CLAUDE.md                       # product, goal, "managed by GAOS — blueprint v7, do not edit", rule index
└── .claude/rules/
    ├── 00-gaos-contract.md         # the reply contract below — survives resume
    ├── 10-brd.md                   # problem, goals, scope, out of scope, rules, metrics
    ├── 20-stories.md               # index only; full criteria travel in the brief
    ├── 30-decisions.md
    ├── 40-technical-policy.md
    ├── 50-coding-policy.md
    ├── 60-security-policy.md       # 6x: one file per further policy, by order
    └── 70-knowledge-sources.md     # url, pinned ref, purpose, note

Rendering is deterministic: the same Blueprint produces byte-identical files in either store, so the digest of the file set identifies the version. Every file is screened by the egress pass before it is sent (BR-32) — a credential pasted into a policy is refused exactly as one in a task brief would be. Only the allowlisted paths above can be written (BR-42), within 64 KiB per file and 256 KiB in total.

Versions and pinning

Editing a policy changes a draft. Publishing renders the draft, computes its digest, and stores an immutable BlueprintVersion {n, digest, files, publishedAt}. Publishing an unchanged Blueprint does nothing — no event, no new number — because two versions with one digest would make "which version did this attempt run under" ambiguous.

A drifted workspace refuses dispatch (BR-39). At submit, the workspace's synced digest must equal the pinned version's digest; otherwise the dispatch is refused with rule blueprint-drift. After the turn, the context ai-claude-cli reports it observed is compared with the manifest: an extra CLAUDE.md from a parent folder, or a missing rule, is drift too. This is how GAOS knows the model saw the Blueprint the record says it saw, rather than assuming it.

The brief: the per-task layer

The brief is the prompt. It carries only what is specific to this attempt:

  • the task — title, role, the story it implements, its acceptance criteria in full;
  • the handoffs of the tasks it depends on, cited by id;
  • on a retry, the review that rejected the previous attempt;
  • the run id, and a one-paragraph restatement of the reply contract.

The brief is what ContextSlice now freezes: its digest is the digest the egress pass cleared, and its citations are recorded per attempt, as before. The Blueprint is cited by version, not copied into the slice.

The reply contract

The model writes into a folder on another host, so GAOS can no longer read a handoff file. The handoff travels in the reply instead (D-057). The reply ends with exactly one fenced block tagged gaos-handoff:

reply
…the model's working notes, kept as the reply artifact…

```gaos-handoff
task: T-ab12
run: gaos.t1.T-ab12.2
role: implement
status: complete            # complete | blocked | partial
criteria:
  - id: AC-1
    met: true
    evidence: "handler returns 409 on an illegal move"
artifacts:
  - kind: file
    ref: "internal/board/move.go"
blockers: []
next_role: verify
must_know:
  - "the move table lives in one place; do not duplicate it in the UI"
```

GAOS takes the last gaos-handoff block and runs it through the same parser and validator the file used. Three checks are added. run must be the current run id — in a resumed session the model can see, and repeat, the block it wrote last time. Two blocks with different run ids are a failure, not a choice. And task must be the task the brief named. A reply that fails any of these is handoff-missing, however good its prose (BR-30).

Limits and open edges

  • The model can edit the files. Claude Code runs with full permissions in the workspace. The contract forbids it, the banner says so, and every sync re-asserts the digest — but a model that rewrites CLAUDE.md mid-turn will be caught after the turn, not prevented during it.
  • No product code lives in the workspace yet. Only instruction files can be written. A task that must change a real repository needs one placed in the workspace, which is OQ-27; until then deliverables travel in the reply.
  • Knowledge sources are listed, not read. OQ-28.
