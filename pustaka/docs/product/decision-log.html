Decision log

Every business and design decision GAOS has actually made, with the evidence that proves it was made. Fifty-two entries, each traceable to an artifact section, a committed file, a product-owner ruling, a measurement, or git history — and a destination for every question the open register resolves.

How this log works

A decision belongs here when it constrains future work and reversing it would cost something. It does not belong here because it seemed important at the time. Every row carries evidence: if a decision cannot be pointed at, it has not been made — it is an open question that somebody has been acting on informally.

The lifecycle

An entry on the open questions page is answered by the product owner. The answer is written here as the next D- number, dated the day it was decided, with the reasoning in the decision text and the evidence pointing at whatever records it. The question's row then flips to Answered → D-nnn. Nothing is deleted from either page; a reversed decision is superseded in place, the way D-004 would be if the event id scheme ever changed.

Dates appear only where git history or a document supplies one. A dash means the decision is embedded in the design artifacts committed on 2026-08-02 without a separately recorded date — which is honest, and better than inventing a day.

Commercial model

Six decisions taken together on 2026-08-08, answering the first block of the open register. They are one decision in six parts: GAOS is given away, and what is sold is the work of making it run and the optional parts nobody needs in order to run it. A seventh, D-038, followed two days later and named the first of those optional parts.

D-0262026-08-08 Answers OQ-01. Open core, self-hosted, with private submodules and paid services — not hosted SaaS. Anyone who clones this repository can run GAOS themselves, and this repository alone is a working system: no private component may ever be required for it to function. D-0452026-08-16 Reconciling the DDL against the version D-043 pins. Edge uniqueness is carried by a unique index on the two endpoints, not by a UNIQUE keyword on the edge type. D-0502026-08-21 The adapter never infers a task's outcome from the process exit code. The handoff document is the only authority on what happened. The measurement behind D-049 found that Claude Code separates a crash from a completed run but not a refusal from a success: an unknown flag, an unknown model, a failed authentication and an exhausted budget all exit 1 with a distinguishing terminal_reason, while a task the model could not do exits 0 with terminal_reason: completed — byte-identical, at the process level, to one it did. Reading success from that is the exact failure §7.6.3 already names as fatal to two-mode interchangeability: a reviewer that special-cases a CLI exit code. So the rule is inverted: the exit code may only classify crash versus ran; everything about the work itself is read from the mandatory handoff document, and a missing or unparseable one is a failed attempt with the signature handoff-missing (BR-30). This is not new policy — it is T-062/T-063 promoted from a convenience to the thing correctness rests on. What makes it cheap: the tool takes a --json-schema and honours it, so the declared shape is enforced by the adapter's own invocation rather than by parsing prose afterwards. Tested with a handoff schema, the model reported "status": "blocked" and "met": false against an acceptance criterion it could not satisfy — the refusal the exit code had hidden. D-0522026-08-22 The refused-dispatch event is named DispatchRefused, and its reason travels in the payload as a machine-readable rule. L-5 requires "a refused dispatch with its reason" and stops short of naming it, and BR-05 makes the catalog closed, so the name had to be decided rather than chosen at a call site. The reasoning is about the second caller, not the first. EgressRefused names the cause and reads more precisely today; it would also oblige BR-35's budget cap to invent a second name for the same shape of event when M10.3 lands, reopening a closed catalog for a distinction that belongs in a field. DispatchRefused names the effect — the dispatch did not happen — and carries rule: secret, local-only, size, empty-slice or path-escape today, and budget-cap when the guard arrives. It also pairs with the TaskDispatched the catalog already had. Two consequences that are easy to miss. First, the payload records the file and the byte offset of a detection and never the matched text: the stream is append-only (BR-04) and the timeline is rendered into a browser, so a payload carrying the credential would write it permanently into the record whose purpose is to prove it never left. Second, a refusal is returned as a result rather than a rejection — it is a recorded state change, and an ErrRejected would write the two events L-5 requires into the stream while keeping them out of the response that renders them. What this cost: one reversal in the state machine. A refused dispatch blocks a task that never started, and dashboard/state_test.go had asserted idle → blocked illegal on the ground that "nothing is running, so nothing can be blocked".
