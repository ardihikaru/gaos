Decision log

Every business and design decision GAOS has actually made, with the evidence that proves it was made. Eighty entries, each traceable to an artifact section, a committed file, a product-owner ruling, a measurement, or git history — and a destination for every question the open register resolves.

How this log works

A decision belongs here when it constrains future work and reversing it would cost something. It does not belong here because it seemed important at the time. Every row carries evidence: if a decision cannot be pointed at, it has not been made — it is an open question that somebody has been acting on informally.

The lifecycle

An entry on the open questions page is answered by the product owner. The answer is written here as the next D- number, dated the day it was decided, with the reasoning in the decision text and the evidence pointing at whatever records it. The question's row then flips to Answered → D-nnn. Nothing is deleted from either page; a reversed decision is superseded in place, the way D-004 would be if the event id scheme ever changed.

Dates appear only where git history or a document supplies one. A dash means the decision is embedded in the design artifacts committed on 2026-08-02 without a separately recorded date — which is honest, and better than inventing a day.

D-0532026-08-22 The heartbeat interval and the Heartbeat event cadence are two different numbers, and an expired lease is never taken by the acquirer. D-3 asks for a lease with an expiry and a heartbeat and does not say how often either happens, so the numbers had to be decided rather than picked at a call site. Why the last number is not the first. A beat is a field write to Task.lastHeartbeatAt, a mutable property the DDL already declares. An event is an append to a stream that is append-only (BR-04), snapshotted every 500 events, and rendered in full by the timeline. At 30s a twenty-minute run writes forty pills, and a six-desk floor running three attempts an hour writes around seven hundred an hour of pure noise. BR-02 says every change emits an event. Its subject is a state change, and a heartbeat is not one — the task is RUNNING before and after. It is evidence of continuity, and 300s is a resolution that answers the question. That is a reading, which is why it is a decision here rather than a comment in the code. And what the beat actually attests to. The supervisor, not the model. D-0542026-08-22 Requeue is kill-then-requeue, and the architecture page's recovery pseudocode was wrong about why. Its middle branch is commented "lease held, process gone". It does not know the process is gone. It knows the beat is stale, and a stale beat means the SUPERVISOR died — which says nothing whatever about the child, because D-2 detached the child precisely so it would outlive its supervisor. What that costs if it is read the easy way. Requeuing on a stale beat starts a second run in a workspace that may still have a live one in it: the exact silent corruption D-3 exists to prevent, reached through the routine meant to recover from failure. Two agents editing one checkout do not crash; they produce a diff neither of them wrote, which is then reviewed, scored and possibly merged. So a run that can be proved neither alive nor dead is MADE dead. The reconciler reads the run record, signals the process group, waits a grace period, signals again, releases the lease, and only then puts the task back at READY. Where nothing is able to kill — no adapter configured, no process ever recorded — the branch degrades to orphan rather than requeuing on a promise it cannot keep. A task that failed and needs a human is a worse outcome than a clean requeue and a far better one than silent corruption. This does not contradict BR-35's "never kills a run already in flight", and the difference is the subject rather than the verb. BR-35 is a BUDGET rule about a run this orchestrator is supervising and whose spend it can still account for; killing that forfeits money already spent. This is a RECOVERY rule about an unsupervised run whose supervisor is already gone. Different subject, opposite risk.
