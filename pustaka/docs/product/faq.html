FAQ

What GAOS costs, who it is for, what is open and what is sold, who pays for the AI models, and where your code goes when an agent runs. The same answers as the BRD, written for someone who has no reason to read a BRD.

Read this one first: GAOS does not work yet

Every answer below describes a product whose design is complete and whose engine is only partly built. As of v0.20.1 what runs is the operator interface, the graph store underneath it, the scheduler, the detached runner with its lease and boot reconciliation, the documentation and the deployment — and still no agent has ever been dispatched to a real model, and no model has ever been called. The repository's own README keeps a designed-versus-built table and this site repeats it on §2.1 of the BRD. Nothing here is a promise about a delivery date, because there is no roadmap with dates on it. If you are evaluating GAOS to use next month, the honest answer is: not yet, and watch the changelog.

Is it free, and can I run it myself?

Is GAOS free?

Yes. Clone the repository and run it. There is no licence key, no trial period, no seat count and no feature that switches off. Everything described in the architecture and graph documents — the scheduler, the readiness rubric, the review and retry loops, replay, Mission Control — belongs to the open repository.

The licence is Apache-2.0 — LICENSE in the repository root, decided as D-035. Use it commercially, modify it, redistribute it, embed it in something else; keep the notices and you have met the terms. It carries an explicit patent grant, which is the part a company's legal review actually looks for. The one thing the licence does not give you is the name: build on GAOS, say so, and call your fork something else (NOTICE).

Do I have to self-host?

Yes, and that is deliberate. There is no hosted GAOS, no managed tier and no shared instance, and none is planned. You run it on your machine, your server or your lab's hardware. The upside is the one everybody asks about anyway: your code and your data never touch anything belonging to this project, because this project runs nothing.

Do I ever have to buy anything?

No. The rule is written into the requirements rather than left to good intentions: the open repository is a complete working system on its own, and no private component may ever be required to install, run, plan, execute, review or replay (BR-27). A paid add-on that does not exist can only cost you a capability you did not have; it can never break what you are running.

You will pay somebody, though — just not this project. Running agents means calling AI models, and those are on your own account.

Who is GAOS for?

Three kinds of user, decided in D-027 rather than inferred from a market study:

Researchers

Because a run that can be replayed from its event stream, with the exact context each attempt received, is reproducible. That is the same machinery an enterprise would buy as an audit trail, wanted for a completely different reason.

Small companies

Teams that want agents doing real work against a real specification, with gates on the things that are expensive to get wrong — money arithmetic, authentication, schema changes — and without adopting a platform.

Individual experts

In IT and outside it. If you know a domain well enough to write down its rules, GAOS is built to make that knowledge the thing agents work from, rather than a prompt you retype.

I am an expert in my field but not in IT. Is this usable by me?

The part you would work in is designed for you: the back office, where the brief, the domain rules, the user stories and the acceptance criteria live. The readiness score exists precisely so that the system can tell you what is missing from a specification in plain terms instead of failing vaguely later.

The part that is not designed for you is standing the thing up — Docker, a database, TLS, a model tool, a tunnel. That gap is exactly why installation is something you can buy. It is fair to describe the paid install as "the bridge for the person who can write the brief but should not have to configure a reverse proxy".

What if I am a large enterprise?

Nothing stops you, and nothing is aimed at you. There is no SSO, no external-auditor tooling, no certification, no procurement process and no uptime commitment — some of that is deferred to later submodules (D-038) and some of it, like hosting, is refused on purpose. If your evaluation depends on any of those, GAOS is the wrong product this year.

Is there anything you promise never to sell?

Yes, and it is written down as a rule rather than a value statement (BR-28): no safety control, termination guard, budget cap or audit record is ever a paid feature — not in a submodule, not behind a support tier. An unattended agent holding a model credential can spend real money and write real code. Charging for the brake would be indefensible when you are the one paying for the fuel.

Why would I pay for installing software I can install for free?

Most people should not. The Starter install exists for the person whose time is worth more than 350 USD and whose expertise is somewhere other than Docker — which describes a lot of researchers and most non-IT domain experts. If you are comfortable with a compose file, the documentation is the same documentation the installer follows, and it is free.

Is this how open-source projects normally charge?

It is the common shape for a project with one maintainer, yes, and each choice has a reason worth knowing if you are evaluating whether the business behind the software is durable:

  • Fixed-scope installation packages, not hourly consulting. A fixed price with a written scope is something you can say yes to; an hourly estimate with a range is something you have to negotiate. The small tier exists to be bought without a meeting.
  • Support priced per production instance, not per seat. Seats are unobservable in software nobody hosts for you, and unenforceable in software that is open source. Instances are countable, and you already know how many you have.
  • Response times, not uptime. Covered below — it is the only kind of commitment anyone can honestly make about software running on your hardware.
  • The academic and individual reductions are published, not negotiated. A researcher who has to email for a discount uses something else instead.

Who pays for the AI models?

Do I bring my own model access?

Always. GAOS never resells model capacity, never holds a credential belonging to you, and is never in the billing path (BR-29, D-030). You use your own provider account, and what you spend is between you and them.

How does GAOS actually call a model?

Two ways, and you choose which with one setting (D-036):

  • CLI mode — GAOS runs the provider's command-line tool as a subprocess. No API key anywhere; your existing subscription pays for the work. This is what gets built first.
  • API mode — GAOS calls the provider's HTTP API with a key from your own environment, billed per token.

Either way it writes the task and its context into the workspace as files, and requires a structured handoff document back. That document is how one agent's work reaches the next agent, and it becomes part of the graph like everything else. The flow, the configuration file and the full comparison are BRD §7.6.

Which should you pick? It is a cost question more than a technical one. A subscription is a flat fee: a busy month costs the same as a quiet one, and a runaway loop wastes time rather than money. Accounting depends on the tool. The first supported adapter, Claude Code, reports its own token and cost figures, so those runs are labelled measured (D-051) — with the caveat that under a subscription the figure is what the work would have cost through the API, not what you marginally paid. Where a tool reports nothing GAOS estimates instead: a local token count priced from a configured table, labelled estimated, and never mixed with the other kind. If your model is not in that table GAOS reports no cost rather than a guess — never a zero (D-044). Who maintains that table is still OQ-22. An API key is metered with exact accounting: every cost is precise and every retry is a real charge, so the budget guard below stops being a convenience and becomes the thing standing between a retry loop and a bill.

One caveat on CLI mode, recorded rather than hidden: driving an interactive tool from a scheduler may sit outside the terms of the subscription you run it under (R-12). Checking your provider's terms is your call, not something GAOS can make for you — and if the answer is no, API mode is a setting rather than a dead end.

Can it spend my money without limit?

The design says no, and since D-037 the design is specific about how. The budget cap is not one number that trips at the end — it has three zones:

  • Paced. Spend is smoothed across the budget period, so a monthly budget cannot be burned in an afternoon. You set the period and how far ahead of the straight line you are willing to run.
  • Throttled, by default at 80% of the cap or when you are running ahead of pace or over a token-per-hour ceiling. GAOS stops starting new work and defers it with a resume time — the tasks keep their place, nothing fails, and they start again by themselves when the window moves on. Your floor shows "deferred — budget window" rather than looking mysteriously idle.
  • Exhausted at 100%: nothing new is dispatched until you deliberately raise the cap or the period rolls over. Work already running is always allowed to finish, because killing it would throw away what it already cost you.

Deferring rather than failing is the deliberate part. Failing a task for lack of budget wastes what the attempt already spent and then invites a retry that spends more — so a deferred task counts as neither a retry nor a failure (BR-34).

None of it is implemented yet, which is why it is the highest-consequence gap in the project (R-05) and why the guards must exist before the first real run — most of all in API mode. When you evaluate GAOS, check that this answer has changed before you point it at a metered account.

Where does my code go?

Where is my data stored?

On your machines. This project stores nothing, backs up nothing and processes nothing on your behalf, because it runs no service at all. Residency is whatever your infrastructure's residency is (D-034).

So nothing leaves my host?

That would be the comfortable answer and it is not the true one. Every attempt sends a slice of your product record and your source code to your model provider — selected automatically by traversing the graph, including files nobody reviewed before they were sent, and the selection gets wider on a retry, because widening the context is what a retry does.

That is the honest description of what an agent system does, and GAOS's answer is to make it visible and controllable rather than to phrase it away (BRD domain L): a published inventory of exactly what can leave, a data-handling profile you fill in for each provider and the interface displays, a redaction and path-allowlist pass that runs before dispatch and refuses rather than reporting a leak afterwards, and a no-egress mode for products that may only be routed to a locally hosted model. Like most of this page, it is designed and not yet built.

Will my code train somebody's model?

GAOS cannot answer that for you, and any product that claims to is speaking for a company it does not control. What it does instead is force the question to be answered before anything runs: each configured provider carries a profile recording what that provider says about retention and training, and when you last checked. Your agreement is with them directly — GAOS is not a party to it.

Can I delete data? The event stream is append-only.

Both are true at once, and the design is deliberate. Heavy payloads — prompts, diffs, logs, documents — are stored outside the record that references them. Deleting a tenant, a product or a run destroys those payloads while the append-only events keep their references, so history stays intact and unrewritten while the content is genuinely gone. A deleted artifact reads as deleted, never as a broken replay, and the deletion produces a certificate stating what went and what deliberately survived (L-7, L-8).

What does support actually commit to?

Is there an SLA?

Not for uptime, and there never will be — an availability promise about software running on your hardware would be a promise about a machine nobody here can see (D-031). What is committed is response time: how quickly a human replies, within stated business hours in one named timezone. Community support makes no commitment at all and is free permanently.

If I hit a bug, do I need a subscription to get it fixed?

No. Fixes go into the public repository for everybody. What a subscription buys is attention — a private channel, a response within a stated window, someone doing your upgrade — never access to correctness.

The project itself

What actually works today?

Mission Control (rendering a simulation, not a fleet), the documentation site, the landing page, and both deployment tiers end to end. The graph is real: the DDL applies on the pinned ArcadeDB version, both tiers carry it, and dashboard/store_arcade.go reads and writes it, so a restart rebuilds the floor from the database rather than from the fixtures. The scheduler decides as a pure function of the task graph and the runner supervises detached work under a workspace lease, reconciling every claimed run on boot. What is not built is the reason those exist: no model has ever been called from this repository, no attempt is recorded as a TaskRun, reviews are simulated, and authentication is absent — the back-office login accepts any value and checks nothing. The designed-versus-built table is maintained honestly and is the thing to read before forming an opinion.

Can I contribute or fork it?

Yes to both, and the terms are written down. Forking needs nothing from anyone — Apache-2.0, rename it, go. Contributing needs a DCO sign-off: one Signed-off-by line per commit, which git commit -s adds, certifying you have the right to submit the work. There is no CLA and no copyright assignment; your contribution stays yours. CONTRIBUTING.md has the rest, including which changes will be refused — anything that weakens a safety control so a paid component could restore it, most of all.

If it is free, what stops it being abandoned?

Nothing structural, and pretending otherwise would be dishonest — this is a single-maintainer project and the revenue model rests on one person's available hours (R-07). What the licence and the self-hosting decision buy you is the thing that actually matters in that scenario: the whole system is on your machine, the source is yours to keep running, and nothing you rely on can be switched off remotely.
