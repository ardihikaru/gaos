How GAOS and the QA tools work together

GAOS plans and tracks the work; the QA tools hold the test catalog and the scripts. They exchange one thing in both directions: the test cases of a product. This page explains who owns what, what moves on its own, what the two sync buttons do, how to set it up and what to look at when it does not work. The exact request and response shapes are in The QA sync API.

The idea in one picture

A product such as sample-product exists in both systems. In GAOS it is a product with a board: one card per test epic, each card showing how many of its test cases are automated. In the QA tools it is a product whose test cases are read from its automation repository, and whose scripts run in Playwright. Neither system is the whole truth, so each owns the part it is good at and tells the other.

Who owns what

Every test case has two halves, and each half has exactly one writer. That is what makes it safe to sync in both directions at once: the two flows never write the same field.

HalfFieldsOwner
Planningcase id, epic, module, features, user story, scenario, polarity (+ or −), level, priority, decision (planned, blocked, manual-only, wont) and its reasonGAOS. The QA tools may create a case, never change one that exists.
Automationis there a script (implemented), its path (spec), and, when they exist, the last result, its time and a run referenceThe QA tools. Inside this half the newest run wins, and an older one is refused as stale.

A case is shown as automated when its decision is planned and it has a script. If a script exists for a case GAOS has parked (blocked, manual-only or wont), the case is listed as needs a decision and GAOS never changes the decision by itself. The rules behind this are BR-51 to BR-54.

QA tools to GAOS: automatic

This direction needs no one to press anything.

  1. The product's automation repository changes (a case is added or a script lands).
  2. The QA tools' knowledge sync reads the repository, on its schedule or when someone starts it, and updates the product's test cases.
  3. If the product is flagged integrated with GAOS and the sync succeeded, the QA tools start a push to GAOS in the background. It never blocks or fails the knowledge sync.
  4. The push sends the cases in batches of 200: first the cases themselves (create-only), then the script facts of every case it sent.

Turning the flag on also starts a full push, and the product's page has a Sync to GAOS now button for a push on demand. What the push does and does not send:

  • Sent: cases whose status is planned or automated and whose code looks like TC-AUTH-001.
  • Skipped, and counted: blocked, manual-only and wont cases (the QA side may not park or retire a case in GAOS) and local drafts, whose codes start with L-.
  • Informational: a case that already exists in GAOS with different planning fields comes back as exists-differs. GAOS keeps its own values. The result shows the count; it is not a failure.
  • Retried: GAOS allows one write at a time per token, so a busy answer (429) is waited out and retried, up to three times.

The outcome (ok, partial or failed, with a note such as sent 1146 cases, unchanged 1067, exists-differs 79, skipped 554) is stored on the product and shown in its GAOS card in the QA tools.

What happens when someone adds a test case

This is the path of a brand-new case, end to end, with nobody touching GAOS:

  1. A test author adds a row to an epic file in the automation repository and merges it.
  2. The next knowledge sync in the QA tools picks the row up as a new test case.
  3. The push creates the case in GAOS as a planned case and bumps its revision. If the case already has a script, implemented and the spec path travel with it; otherwise the script facts follow when the script is written and the next sync runs.
  4. On sample-product's board the epic's card now counts one more case. When the script exists, the card's automated number rises. Nothing is written to the card's task: the numbers are read from the catalog every time the board is drawn.

If the case belongs to an epic GAOS has not seen, GAOS creates the epic too, and adds one new card to the board. That card is always born Blocked, with the reason added by the QA catalog; plan its design and review before unblocking. The reason is the design gate (BR-46): work the QA side adds must not start without a person releasing it. Only an operator moving the card releases it. If the product has no workflow yet, or the floor is being replayed at that moment, the epic is recorded without a card and the QA tab lists it.

What never happens

Data from the QA tools never moves an existing card, never changes a decision, never changes the BRD or a policy, and never reaches another product. The QA token is scoped to the products the GAOS operator listed for it. At most 5 new epics per request, 100 epics and 5,000 cases per product.

GAOS to QA tools: the two buttons

On a product's QA tab in GAOS there are two buttons. They are an operator's tool, for the times when you want GAOS and the QA tools to compare notes now rather than after the next knowledge sync.

ButtonWhat GAOS doesWhat it changes
Pull from QA toolsAsks the QA tools for the script facts of the product's cases, page by page (up to 200 cases a page, up to 20 pages a click), and applies them like any inbound result.Only the automation half in GAOS (implemented, spec). Today the QA tools hold no per-case run results, so no pass or fail comes back.
Push to QA toolsSends GAOS's planning data (decision, reason, scenario, module, features and the rest) for every case that changed since the last push, in batches of 200.Only the QA tools' gaos_decisions table. It never writes the synced test cases, which stay read-only there. A newer revision wins; an older push leaves the stored row alone.

After a click the tab shows a last-sync line for each button: ok or failed, how long ago, how many items, and a note. A push also lists up to 20 case ids the QA tools refused.

Some limits you will meet:

  • One sync at a time, and 30 seconds between starts, across the whole of GAOS. A second click answers the last sync started moments ago; wait 16s (HTTP 409).
  • A click lasts at most 60 seconds. The first push of a whole catalog (1,700 cases) takes two clicks, because each batch of 200 takes the QA tools about 15 seconds. GAOS remembers where it stopped, so the second click carries on; later pushes only send what changed.
  • The buttons are disabled, with the reason printed beside them, when the QA tools are not connected (GAOS_QA_URL unset), when the product is not in the list of products allowed to exchange data (GAOS_API_QA_PRODUCTS) or while the floor is in replay.

What you see on the board

sample-product's board has one card per test epic ("Automate: ..."), a design card, a review card and a release card. Each epic card carries a small badge: automated / cases with a bar, and a failing marker if the last run of one of its cases failed. The badge is a live view of the catalog; it is not stored on the task. Cards start in Blocked because GAOS's design gate holds all implementation work until a design has been written and reviewed; running those two cards is the first thing to do on a new product. The QA tab next to Board shows the whole catalog: totals, the per-epic table, epics with a regression, the cases that need a decision, and the two sync lines.

Setting it up

Both systems run on the same machine (rnd-v3-vpn) and talk over the tunnel, so no token has to cross the shared public edge. Three tokens exist on the GAOS side, one per purpose, and the three must differ (if two are equal GAOS disables its whole API). A token is the text gaos_ followed by 32 or more letters and digits.

The order that works, for a new product:

  1. Seed the product in GAOS (deploy/seed/sample-product/seed.sh for sample-product). It prints the product id.
  2. Put that id in GAOS_API_QA_PRODUCTS and redeploy GAOS. The deploy command is the one in the environments page, with the extra variables.
  3. Create the token files before the deploy (the deploy refuses a production tag without them), and put the matching values in the QA tools' env without printing them.
  4. Deploy the QA tools (run their migration first), then switch the product's integration on.

To revoke a token, empty its file (GAOS) or remove it from the env (QA tools) and restart that side. A token that is unset stops working at once: a caller with it gets 401 from GAOS (and 503 when no GAOS token is set at all), and the QA tools answer 503 when their inbound token is unset.

Checking that it works

  • In GAOS: the product's QA tab. The totals should match the QA tools' product (sample-product: 1,700 cases). The two last-sync lines say when each button last ran and how it went.
  • In the QA tools: the product's GAOS card shows the last push, its status and note. A healthy push reads rejected 0.
  • From a shell on the VM (the token is read from its file and never printed): GET /api/v1/products/p-6/qa/summary with the QA token returns the same totals as the tab.

Security in short

  • Tokens live in files (GAOS) or the server env (QA tools), mode 600, never in the repository or in a log. A request is checked in constant time and an unset token closes the surface.
  • Everything a caller sends is size-limited (200 items, 1 MiB) and strictly decoded: an unknown field is a refusal. Text from either side is screened for secrets and stripped of markup before it is stored.
  • Each side ignores the half it does not own, and the QA token cannot reach a product it was not given.
  • GAOS refuses redirects when it calls the QA tools and bounds the response; the destination is set by the operator in configuration, never taken from a request.
  • The back office itself still has no real login (OQ-34), so the two buttons can be pressed by anyone who can reach it; the cooldown and the product scope bound the damage.

What is not built yet

  • Per-case run results. The QA tools do not map Playwright runs to catalog cases, so a pull carries script facts only and the board's failing marker stays empty until they do.
  • Deleting a case. Nothing deletes a case in GAOS; one is retired with decision wont. A case removed from the automation repository now reaches GAOS as no script (the QA tools send implemented: false for it) and stays in the catalog.
  • Settling the exists-differs cases. The QA tools' product page has a GAOS decisions view that lists what GAOS sent and which fields differ from what the QA tools would send, so the differences can be found; changing a case's planning fields is still done on the GAOS side (the admin catalog route or a re-seed).

The tombstones and the decisions view are merged in the QA tools and become visible with their next deploy.

The decisions behind all of this are D-072 to D-076; the design is docs/designs/sample-product-qa-sync.md, and the QA tools' own side is docs/designs/GAOS_INTEGRATION.md and docs/designs/GAOS_INBOUND.md in the qa-automation-tools repository.
