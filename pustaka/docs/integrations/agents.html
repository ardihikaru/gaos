Integrations

Agents, severity and review fixes

A product says which agents work on it. That switches its pull-request flows on, role by role. The reviewer's finding becomes a severity you can see and filter on the board, a medium or worse finding asks GitHub for changes, and a low one can be fixed by an agent with a draft pull request into the reviewed branch.

Where this comes from

Decision D-102, rule BR-61 in BRD §9.6, cases TC-800 … TC-818 in the QA test plan. The pull-request flows themselves are described in Pull-request agents, and the fix machinery in Defect auto-fix. The examples use an invented product, Route Planner.

Assignment

A product lists the agents assigned to it. One agent can be assigned to several products: Kite, the unit-test builder, can serve Route Planner and three other products at once. The list is stored on the product record (Product.assignedAgents, Product.assignedSet), so it survives a restart and needs no schema change.

Three states of a product

StateHow you get therePull-request flowsReview event
Not configuredThe default for every product, old and newAll run, as before this featureComment only

Stop gating returns a product to “not configured” and forgets its list. Cards already on the board when a role is switched off are left alone and finish normally; only new cards are affected.

Which roles assignment switches

RoleAgentThe card it switches

Assignment switches a role on for a product; it does not choose which agent runs a card. Each of these roles has one agent except qa, and the QA tool, not an agent, runs the e2e work. Cards planned by an external-tasks API client and the test planner's cards from a bundle are never gated: they are explicit requests. They carry a source label instead, so you can filter them.

Who may change it

Only an account listed in GAOS_AUTOFIX_ADMINS sees the editor and may post to POST /agents/assign (fields product, agent repeated, action=save|reset). Every change is a RecordUpdated event naming the account's alias, never its address; the first save of a product says that gating and requested changes are now on.

Severity on the board

The reviewer ends its reply with a severity: none, low, medium, high or critical. GAOS stores it as a label of the family severity:* on the card, before anything is posted, so a review that was held for a secret or failed to post still shows what was found.

  • Kanban: a chip with the level written in it, first among the card's labels; none has no chip. Medium is amber, high red, critical a red block.
  • Table: a Severity column (sortable; worst first, a card without a severity last both ways) and a Labels column.
  • Filter: the Every severity select offers the levels on the product's cards and Medium or worse. The address keeps it, for example ?severity=medium%2B.

An operator may correct a severity through the label route (for example to downgrade a false critical). That changes the record only: nothing is posted again and the card does not move.

Comment or request changes

SeverityNot configuredConfiguredCard afterwards
none, lowCommentCommentDone (a low may plan a review fix)
mediumCommentRequest changesDone
high, criticalCommentRequest changesStays in Review, labelled pr-review:needs-manual

GAOS never approves. It requests changes only when it knows the pull request's author and the account that posts the review, and they differ; otherwise it comments. GAOS reviews a pull request once and never dismisses its own review, so a request-changes body ends with: “GAOS reviews once. When these points are addressed, a maintainer dismisses this review.”

Whose name is on the review

The review posts under the account of GAOS_GITHUB_TOKEN_FILE. If that is a person's token, a request for changes appears as that person's judgement, and where branch protection requires approvals it blocks the merge until someone dismisses it. Use a bot account's token before configuring a product.

Low findings fixed by an agent

A low finding can become a review fix. GAOS records it as a defect of kind review, already triaged easy, and the auto-fix pipeline does the rest: the fixer agent edits the code, and GAOS opens a draft pull request into the reviewed pull request's own branch, on top of the exact commit the reviewer read.

The fix follows the source's root branch. Route Planner's feature/route-limits was cut from staging and targets staging; the fix lands in feature/route-limits and reaches staging when that branch merges. GAOS never opens a review fix against staging, main or any other shared branch.

When a review fix is planned

  1. The product is configured and Mica (fixer) is assigned to it.
  2. Auto-fix is on for the product.
  3. The head branch matches one of reviewFixHeads — patterns with a literal first segment such as feature/*; *, ** and a bare branch name are refused.
  4. The repository is one of the auto-fix targetRepos and not an automation repository.
  5. The day's reviewFixCap (default 3, at most 20, per product, UTC day) is not reached.
  6. The head has not moved since the review, the file list is complete, and the pull request changes nothing under .github/.

The review card's reason says what happened: review posted; review fix planned (<card>), or a reason such as ; no fixer assigned, ; auto-fix off, ; branch not allowed for review fixes, ; review fix cap reached, ; head moved since review.

The settings

Two fields join the product's auto-fix settings (POST /products/{id}/autofix, admins only):

FieldMeaning
reviewFixHeadsOne branch pattern per line, at most 8. Empty: review fixes are off.
reviewFixCapReview fixes planned per UTC day. 0 means the default 3; at most 20. Counted apart from the defect fix cap.

The checks before anything is written

GAOS reads the pull request again before the agent runs, and once more before any branch exists. Any of these blocks the card with the reason shown and closes the review fix:

ReasonWhy
review-pr-closedThe pull request closed or merged.
review-base-changedIts head is another branch now.
review-base-movedIts head is not the commit the reviewer read.
review-forkIt comes from a fork (always refused).
review-shared-branchIts branch is the default branch, the auto-fix base, an allowed retarget base, or protected.
review-branch-not-allowedIts branch no longer matches reviewFixHeads.
review-files-incompleteGitHub's file list was cut short.
review-workflowsIt changes .github/.
review-not-targetThe repository is no longer a fix target.
review-unassignedThe fixer was unassigned since.
review-outside-pathsThe agent edited a file the pull request does not change, or added a file outside their folders.

The fixer sees the review findings and the pull request's code as untrusted data, fenced, after its instructions. Every other auto-fix check still applies: the allowed and forbidden paths, the CI-secret check, the egress screen. When the draft opens, GAOS posts one line on the reviewed pull request: GAOS opened a draft fix: <url>.

What happens next

  • The reviewed pull request merges before the fix starts: the fix card is canceled. GAOS checks the merge with GitHub first.
  • The draft's base changes (GitHub retargets it when the reviewed branch is deleted): GAOS records it and closes the review fix; it closes nothing on GitHub. A person decides what to do with the draft.
  • The draft is closed unmerged: the review fix closes; no second attempt is planned.
  • GAOS's own review fix merging into the feature branch plans no unit-test card; the feature branch's own merge does.
  • A review fix is never retargeted.

Where a card came from

Cards planned from a GitHub event or the staging callback carry no source label. The two kinds of card that assignment does not gate say where they came from, so you can filter them on the board's Label select:

LabelThe card
source:apiCreated by an external-tasks API client (a review, unit tests, an e2e automation or run it asked for).
source:bundleThe test planner's card for a bundle of merged pull requests.

The planner sets them; an operator cannot. An API request for a card GitHub already planned adopts that card and adds no label to it. There is no backfill: only cards planned from v0.64.0 on carry a source label.

Set it up for a product

  1. Sign in to the back office with an account listed in GAOS_AUTOFIX_ADMINS.
  2. Open Agents, choose the product in the filter, open Edit assignments.
  3. Tick Juno · PR Reviewer, Kite · Unit Test Builder and a QA agent (Ember or Flint), then Save. The notice under the filter now says which roles do not run.
  4. For review fixes: also tick Mica · Defect Fixer, and in the product's auto-fix settings turn auto-fix on, list the target repositories, and set reviewFixHeads (for example feature/* and bugfix/*).
  5. Check the Board: the next opened pull request shows a review card, then a severity chip.

To undo it, open Edit assignments and press Stop gating.

The second release: e2e kinds, staging creates and merged specs

Built in v0.65.0, waiting on the QA tool

GAOS's half of parts 1–3 shipped in v0.65.0 (D-103, design docs/designs/release-b-e2e-kinds-merge-unit-tests.md). The QA tool's half follows in its own pull requests. Until the QA tool lists a capability, GAOS sends what it sends today, so nothing changes by itself. Unit tests (part 4) get a design of their own.

The second release finishes the e2e automation builder. In short: when a repository is deployed to staging, GAOS runs its automation of the repository's kind and, if the product asks for it, has the QA tool create what is missing; a person approves each new spec; the QA tool may let it merge by itself once its checks pass; GAOS then runs it.

How it works: the data flow

Three systems take part: your CI (it deploys to staging), GAOS (it plans cards and asks), and the QA tool (it writes and runs the specs). GitHub merges; GAOS never does. Each flow below reads left to right; the numbered list says who calls whom.

Open the Agents page, pick the product, and open E2E repository kinds (admins only, the same accounts as auto-fix). Choose a kind for each repository and save. The staging run card of a repository with a kind carries e2e-kind:be or e2e-kind:fullstack: shown and filterable like every label, never settable by hand. Route Planner's acme/route-api is be; acme/route-web is fullstack. Saving kinds never touches assignment.

2. On a staging deploy: create what is missing

Tick On a staging deploy, ask the QA tool to create missing automation in the same editor. It is off by default, because it lets the staging credential start generation jobs. Then:

  1. The devops pipeline calls the staging callback, as today. GAOS plans the run of the repository's kind.
  2. On a new commit only, GAOS reads the product's QA catalog for planned cases with no automation at the kind's levels, and plans a create card for each: at most 2 per deploy (GAOS_E2E_CREATE_MAX) and 4 open per product (GAOS_E2E_CREATE_OPEN). The answer carries creates.
  3. A case is never created twice. Each of these blocks it: an open card creating it; its spec pull request open (30 days); merged but not yet implemented in the catalog (14 days); closed, or its create card failed (7 days).
  4. The QA tool writes the spec and waits for a person to approve it in the QA tool. The card ends Done when the spec pull request is open, and its reason says how it will merge.

3. The approved spec merges by itself, then runs

Tick Let the QA tool auto-merge a spec a person approved (off by default; it applies only in the Working or Complete readiness band). After a person approves a spec in the QA tool (an answer given in the GAOS Inbox leaves the pull request for a person), the QA tool asks GAOS (GET /api/v1/products/{id}/spec-auto-merge, QA token) and, when allowed, turns on GitHub's auto-merge pinned to the exact commit that was approved. It does so only when the automation repository has a ruleset that lets only the QA tool's account push qa-auto/* branches and a required check from a fixed source; otherwise it leaves the pull request for a person. GAOS never merges and holds no merge token.

When the spec pull request merges, GAOS plans one run of that case if the merged head is the approved commit, a qa agent is assigned, and the QA catalog shows the case implemented. If the catalog has not caught up yet, the row on the Pull requests page says waiting for the catalog and the run is planned when the result arrives (within 14 days). A merge at another commit is noted on the row and in the activity feed, and its case is not run.

What GitHub must allow first

The QA tool turns auto-merge on only after it has read, through GitHub's API, a ruleset that restricts updates and deletions of qa-auto/* branches and required checks bound to their source on the base branch. On a private repository GitHub offers rulesets only on a paid plan (Team, or Pro for a personal account); on the free plan the API answers "Upgrade to GitHub Pro or make this repository public" and every spec is left for a person to merge. The QA tool's GitHub account must also be a bot account without admin or maintain rights on the automation repository: an admin could bypass the rules, so the QA tool refuses one. Until both hold, keep the auto-merge switch off: GAOS still runs each new case once a person merges its spec.

Spec auto-merge is off by default everywhere. The GAOS switch is off for every product until an admin ticks it, and the QA tool’s QA_SPEC_AUTO_MERGE is unset, which is off. Keep both off for a private automation repository on GitHub’s free plan: without rulesets nothing can be merged safely, so every spec waits for a person.

4. Unit tests: read from the repository’s own CI result

Built in v0.67.0 (D-105, BR-65; design docs/designs/release-b4-unit-tests.md). GAOS runs no test. The repository owner adds one GitHub Actions workflow (the template is below); GitHub runs it on every merge commit in a disposable VM, and GAOS reads the result of that one workflow. A failure becomes a defect that waits for an auto-fix admin before any agent works on it. The feature is off for every product until an auto-fix admin turns it on. Writing missing tests is a later design (docs/designs/release-b4b-unit-create.md).

Two result sources (v0.68.0, D-106). Each product chooses where its result comes from: GitHub Actions (the default: GAOS reads the workflow’s check, the flow below) or Jenkins (the organisation’s Jenkins runs the tests on its own agents and posts the result to GAOS, below). Either way GAOS executes nothing, the defect, the hold, the close on a pass and the notices are the same, and a merge with no result is never a pass. Under either source, tests that need a database or the network must skip under -short before the switch is turned on.

On the Auto-fix page, open Unit tests (CI) for <product> (auto-fix admins only; POST /products/{id}/autofix/unit), read its Before you switch this on checklist, and choose where results come from. It needs auto-fix on, a fixer and a triager assigned, a fix-target repository, GitHub and the Brain Town reader (and, for Jenkins, the product’s unit-results credential). You can name another workflow file or check name, extra bases beside the auto-fix base branch (or the default branch), and a daily cap of new unit defects (default 5). First merge the workflow and make sure its run on the base is green.
  2. A merge plants a watch. A pull request of a fix-target repository merged into a unit base gives GAOS its merge commit. For that repository the old agent unit-test card is no longer planned; other repositories and products keep it, as Pull-request agents describes.
  3. GAOS reads the check. Every 2 minutes, at most 10 merges at a time: the push run of the workflow on that commit and base, and the check run named unit-tests of that run’s own check suite from the github-actions app. A check posted by anything else, and every commit status, is ignored. A failure counts only when the run carries the workflow’s unit-tests-total notice, so a job that never started (a billing or spending limit) files nothing.
  4. A failure files a held defect. One open unit defect per repository and base (plus one for a failed build), naming at most ten failing tests; a new failing set updates it. Its triage card is born Blocked; only an auto-fix admin can release or cancel it (the cancel closes the defect), and nobody else can close it. The group gets one line.
  5. After release the usual auto-fix path runs: triage, then a draft fix pull request against the branch whose tests failed. The fix may not change the failing tests’ files, add tests beside them or add TestMain or init, and it is never retargeted.
  6. A later green check closes it, or, while its card is still held, marks it (“checks passed at …”) so the admin can close it by cancelling the card.

The workflow the repository owner adds

Merge it through an ordinary reviewed pull request as .github/workflows/unit-tests.yml; GAOS never writes workflow files. Set the repository’s default workflow permissions to read-only and let no other workflow grant checks: write. Verify each pinned action SHA before merging (gh api repos/actions/checkout/commits/<sha> --jq .sha, and the tag’s ref points to it). The go test step holds no secret; a private-module token is used only by go mod download. Tests that need a database or the network are skipped with -short.

yaml
name: unit-tests
on:
  push:
    branches: [develop, staging, main]
  pull_request:
permissions:
  contents: read
jobs:
  unit-tests:
    name: unit-tests
    runs-on: ubuntu-latest
    timeout-minutes: 30
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
        with:
          persist-credentials: false
      - uses: actions/setup-go@d8cbb8045d7f43706b9177cceb36c1f91a6644d5 # v7.1.0
        with:
          go-version-file: go.mod
      - name: modules
        env:
          MODULES_TOKEN: ${{ secrets.MODULES_TOKEN }} # only if private modules are needed
        run: |
          if [ -n "$MODULES_TOKEN" ]; then
            git config --global url."https://x-access-token:${MODULES_TOKEN}@github.com/".insteadOf "https://github.com/"
          fi
          go mod download
          git config --global --unset-all url."https://x-access-token:${MODULES_TOKEN}@github.com/".insteadOf || true
      - name: go test
        shell: bash
        run: |
          set +e +o pipefail
          go test -short -json ./... > test.json
          status=$?
          mod=$(go list -m)
          # leaf tests only: a parent fails when a subtest fails; keep the deepest names
          fails=$(jq -r 'select(.Action=="fail" and .Test!=null) | "\(.Package) \(.Test)"' test.json | sort -u |
            awk '{a[NR]=$0} END {for(i=1;i<=NR;i++){leaf=1; for(j=1;j<=NR;j++) if(j!=i && index(a[j], a[i]"/")==1) leaf=0; if(leaf) print a[i]}}')
          n=$(printf '%s\n' "$fails" | grep -c . || true)
          printf '%s\n' "$fails" | head -n 10 | while read -r pkg test; do
            [ -z "$test" ] && continue
            dir=${pkg#"$mod"}; dir=${dir#/}; [ -z "$dir" ] && dir=.
            file=$(grep -l "func ${test%%/*}(" "$dir"/*_test.go 2>/dev/null | head -n 1 || true)
            file=${file#./}
            echo "::error file=${file},title=${test}::${pkg} ${test} failed"
          done
          echo "::notice title=unit-tests-total::${n}"
          exit $status

Jenkins posts the result

With Results come from: Jenkins, GAOS reads no GitHub check. The organisation’s Jenkins builds each merge commit of a unit base, runs go test -short on its own agents and posts one result per build. The result finishes that merge’s watch exactly as a GitHub check would: a failure files or updates the held defect, a pass closes it (or marks a held one), and a merge with no result 6 hours after it was merged ends no-ci with a line to the group at most once a day (“no unit-test result from Jenkins on a merge; is the Jenkins stage installed?”). The route and the credential. POST /api/v1/products/{id}/unit-results, HTTP Basic with the product’s unit-results credential: a line productId:user:password in the file named by GAOS_UNIT_RESULTS_BASIC_AUTH_FILE (mode 0600, a password of at least 32 characters, made with openssl rand -base64 32). It is checked by the staging callback’s gate but is never the staging credential: neither opens the other route. A credential of another product answers 404; five failures from one address in 5 minutes lock that address out of this route for 5 minutes. An empty file leaves the route off (503 jenkins-off). GAOS_JENKINS_ORIGIN (optional, e.g. https://jenkins.acme.example) is the only origin whose build links the Auto-fix page shows as links.

A result that arrives within 24 hours after its merge ended no-ci (a long Jenkins queue) is still accepted. Verified on: none yet — the two templates below are checked by reading; the first real run is the check: merge a pull request with a deliberately failing test, see one held card and one group line, then revert it. On that first run, also check that the watch’s commit is the pull request’s merge commit, that the caller’s address GAOS recorded is Jenkins’ public address, that a branch build cannot bind the credential, that a Jenkins account that is not an administrator sees neither Configure nor Replay nor Build on the report job, nor the credential on its folder, and that the report job runs with the Groovy sandbox off and no per-signature approval was added.

The work is split in two, because in a multibranch pipeline every branch builds its own Jenkinsfile and whoever pushes a branch controls it:

  • The test stage, in the repository’s Jenkinsfile. It runs on the unit bases only, holds no credential, downloads modules in one container and runs the tests in a second with --network none, resolves each failing test to its file, and archives four small files. At the very end (post { always }, so it never gates a deploy) it triggers the report job and does not wait.
  • The report job, defined in Jenkins by an administrator, in no repository. It is the only holder of the credential, stored as Username with password in its folder only, on a gaos-report agent restricted to it. It reads the upstream build from the build cause (never a parameter), refuses any upstream that is not exactly <folder>/<repo>/(develop|staging|main), refuses a replayed build, posts the commit the upstream checkout recorded, refuses a symlinked or oversized artifact, and passes the password to curl on its standard input. It runs with the Groovy sandbox off under a whole-script approval; never add per-signature approvals — they would open these calls to every pipeline on the instance.

Conditions the owner must meet (GAOS cannot check them)

The credential is bound only by the report job (folder-scoped), or, if there is no separate job, is branch-restricted to the unit bases — otherwise anyone who can push a branch the pipeline builds can read it. Run and Replay on the unit-base jobs are restricted to the people trusted to post results. Configure, Replay and Build on the report job, and every credential permission on its folder, are held only by Jenkins administrators. A holder of the credential can post any result for a pending merge of its product; the hold and the admin release bound what a forged failure can do.

      agent { label 'docker' }                          // a node with Docker; both containers share its workspace
      steps {

          env.UNIT_COMMIT = env.GIT_COMMIT                  // Groovy, before any test runs (a cross-check only)

          def goEnv = "export HOME=$WORKSPACE/.home GOCACHE=$WORKSPACE/.cache/go-build GOMODCACHE=$WORKSPACE/.cache/go-mod;"
          // Modules, with network. Private modules only: bind the module token here, then remove the rewrite.
          go.inside { sh "${goEnv} go mod download" }

          go.inside('--network none') {

          mkdir -p unit
          go test -short -json ./... > unit/test.json 2> unit/test.err
          echo $? > unit/status.txt
          mod=$(go list -m)
          # leaf tests only: a parent fails when a subtest fails; keep the deepest names
          sed -n 's/.*"Action":"fail","Package":"\\([^"]*\\)","Test":"\\([^"]*\\)".*/\\1 \\2/p' unit/test.json | sort -u |
            awk '{a[NR]=$0} END {for(i=1;i<=NR;i++){leaf=1; for(j=1;j<=NR;j++) if(j!=i && index(a[j], a[i]"/")==1) leaf=0; if(leaf) print a[i]}}' > unit/fails.txt
          grep -c . unit/fails.txt > unit/total.txt
          : > unit/failing.tsv
          head -n 50 unit/fails.txt | while read -r pkg test; do
            dir=${pkg#"$mod"}; dir=${dir#/}; [ -z "$dir" ] && dir=.
            case "$dir" in /*|*..*) continue;; esac
            file=$(grep -l "func ${test%%/*}(" "$dir"/*_test.go 2>/dev/null | head -n 1); file=${file#./}
            [ ${#test} -gt 512 ] || [ ${#file} -gt 512 ] && continue
            printf '%s\t%s\n' "$test" "$file" >> unit/failing.tsv
          done
          { cat unit/test.err; sed -n 's/.*"Action":"build-output".*"Output":"\\(.*\\)"}$/\\1/p' unit/test.json; } | head -c 1800 > unit/summary.txt
          exit 0
            ''')
          }
        }
        archiveArtifacts artifacts: 'unit/status.txt,unit/total.txt,unit/failing.tsv,unit/summary.txt',
                         followSymlinks: false            // a symlink left by test code archives nothing
      }
    }
  }
  post {
    always {                                             // after every stage: never gates deploy
      script {
        if (env.UNIT_COMMIT) {
          catchError(buildResult: 'SUCCESS', stageResult: 'UNSTABLE') {

                  parameters: [string(name: 'COMMIT', value: env.UNIT_COMMIT)]
          }
        }
      }
    }
  }

// Job "gaos-unit-report" — a Pipeline job an administrator defines in Jenkins, in the folder that holds
// the credential "gaos-p-9" (the product's unit-results credential). Not in any repository. Verified on: none yet.
pipeline {
  agent none
  parameters { string(name: 'COMMIT', defaultValue: '') }
  options { timeout(time: 15, unit: 'MINUTES') }
  stages {
    stage('report to GAOS') {
      steps {
        script {
          def up = currentBuild.getBuildCauses('org.jenkinsci.plugins.workflow.support.steps.build.BuildUpstreamCause')
          if (up.size() != 1) { error('not triggered by a unit-base build') }
          def job = up[0].upstreamProject, num = up[0].upstreamBuild.toString()
          def branch = job.tokenize('/').last()
          // The full path, not any folder ending in route-api.
          if (!(job ==~ /^acme\/route-api\/(develop|staging|main)$/)) { error("not a unit-base job: ${job}") }
          // The commit the upstream build recorded, and no Replay. this job runs with the
          // Groovy sandbox OFF and an administrator approves the WHOLE script once. Never approve these calls
          // one signature at a time: that would open them to every pipeline on the instance.
          def run = Jenkins.get().getItemByFullName(job)?.getBuildByNumber(num as int)
          if (run == null) { error('upstream build not found') }
          if (run.getCause(org.jenkinsci.plugins.workflow.cps.replay.ReplayCause) != null) { error('a replayed build is not reported') }
          // Exact repository match: normalise scheme, user, host case and a trailing .git; exactly one BuildData.
          def norm = { String u -> u.replaceFirst(/^[a-z+]+:\/\//, '').replaceFirst(/^[^@\/]+@/, '').replaceFirst(/:/, '/').replaceFirst(/\.git$/, '').toLowerCase() }
          def want = 'github.com/acme/route-api'
          def hits = run.getActions(hudson.plugins.git.util.BuildData).findAll { d -> d.remoteUrls.any { u -> norm(u) == want } }
          if (hits.size() != 1) { error("expected exactly one checkout of ${want}, found ${hits.size()}") }
          def commit = hits[0].lastBuiltRevision?.sha1String
          if (!(commit ==~ /[0-9a-f]{40}/)) { error('no recorded commit') }
          if (params.COMMIT && params.COMMIT != commit) { error('the COMMIT parameter differs from the recorded commit') }
          def runUrl = "${env.JENKINS_URL}${up[0].upstreamUrl}${num}/"
          def answer = ''
          for (int i = 0; i < 10; i++) {
            node('gaos-report') {                       // label restricted to this job; has jq and curl
              deleteDir()
              catchError(buildResult: 'SUCCESS', stageResult: 'UNSTABLE') {
                copyArtifacts projectName: job, selector: specific(num), filter: 'unit/*'
                withEnv(["U_COMMIT=${commit}", "U_BRANCH=${branch}", "U_RUN=${runUrl}"]) {
                  sh '''#!/bin/bash
                    set -e
                    for f in unit/*; do                       # no symlink, nothing over 64 KiB
                      [ -L "$f" ] && { echo "refused: $f is a symlink"; exit 1; }
                      [ "$(stat -c %s "$f")" -le 65536 ] || { echo "refused: $f is over 64 KiB"; exit 1; }
                    done
                    status=$(cat unit/status.txt); n=$(cat unit/total.txt)
                    jq -R -s 'split("\\n") | map(select(length > 0) | split("\\t") | {test: .[0], file: (.[1] // "")})' \
                      unit/failing.tsv > failing.json
                    summary=''
                    if [ "$status" = 0 ]; then result=passed; n=0; echo '[]' > failing.json
                    elif [ "$(jq length failing.json)" -gt 0 ]; then result=failed
                    else result=build-failed; echo '[]' > failing.json; summary=$(cat unit/summary.txt)
                    fi
                    jq -n --arg repo acme/route-api --arg commit "$U_COMMIT" --arg branch "$U_BRANCH" \
                      --arg result "$result" --argjson total "$n" --slurpfile failing failing.json \
                      --arg summary "$summary" --arg runUrl "$U_RUN" \
                      '{repo: $repo, commit: $commit, branch: $branch, result: $result, total: $total,
                        failing: $failing[0], summary: $summary, runUrl: $runUrl}' > body.json
                  '''
                }
                withCredentials([usernamePassword(credentialsId: 'gaos-p-9',
                                                  usernameVariable: 'GAOS_USER', passwordVariable: 'GAOS_PASS')]) {
                  answer = sh(returnStdout: true, script: '''#!/bin/bash
                    cred=$(printf '%s:%s' "$GAOS_USER" "$GAOS_PASS" | sed 's/[\\\\"]/\\\\&/g')
                    code=$(printf 'user = "%s"\\n' "$cred" |
                      curl -sS -K - -o answer.json -w '%{http_code}' -H 'Content-Type: application/json' \
                        --data-binary @body.json 'https://gaos.acme.example/api/v1/products/p-9/unit-results' || true)
                    err=$(jq -r '.error // ""' answer.json 2>/dev/null || true)
                    echo "${code:-000} ${err}"
                  ''').trim()
                }
              }
            }
            def code = answer.tokenize(' ')[0] ?: '000'
            def err = answer.tokenize(' ').size() > 1 ? answer.tokenize(' ')[1] : ''
            def again = (code == '409' && err == 'no-watch') || code in ['429', '000', '502', '503']
            if (!again) { break }
            sleep(time: 60, unit: 'SECONDS')               // outside node: no executor is held
          }
          if (!(answer.startsWith('200') || answer.startsWith('202'))) { unstable("GAOS answered ${answer}") }
        }
      }
    }
  }

GAOS never writes the Jenkinsfile or the report job. Review of the merged pull request does not guard branch builds; the credential’s scope does.

Tests that need a database or the network skip under -short

Both sources run go test -short. A unit base whose suite needs a live database, the network or another service is red on every clean merge, and every merge would file a defect. So before the switch is turned on, make each such test skip under -short:

go
func TestRouteStore(t *testing.T) {
    if testing.Short() {
        t.Skip("needs a database")
    }
    // …
}

A package whose TestMain opens the service checks testing.Short() after flag.Parse() and returns m.Run() without opening it. To find the tests to mark, run go test -short ./... once on a machine with no database and no network (for example in a container started with --network none after go mod download): every failure there is a test to mark or a real defect. A build tag (//go:build integration) is an equivalent way to keep such tests out; -short is the documented one because both templates pass it. The Auto-fix page shows the same rule in its Before you switch this on checklist.
