Agents, severity and review fixes

A product says which agents work on it. That switches its pull-request flows on, role by role. The reviewer's finding becomes a severity you can see and filter on the board, a medium or worse finding asks GitHub for changes, and a low one can be fixed by an agent with a draft pull request into the reviewed branch.

Where this comes from

Decision D-102, rule BR-61 in BRD §9.6, cases TC-800 … TC-818 in the QA test plan. The pull-request flows themselves are described in Pull-request agents, and the fix machinery in Defect auto-fix. The examples use an invented product, Route Planner.

Assignment

A product lists the agents assigned to it. One agent can be assigned to several products: Kite, the unit-test builder, can serve Route Planner and three other products at once. The list is stored on the product record (Product.assignedAgents, Product.assignedSet), so it survives a restart and needs no schema change.

Three states of a product

StateHow you get therePull-request flowsReview event
Not configuredThe default for every product, old and newAll run, as before this featureComment only

Stop gating returns a product to “not configured” and forgets its list. Cards already on the board when a role is switched off are left alone and finish normally; only new cards are affected.

Which roles assignment switches

RoleAgentThe card it switches
pr-reviewerJunoThe review card when a pull request opens

Assignment switches a role on for a product; it does not choose which agent runs a card. Each of these roles has one agent except qa, and the QA tool, not an agent, runs the e2e work. Cards planned by an external-tasks API client and the test planner's cards from a bundle are never gated: they are explicit requests. They carry a source label instead, so you can filter them.

Who may change it

Only an account listed in GAOS_AUTOFIX_ADMINS sees the editor and may post to POST /agents/assign (fields product, agent repeated, action=save|reset). Every change is a RecordUpdated event naming the account's alias, never its address; the first save of a product says that gating and requested changes are now on.

Severity on the board

The reviewer ends its reply with a severity: none, low, medium, high or critical. GAOS stores it as a label of the family severity:* on the card, before anything is posted, so a review that was held for a secret or failed to post still shows what was found.

  • Kanban: a chip with the level written in it, first among the card's labels; none has no chip. Medium is amber, high red, critical a red block.
  • Table: a Severity column (sortable; worst first, a card without a severity last both ways) and a Labels column.
  • Filter: the Every severity select offers the levels on the product's cards and Medium or worse. The address keeps it, for example ?severity=medium%2B.

An operator may correct a severity through the label route (for example to downgrade a false critical). That changes the record only: nothing is posted again and the card does not move.

Comment or request changes

SeverityNot configuredConfiguredCard afterwards
none, lowCommentCommentDone (a low may plan a review fix)
mediumCommentRequest changesDone
high, criticalCommentRequest changesStays in Review, labelled pr-review:needs-manual

GAOS never approves. It requests changes only when it knows the pull request's author and the account that posts the review, and they differ; otherwise it comments. GAOS reviews a pull request once and never dismisses its own review, so a request-changes body ends with: “GAOS reviews once. When these points are addressed, a maintainer dismisses this review.”

Whose name is on the review

The review posts under the account of GAOS_GITHUB_TOKEN_FILE. If that is a person's token, a request for changes appears as that person's judgement, and where branch protection requires approvals it blocks the merge until someone dismisses it. Use a bot account's token before configuring a product.

Low findings fixed by an agent

A low finding can become a review fix. GAOS records it as a defect of kind review, already triaged easy, and the auto-fix pipeline does the rest: the fixer agent edits the code, and GAOS opens a draft pull request into the reviewed pull request's own branch, on top of the exact commit the reviewer read.

The fix follows the source's root branch. Route Planner's feature/route-limits was cut from staging and targets staging; the fix lands in feature/route-limits and reaches staging when that branch merges. GAOS never opens a review fix against staging, main or any other shared branch.

When a review fix is planned

  1. The product is configured and Mica (fixer) is assigned to it.
  2. Auto-fix is on for the product.
  3. The head branch matches one of reviewFixHeads — patterns with a literal first segment such as feature/*; *, ** and a bare branch name are refused.
  4. The repository is one of the auto-fix targetRepos and not an automation repository.
  5. The day's reviewFixCap (default 3, at most 20, per product, UTC day) is not reached.
  6. The head has not moved since the review, the file list is complete, and the pull request changes nothing under .github/.

The review card's reason says what happened: review posted; review fix planned (<card>), or a reason such as ; no fixer assigned, ; auto-fix off, ; branch not allowed for review fixes, ; review fix cap reached, ; head moved since review.

The settings

Two fields join the product's auto-fix settings (POST /products/{id}/autofix, admins only):

FieldMeaning
reviewFixHeadsOne branch pattern per line, at most 8. Empty: review fixes are off.
reviewFixCapReview fixes planned per UTC day. 0 means the default 3; at most 20. Counted apart from the defect fix cap.

The checks before anything is written

GAOS reads the pull request again before the agent runs, and once more before any branch exists. Any of these blocks the card with the reason shown and closes the review fix:

ReasonWhy
review-pr-closedThe pull request closed or merged.
review-base-changedIts head is another branch now.
review-base-movedIts head is not the commit the reviewer read.
review-forkIt comes from a fork (always refused).
review-shared-branchIts branch is the default branch, the auto-fix base, an allowed retarget base, or protected.
review-branch-not-allowedIts branch no longer matches reviewFixHeads.
review-files-incompleteGitHub's file list was cut short.
review-workflowsIt changes .github/.
review-not-targetThe repository is no longer a fix target.
review-unassignedThe fixer was unassigned since.
review-outside-pathsThe agent edited a file the pull request does not change, or added a file outside their folders.

The fixer sees the review findings and the pull request's code as untrusted data, fenced, after its instructions. Every other auto-fix check still applies: the allowed and forbidden paths, the CI-secret check, the egress screen. When the draft opens, GAOS posts one line on the reviewed pull request: GAOS opened a draft fix: <url>.

What happens next

  • The reviewed pull request merges before the fix starts: the fix card is canceled. GAOS checks the merge with GitHub first.
  • The draft's base changes (GitHub retargets it when the reviewed branch is deleted): GAOS records it and closes the review fix; it closes nothing on GitHub. A person decides what to do with the draft.
  • The draft is closed unmerged: the review fix closes; no second attempt is planned.
  • GAOS's own review fix merging into the feature branch plans no unit-test card; the feature branch's own merge does.
  • A review fix is never retargeted.

Where a card came from

Cards planned from a GitHub event or the staging callback carry no source label. The two kinds of card that assignment does not gate say where they came from, so you can filter them on the board's Label select:

LabelThe card
source:apiCreated by an external-tasks API client (a review, unit tests, an e2e automation or run it asked for).
source:bundleThe test planner's card for a bundle of merged pull requests.

The planner sets them; an operator cannot. An API request for a card GitHub already planned adopts that card and adds no label to it. There is no backfill: only cards planned from v0.64.0 on carry a source label.

Set it up for a product

  1. Sign in to the back office with an account listed in GAOS_AUTOFIX_ADMINS.
  2. Open Agents, choose the product in the filter, open Edit assignments.
  3. Tick Juno · PR Reviewer, Kite · Unit Test Builder and a QA agent (Ember or Flint), then Save. The notice under the filter now says which roles do not run.
  4. For review fixes: also tick Mica · Defect Fixer, and in the product's auto-fix settings turn auto-fix on, list the target repositories, and set reviewFixHeads (for example feature/* and bugfix/*).
  5. Check the Board: the next opened pull request shows a review card, then a severity chip.

To undo it, open Edit assignments and press Stop gating.

The second release: e2e kinds, staging creates and merged specs

Built in v0.65.0, waiting on the QA tool

GAOS's half of parts 1–3 shipped in v0.65.0 (D-103, design docs/designs/release-b-e2e-kinds-merge-unit-tests.md). The QA tool's half follows in its own pull requests. Until the QA tool lists a capability, GAOS sends what it sends today, so nothing changes by itself. Unit tests (part 4) get a design of their own.

The second release finishes the e2e automation builder. In short: when a repository is deployed to staging, GAOS runs its automation of the repository's kind and, if the product asks for it, has the QA tool create what is missing; a person approves each new spec; the QA tool may let it merge by itself once its checks pass; GAOS then runs it.

How it works: the data flow

Three systems take part: your CI (it deploys to staging), GAOS (it plans cards and asks), and the QA tool (it writes and runs the specs). GitHub merges; GAOS never does. Each flow below reads left to right; the numbered list says who calls whom.

A. A staging deploy runs the automation, and creates what is missing.

1 · CIcalls GAOS's staging callback
→
2 · GAOSplans the run card (+ creates)
→
3 · QA toolruns the cases of the kind
→
4 · GAOScard Done or Failed
  1. The pipeline calls POST /api/v1/products/{id}/staging with the repository and commit (HTTP Basic, one credential per product).
  2. GAOS plans one run card, labelled with the repository's kind. If staging creates is on and this is a new commit, it also plans up to two create cards for planned cases with no automation yet.
  3. GAOS's QA runner asks the QA tool for a job per card (POST /api/v1/gaos/automation with kind, only when the QA tool lists that capability) and polls it.
  4. A run ends the card Done (the results are on the QA side and in the catalog) or Failed with its reason.

B. A new spec: created, approved, merged, then run.

1 · QA toolwrites the spec, runs it on staging
→
2 · Personapproves it in the QA tool
→
3 · QA toolpushes, opens the PR, arms auto-merge
→
4 · GitHubmerges when the checks pass
→
5 · GAOSruns that case once
  1. The create card's job generates the spec and repairs it against staging. The card waits in Needs you.
  2. A person approves the spec. Only an approval given in the QA tool can lead to an auto-merge; an answer from the GAOS Inbox opens the pull request for a person to merge.
  3. The QA tool pushes the commit (GAOS records it as the approved commit) and opens the pull request. If GAOS still allows it (GET /api/v1/products/{id}/spec-auto-merge: the product's auto-merge switch on, the Working or Complete band) and every repository check passes, it turns on GitHub's auto-merge pinned to that commit.
  4. GitHub merges when the required checks pass. Otherwise a person merges.
  5. GAOS's pull-request poller sees the merge. If the merged head is the approved commit and the QA catalog shows the case implemented, GAOS plans one run of that case. Any other head is noted on the Pull requests page and not run.

C. A pull request is opened, reviewed, and a low finding fixed.

1 · GitHubPR opened (via Brain Town)
→

→

→
4 · Micaa low finding: draft fix PR
  1. Brain Town forwards pr.opened for a repository the product lists.
  2. GAOS plans a review card when a PR reviewer is assigned (see Assignment).
  3. The review is posted on GitHub; medium and worse request changes, and the card gets a severity:* label.
  4. A low finding on an allowed branch becomes a draft pull request into the reviewed pull request's own branch (Low findings fixed by an agent).

1. A kind per repository

KindA staging run runsThe QA tool may create

Open the Agents page, pick the product, and open E2E repository kinds (admins only, the same accounts as auto-fix). Choose a kind for each repository and save. The staging run card of a repository with a kind carries e2e-kind:be or e2e-kind:fullstack: shown and filterable like every label, never settable by hand. Route Planner's acme/route-api is be; acme/route-web is fullstack. Saving kinds never touches assignment.

2. On a staging deploy: create what is missing

Tick On a staging deploy, ask the QA tool to create missing automation in the same editor. It is off by default, because it lets the staging credential start generation jobs. Then:

  1. The devops pipeline calls the staging callback, as today. GAOS plans the run of the repository's kind.
  2. On a new commit only, GAOS reads the product's QA catalog for planned cases with no automation at the kind's levels, and plans a create card for each: at most 2 per deploy (GAOS_E2E_CREATE_MAX) and 4 open per product (GAOS_E2E_CREATE_OPEN). The answer carries creates.
  3. A case is never created twice. Each of these blocks it: an open card creating it; its spec pull request open (30 days); merged but not yet implemented in the catalog (14 days); closed, or its create card failed (7 days).
  4. The QA tool writes the spec and waits for a person to approve it in the QA tool. The card ends Done when the spec pull request is open, and its reason says how it will merge.

3. The approved spec merges by itself, then runs

Tick Let the QA tool auto-merge a spec a person approved (off by default; it applies only in the Working or Complete readiness band). After a person approves a spec in the QA tool (an answer given in the GAOS Inbox leaves the pull request for a person), the QA tool asks GAOS (GET /api/v1/products/{id}/spec-auto-merge, QA token) and, when allowed, turns on GitHub's auto-merge pinned to the exact commit that was approved. It does so only when the automation repository has a ruleset that lets only the QA tool's account push qa-auto/* branches and a required check from a fixed source; otherwise it leaves the pull request for a person. GAOS never merges and holds no merge token.

When the spec pull request merges, GAOS plans one run of that case if the merged head is the approved commit, a qa agent is assigned, and the QA catalog shows the case implemented. If the catalog has not caught up yet, the row on the Pull requests page says waiting for the catalog and the run is planned when the result arrives (within 14 days). A merge at another commit is noted on the row and in the activity feed, and its case is not run.

4. Unit tests: decided, not built

Unit tests run through the QA tool in a sandbox it provides, a failure becoming a defect a person releases first. They need their own design and the QA tool's sandbox; until then the unit-test card behaves as Pull-request agents describes.
