Integrations

How integration works

GAOS plans and tracks the work; two external systems do the rest. ai-manager runs every model turn in the product's own workspace, and the QA tools run the test scripts and report back. Any other client — a mobile app, a chat bot — can ask the operator a question through the same machine API. This page shows each connection, who starts it, and how it is authenticated.

The picture

Read it left to right as the life of a piece of work: a client or the QA tools talk to GAOS's machine API; GAOS keeps the graph, the board and the operator's inbox; every model turn goes out through ai-manager, which runs a worker such as ai-claude-cli inside the product's provisioned workspace. GAOS never runs a model tool itself (D-055).

Every connection

Twelve connections, and only twelve. Every credential is a file on the host, mode 600, named by an environment variable; none is ever in the repository, a log line or a page. The pull-request flow and the platforms bound to a product are switched on per product; with none configured, the first seven are all there is.

Three GAOS tokens, never equal

GAOS's own API has three tokens: admin (seeding and catalog import, by an operator), QA (the QA tools calling GAOS) and outbound (GAOS calling the QA tools). If two of them are equal GAOS disables its whole API at boot and logs disabled (two of the admin, QA and outbound tokens are equal): the QA tools holding admin rights, or replaying GAOS's own credential back at it, is the failure this refuses. A registered client's token must differ from all three and from every other client's. A token is gaos_ followed by 32 or more letters and digits; GAOS keeps only its SHA-256 digest.

A question round trip

A client asks the operator something; the operator answers in the back office; the answer goes back. The QA tools are told by webhook, any other client polls. The first answer wins, from wherever it came.

text
client                     GAOS                                  operator (back office)
  │ POST /api/v1/products/p-1/inbox  {externalId, question, options}
  │──────────────────────────▶│ ExternalQuestionAsked
  │◀──── 201 {status: open} ──│ ──── "Needs you" shows the item ───▶│
  │                           │                                      │ picks an option
  │                           │◀──────────── answer ─────────────────│
  │                           │ ExternalQuestionAnswered (source: gaos, back-office)
  │                           │
  │  (QA tools only)          │ worker, within 10 s:
  │◀─ POST {GAOS_QA_URL}/api/v1/gaos/inbox-answer  {externalId, status, choice, …}
  │── 2xx ───────────────────▶│ ExternalAnswerDelivery: delivered
  │   (else: retry after 30 s, 2 min, 10 min, 1 h; gave-up after 5 attempts)
  │
  │  (any client, any time)
  │ GET /api/v1/products/p-1/inbox/{externalId}
  │◀──── 200 {status: answered, choice, optionLabel, source} ──

A client may also answer its own item (POST …/inbox/{externalId}/answer); the answer records its source — kind, client, origin and the actor the client reported (BR-57). The details are in Webhooks and external clients and the QA sync API.

A results push

The QA tools own the automation facts of a test case — implemented, spec, result, run time — and GAOS owns the plan. A run's results reach GAOS one of two ways, and both end in the same store operation.

text
CI run ends ──▶ QA tools ── POST /api/v1/products/p-1/qa/results  {items[≤200]} ──▶ GAOS
                                 ◀── 200 {applied, unchanged, rejected[]} ──
                GAOS: automation facts applied; the epic card's badge moves; no task moves

operator presses "Pull results" on the QA tab
                GAOS ── GET {GAOS_QA_URL}/api/v1/gaos/results?product=…&after=… ──▶ QA tools
                     ◀── 200 {items, next, more}  (up to 20 pages, 60 s) ──
                GAOS: each page applied exactly like a push

A result never moves a card (OQ-35); the badge on the epic's card is a live view of the catalog. Push catalog is the reverse direction: GAOS sends the planning fields to POST /api/v1/gaos/catalog.

A model turn

When the board (or the scheduler, under GAOS_RUNNER=on) dispatches a task, GAOS freezes the task's context, screens it for secrets, and sends one turn:

text
GAOS ── POST /v1/chat  X-Request-ID: gaos.<tenant>.<run>  {prompt, workspace_id | session_id, …} ──▶ ai-manager
     ◀── 202 ──
GAOS ── GET /v1/requests/<id>/result  every 2 s, up to 660 s ──▶
     ◀── 202 (running) … 200 {text, session_id, cost_usd, question?} ──
GAOS: the reply's handoff block is extracted; the card moves; a question goes to "Needs you"

Before a product's first turn, a Blueprint sync provisions its workspace through POST /admin/workspaces/provision. Every call is listed, with its statuses and its caller, in the ai-manager REST reference.

A task from an outside platform

A client with the tasks capability plans work without signing in (D-099). GAOS checks the body, the product and the pull request, makes one card, and says who will start it; the client polls by its own id.

text
client ── POST /api/v1/products/p-1/tasks  {kind, externalId, pr}  ──▶ GAOS
                                  GAOS: client scope → tasks capability → product → body
                                        the product follows the repository? the runner is not off?
                                        the same externalId again → 200, the same card (no second card)
                                        GitHub: the pull request is open (review) or merged (unit test)
       ◀── 201 {taskId, status, column, labels, dispatch} ──
           dispatch: scheduler | auto | operator | manual-review | qa-tool
client ── GET /api/v1/products/p-1/tasks?externalId=… ──▶ GAOS
       ◀── 200 {status, column, reason, updatedAt} ──   (until DONE, FAILED or CANCELED)

A manual review is never dispatched: GAOS announces it to the WhatsApp group, naming the client. An e2e kind is worked by the QA tool, and automation-run can be cancelled by the client that started it.

A defect to a draft pull request

The QA tool reports a defect; two agents judge and fix it; GAOS alone writes to GitHub, with its own write token (Defect auto-fix).

GAOS ── turn ──▶ ai-manager: Defect Triager → easy | medium | complex   (DefectTriaged)
GAOS ── turn ──▶ ai-manager: Defect Fixer → edits + a test             (easy, switch on, cap left)

A bundle to a test plan

For a product in GAOS_PR_TEMPLATE_PRODUCTS, the PR template ties pull requests in several repositories into one bundle, and one test plan is made when all of them are finished (D-100).

text
GitHub PR body ──▶ GAOS poller: the code, the cross-repo links, the QA notes
                   bundle key  taskmgr:<code>   or   pr:<owner/repo#n> of the linker
                   no code, no source → one comment + one WhatsApp line (missing code)
                   bound to TaskMgr → GetTask(<code>); unknown → one comment + one line
every member merged or closed, one merged, 10 min quiet
                   GAOS: one Test plan card (role test-planner) → a model turn proposes cases
                   GAOS ── POST /api/v1/gaos/case-proposals ──▶ QA tools: draft cases, links to the PR URLs
                   the card ends DONE  (each member's review card moved to DONE on its own merge, rule pr-merged)
                   bound to TaskMgr → bundle:planned to the task's QA; one note on the task

A notice

A review finding of medium or worse, a held review, a failed run, a manual or needs-manual review label (D-101), a missing or unknown task code and a ready test plan each send one WhatsApp line with the card’s id — never code and never the findings.

text
event on a card ──▶ notifier: the login (the PR author, or the last committer)
   GAOS contact for the login?         yes → that contact, if its filter wants the kind; else the group
   no contact, product bound to TaskMgr → the TaskMgr person with that checked login (alias tm:<user>)
   nobody                              → the pinned group
   ContactNotified {alias, kind, outcome}   (never the number, never the text)

TaskMgr, a bound platform

One product per instance can be bound to TaskMgr, the team’s task manager (D-104). GAOS reads people and tasks over gRPC with TLS and writes one note per finished bundle; the people stay in memory (BR-63).

TaskMgrpeople, tasks
⇄
GAOSdirectory, validation, notifier
→
WhatsAppa person or the group

ListUsers fills the directory every fifteen minutes; GetTask checks a pull request’s code and, again, a finished test plan’s task; AddComment writes the note. A refused credential or an outage opens a circuit breaker, and every use falls back to the contact, the group and no validation. The whole path is on the TaskMgr page.
