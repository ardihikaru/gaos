Integrations

How integration works

GAOS plans and tracks the work; two external systems do the rest. ai-manager runs every model turn in the product's own workspace, and the QA tools run the test scripts and report back. Any other client — a mobile app, a chat bot — can ask the operator a question through the same machine API. This page shows each connection, who starts it, and how it is authenticated.

The picture

Read it left to right as the life of a piece of work: a client or the QA tools talk to GAOS's machine API; GAOS keeps the graph, the board and the operator's inbox; every model turn goes out through ai-manager, which runs a worker such as ai-claude-cli inside the product's provisioned workspace. GAOS never runs a model tool itself (D-055).

Three GAOS tokens, never equal

GAOS's own API has three tokens: admin (seeding and catalog import, by an operator), QA (the QA tools calling GAOS) and outbound (GAOS calling the QA tools). If two of them are equal GAOS disables its whole API at boot and logs disabled (two of the admin, QA and outbound tokens are equal): the QA tools holding admin rights, or replaying GAOS's own credential back at it, is the failure this refuses. A registered client's token must differ from all three and from every other client's. A token is gaos_ followed by 32 or more letters and digits; GAOS keeps only its SHA-256 digest.

A question round trip

A client asks the operator something; the operator answers in the back office; the answer goes back. The QA tools are told by webhook, any other client polls. The first answer wins, from wherever it came.

text
client                     GAOS                                  operator (back office)
  │ POST /api/v1/products/p-1/inbox  {externalId, question, options}
  │──────────────────────────▶│ ExternalQuestionAsked
  │◀──── 201 {status: open} ──│ ──── "Needs you" shows the item ───▶│
  │                           │                                      │ picks an option
  │                           │◀──────────── answer ─────────────────│
  │                           │ ExternalQuestionAnswered (source: gaos, back-office)
  │                           │
  │  (QA tools only)          │ worker, within 10 s:
  │◀─ POST {GAOS_QA_URL}/api/v1/gaos/inbox-answer  {externalId, status, choice, …}
  │── 2xx ───────────────────▶│ ExternalAnswerDelivery: delivered
  │   (else: retry after 30 s, 2 min, 10 min, 1 h; gave-up after 5 attempts)
  │
  │  (any client, any time)
  │ GET /api/v1/products/p-1/inbox/{externalId}
  │◀──── 200 {status: answered, choice, optionLabel, source} ──

A client may also answer its own item (POST …/inbox/{externalId}/answer); the answer records its source — kind, client, origin and the actor the client reported (BR-57). The details are in Webhooks and external clients and the QA sync API.

A results push

The QA tools own the automation facts of a test case — implemented, spec, result, run time — and GAOS owns the plan. A run's results reach GAOS one of two ways, and both end in the same store operation.

text
CI run ends ──▶ QA tools ── POST /api/v1/products/p-1/qa/results  {items[≤200]} ──▶ GAOS
                                 ◀── 200 {applied, unchanged, rejected[]} ──
                GAOS: automation facts applied; the epic card's badge moves; no task moves

operator presses "Pull results" on the QA tab
                GAOS ── GET {GAOS_QA_URL}/api/v1/gaos/results?product=…&after=… ──▶ QA tools
                     ◀── 200 {items, next, more}  (up to 20 pages, 60 s) ──
                GAOS: each page applied exactly like a push

A result never moves a card (OQ-35); the badge on the epic's card is a live view of the catalog. Push catalog is the reverse direction: GAOS sends the planning fields to POST /api/v1/gaos/catalog.

A model turn

When the board (or the scheduler, under GAOS_RUNNER=on) dispatches a task, GAOS freezes the task's context, screens it for secrets, and sends one turn:

text
GAOS ── POST /v1/chat  X-Request-ID: gaos.<tenant>.<run>  {prompt, workspace_id | session_id, …} ──▶ ai-manager
     ◀── 202 ──
GAOS ── GET /v1/requests/<id>/result  every 2 s, up to 660 s ──▶
     ◀── 202 (running) … 200 {text, session_id, cost_usd, question?} ──
GAOS: the reply's handoff block is extracted; the card moves; a question goes to "Needs you"

Before a product's first turn, a Blueprint sync provisions its workspace through POST /admin/workspaces/provision. Every call is listed, with its statuses and its caller, in the ai-manager REST reference.
