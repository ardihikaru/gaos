Integrations

Pull requests

GAOS touches pull requests in three ways: it opens a draft fix for an easy defect, it reviews the ones Brain Town reports, and the QA tool opens one on the automation repository after a person approves a generated spec. The Pull requests page in the back office lists all of them, per product, with their state, their branch and base, the task each belongs to and, for the QA tool, a link to the job. It reads; it never merges, marks ready or closes anything (D-092).

Where each kind comes from

KindSourceIts task
Auto-fixThe draft pull request GAOS opened for a defect (the fix record, Defect auto-fix).The fix card.
ReviewA pull request Brain Town reported on a repository the product follows (Pull-request agents). A row is written when GAOS plans the cards, and once at the first start for pull requests already open.The reviewer card.
QA toolThe pull request a QA job opened, reported by the QA tool in the job’s status. Only a repository listed in the product’s automationRepos makes a row.The e2e card.

The page

  • Per product, newest first, at most 200 rows. Tabs: Open (open and draft), Merged, Closed, All. Filters: product and kind.
  • A row shows the pull request (a link to GitHub), its kind and state, the title, branch → base (“unknown” until GAOS has read it), the task (a button that opens the task’s detail sheet, with its status), the defect or the QA case and, when the QA tool sent a link on its own host, a link to the job, and the age.
  • The drawer adds the related tasks, the branch and base, and the pull requests it replaced or was replaced by. It makes no GitHub call.
  • Kept fresh by the poller, not by the page: every 5 minutes for the first 7 days, hourly after, up to 90 days for a review or QA row. A row says “not followed since” once it is no longer read, and “no longer followed” when the product stopped following the repository. The page itself refreshes every 30 seconds without touching GitHub.
  • A GitHub failure shows a banner and leaves the rows as they were.

For a product listed in GAOS_PR_TEMPLATE_PRODUCTS, a row also shows the bundle it belongs to and, when GAOS sent the missing-code alert, the chip no task code (Bundles from the PR template). A member of a bundle that is not planned yet is kept past the 30-day prune. When the product is bound to TaskMgr, the code is also checked against TaskMgr’s tasks, and a code TaskMgr does not know records the alert unknown-task-code (TaskMgr).

The settings

Both are fields of POST /products/{id}/autofix, for the accounts on the auto-fix admin list. The post replaces the whole configuration, so a field left out is cleared.

FieldMeaning
automationReposThe repositories (owner/repo, at most 4) where the QA tool opens its pull requests. They are deliberately not the product’s own repositories: a repository there would put the QA tool’s generated pull requests into the review flow.
allowedBasesThe branches (at most 8) a fix pull request may later be moved to. Empty means none.

Every change of these is recorded in the AutoFixConfigured event with the account’s alias.

Change the base branch

For a draft GAOS opened, the drawer has a Retarget block for the accounts on the auto-fix admin list. GAOS does not edit the pull request. It raises the defect’s generation and plans a related fix task against the chosen base; the AI redoes the fix on that base’s code and a new draft pull request opens against it.

What happensDetail
Choosing a baseOnly the product’s allowedBases, minus the current base; the route checks that the branch exists on GitHub, once, when you press the button.
The taskAn ordinary fix task of the next generation, titled “(retarget to …)”, with the account, the rule and the reason in its event. It spends the product’s daily fix cap and waits its turn like any fix.
The AIIt gets the source of the new base and the previous fix as untrusted data, and the usual limits apply (three files, 40 and 120 lines, allowed paths, the CI check against the new base).
The resultA new draft pull request on a branch ending in the generation, linked both ways, with a comment on each; one WhatsApp line marked retarget.
The old pull requestLeft open for a person to close. Closing or merging it never moves the defect after the new one exists; a merge while the retarget is still pending lands the fix and blocks the retarget task.
LimitsAt most three retargets of a defect; one at a time; a base removed from allowedBases is refused from then on, even for a task someone unblocks.

When the button is off, the drawer says why and how to turn it on (not an admin, not a GAOS branch, closed, base not yet known, already retargeted, a task already working, three retargets, no other allowed base).

What it never does

  • Merge, mark ready, approve or close a pull request, or change the base of one it already opened: a retarget opens a new draft instead.
  • Read a repository the product does not follow, or build a link from a URL someone else supplied: GitHub links come from the validated owner, repository and number, and the QA link only from the one host GAOS is configured to trust.
  • Show GitHub’s text as markup: titles, authors and branch names are plain text, and a title that matches a secret detector is withheld.
