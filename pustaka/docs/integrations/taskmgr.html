TaskMgr

TaskMgr is the team’s task manager. It already knows each task’s product, status and QA, and each person’s role, WhatsApp number and checked GitHub login. GAOS can bind one product to it as a third-party platform. That product’s pull-request codes are then checked against real tasks, its notices reach people GAOS has no contact for, and a finished test plan is reported back on the task (D-104).

The binding

On the back office’s Integrations view, an auto-fix admin (the accounts in GAOS_AUTOFIX_ADMINS) picks a product, types its TaskMgr product code and ticks enabled. The form posts POST /products/{id}/third-party.

  • A product has at most one binding per kind; the only kind is taskmgr.
  • An instance binds one product per kind. Binding a second answers 409 and names the product that holds it.
  • Disabling keeps the entry with enabled off; nothing is deleted.
  • Every change is a ThirdPartyConfigured event: the alias, the kind, the switch and the code.
  • The binding is stored on the product (thirdParty), like auto-fix, so it needs no schema change.

The link is ready only when the settings below are usable, the circuit breaker is closed, the binding is enabled, and the product is in GAOS_PR_TEMPLATE_PRODUCTS — without that, GAOS reads no code at all. A bound product missing from that list shows Degraded.

The settings

VariableRule
GAOS_TASKMGR_GRPC_ADDRTaskMgr’s gRPC address, ip:port, an IP literal. A hostname is refused. Empty means off.
GAOS_TASKMGR_CA_FILEThe PEM certificate TaskMgr serves, pinned as the only root; the server name checked is the IP. Required unless the address is loopback. Prod: deploy/stacks/prod.pr-taskmgr-ca.pem, mounted at /run/secrets/pr-taskmgr-ca.pem.
GAOS_TASKMGR_AUTH_FILEA regular file with no group or other permission bits, one line username:password. Empty means off. Prod: deploy/stacks/prod.pr-taskmgr-auth, mounted at /run/secrets/pr-taskmgr-auth.

Both files match the prod.pr-* class, so the existing guards cover them: they are gitignored, check-stacks.sh fails if one is tracked, and a prod deploy refuses to start while one is missing.

TLS and the pinned certificate

The VPN between the VMs runs through a hub that decrypts WireGuard and encrypts it again. Plaintext gRPC would show the hub every credential and every phone number. So GAOS speaks gRPC over TLS 1.3 to the certificate in GAOS_TASKMGR_CA_FILE, and dials only the configured IP; the hub relays ciphertext.

bash
# on the GAOS host: copy TaskMgr's public certificate (never its key)
install -m 600 grpc.crt deploy/stacks/prod.pr-taskmgr-ca.pem
# the address, in the instance's env file
GAOS_TASKMGR_GRPC_ADDR=<taskmgr-addr>

TaskMgr’s certificate is self-signed and valid for three years. To renew it, replace the file on both sides and restart GAOS.

The TaskMgr account

GAOS signs in as a TaskMgr rest-client that holds the gRPC integration grant, never gRPC access (the admin grant). The integration grant allows three methods — ListUsers, GetTask, AddComment — only on the client’s TaskMgr products. It has no REST access and a comment rate limit. Create it with full access off, product access to the bound product only, and a one-year expiry.

Never use the admin grant

A rest-client with gRPC access acts as a TaskMgr admin: it can reset passwords and change any task. A GAOS secret holding it would be a full TaskMgr admin credential.

The people directory

GAOS keeps, in memory only, the active TaskMgr people the account may see: by id, and by lower-case GitHub login for checked logins. A login two checked people share is dropped and counted as a conflict. A number is usable when TaskMgr marks it active and it has 7 to 15 digits; it is sent as <digits>@s.whatsapp.net.

  • A failed refresh keeps the previous directory, shown as stale since a time.
  • Disabling the binding empties it; nothing is fetched while no binding is enabled.
  • A number is never stored, logged, put in a packet, sent to Brain Town or written into an event (BR-63). The one stored identifier is the alias tm:<username> in ContactNotified.
  • Everyone sees the counts — people, GitHub-linked, usable numbers, login conflicts. Only an auto-fix admin sees the table of name, role, GitHub login and masked number.

The note on the task

text
GAOS: the pull requests of this task are finished: 2 merged, 1 closed without merging.
https://github.com/example/app/pull/41
https://github.com/example/api/pull/17
Test plan: 3 draft case(s) created, 1 linked, 0 refused: TC-DEMO-001, TC-DEMO-002, TC-DEMO-003, TC-DEMO-010.
[gaos bundle taskmgr:DEMO-FEATURE-00042 · card t-512]

It is written only after a fresh lookup confirms the task belongs to the bound product, and only for a taskmgr: bundle. At most ten pull-request links are listed, case codes must look like case codes, and the text stays within TaskMgr’s 1500 characters with the marker line kept. A failure is logged and never retried; it never fails the card.

When TaskMgr is down

  • A refused credential (or TaskMgr’s lockout) stops every call until the credential file changes or an hour passes. The block shows Unusable: TaskMgr refused the credential.
  • Three unavailable answers in a row stop calls for one minute, doubling to thirty. The block shows Degraded.
  • While calls are stopped, nothing is checked, no notice uses TaskMgr, and every use falls back to the behaviour before TaskMgr: the contact or the group, no validation, no note.
  • A lookup on the poll path waits at most three seconds, so a slow TaskMgr never stalls the pull-request poll.

Troubleshooting

You seeWhy, and what to do
OffNo address, an empty credential file, or no enabled binding. Set all three.
Unusable at bootA hostname instead of an IP, no certificate for a non-loopback address, or an auth file readable by others (chmod 600).
Unusable: refused the credentialThe rest-client is wrong, expired or lacks the integration grant. Fix it in TaskMgr, rewrite the file; the change of file is enough to retry.
Degraded: not in the template listAdd the product to GAOS_PR_TEMPLATE_PRODUCTS and redeploy.
A notice still goes to the groupThe author has a GAOS contact (it wins), the TaskMgr login is not checked, or the number is inactive.
A valid code is called unknownThe case differs (TaskMgr ids are matched exactly), or the task belongs to another TaskMgr product, or the account lacks access to that product.
409 on the bindingAnother product holds the TaskMgr binding. Disable it there first.
