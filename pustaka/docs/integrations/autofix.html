Integrations

Defect auto-fix

The QA tool pins a known defect as an expected failure, so a defect used to be invisible to GAOS and equally queued whether it was a one-line validation or a billing problem. Now the QA tool reports it, GAOS classifies it from the product's own policy, and a defect that is easy to fix ends as a draft pull request that a person reviews. It is narrow on purpose: a backend-only defect, three kinds of fix, a few files, an explicit switch per product, and daily caps (D-091).

What auto-fix does

StepWhat happensWho
1The QA tool reports a defect of a case: a pinned expected failure, an unexpected failure, or a pinned failure that now passes.QA tool
2GAOS records it (DefectReported) and plans a triage card labelled defect:triage.GAOS
3The Defect Triager reads the product's defect-triage policy, the facts and the source files GAOS found, and answers easy, medium or complex.Agent
4GAOS re-checks the verdict, records it (DefectTriaged) and plans a fix card born with its label defect:easy, defect:medium or defect:complex.GAOS
5Easy, backend-only, switch on, cap left: the fix card is dispatched with no operator move. Otherwise it waits in READY, or is born BLOCKED (a complex defect also sends a notice).GAOS
6The Defect Fixer answers with edits and tests, never whole files.Agent
7GAOS applies the edits, enforces the caps, creates a branch and a draft pull request through the GitHub API, labels it and posts the before and after as a comment.GAOS
8GAOS sends one WhatsApp line with the link; the fix card ends DONE.GAOS
9GAOS follows the pull request (draft, ready, merged, closed) and shows it in the Auto-fix view.GAOS

What easy means

The policy is a product's own, written in its Blueprint under the key defect-triage. The shape GAOS ships is neutral:

VerdictMeaning
EasyA fix a reviewer can judge from the diff alone, in one resolver or route, with a unit test: a missing or wrong validation (a date format, a length the contract does not enforce, an inverted check), a formatting problem in input parameters, or a minimum or maximum check (a negative or zero amount accepted).
MediumA business rule or a state guard inside one service that needs a person's judgement: a duplicate accepted, a status that should block an action, a missing nil guard.
ComplexAuthentication, authorisation or anonymous access; billing, price or stock; a schema or migration; more than one service or repository; anything whose expected behaviour is a business decision.

An easy fix never edits generated code, a schema, a migration, a dependency file, CI, authentication or anything that prices or stocks, never changes more than three files, and never lacks a unit test.

GAOS checks the verdict

An easy verdict is accepted only if its class is validation, format or min-value, the repository is one the product owns, and every file is one GAOS put in the packet and the product's allowed paths admit. Otherwise it is downgraded to medium and the reason is recorded. The deterministic gate is the path set, not the class. A defect in acme-org/sample-service reported as DEF-101 that fails this check simply waits for a person.

The settings

A fine-grained token with Contents, Pull requests and Issues read and write on the application repositories only is recommended. In production the two files are deploy/stacks/prod.pr-github-write-token and prod.pr-autofix-admins. They are gitignored and must exist before up; an empty one leaves auto-fix off.

FieldRule
caseIdA case of the product's catalog.
kindxfail, fail or xpass.
defectIdDEF- and 1 to 6 digits; required for xfail and xpass.
automationType, backend, levelbe or e2e; graphql, rest or empty; API, GQL, WEB or E2E.
targetReposowner/repo, at most 8. GAOS keeps only repositories the product owns.
operationsAt most 5 names, used only as search terms; they never widen what a fix may touch.
spec, title, excerptA valid spec path; at most 200 characters; at most 4 KiB.
RequestAt most 256 KiB (413 too-large) and 50 items; an unknown field is 400; at most 50 new defect keys per product per UTC day.

The answer is 200 {"applied":n,"unchanged":n,"rejected":[{caseId,reason}]}: a bad item is rejected with a reason and the rest apply. A repeat updates the last-seen time and plans nothing; an xpass marks the defect fixed and cancels its open cards; a fail after a fix is a regression, whose fix card is born BLOCKED and is never fixed automatically. Everything in an item is untrusted: its text is stripped of backticks, angle brackets and line breaks, screened for secrets, reaches an agent only as data and appears in no event, card title or log line.

The caps

CapValue
Files in a fix3, at least one of them a test
Changed lines (added plus removed)40 outside tests, 120 in tests
Automatic dispatchesThe fix and triage caps above, per product per UTC day. They count dispatches, not pull requests, and are the only spend bound for these cards.
Branchgaos/fix-<slug>, never moved or overwritten
Pull requestDraft only; never ready, approved or merged by GAOS

A failing cap does not retry: the card is blocked with its reason and the verdict is kept.

The Auto-fix view

The back office's Auto-fix view lists every product's drafts. Its tiles count open drafts, ready for review, merged in seven days, defects awaiting triage, cards waiting for a person and today's automatic dispatches. The table has a state chip, the defect, its difficulty, the pull request's link and age, and whether WhatsApp was told; filters for product, state and difficulty live in the URL; a detail drawer shows the before and after, the changed files and the timeline. It refreshes every 30 seconds, says why auto-fix is off for a product, announces an unreachable GitHub, and shows the kind of write token in use. It never shows a token or a failure excerpt.

Since v0.71.0 (D-108) the view has three sections — Fix pull requests (the default, and always when a drawer is open), Cards waiting (five a page) and Auto-fix by product — with the product and difficulty filters above them. Each pull request shows its branch and base, and what triggered it: a QA report, a review finding, a unit-test failure, a retarget of an earlier pull request or a second attempt after one was closed, linked to the earlier record in the drawer.

Duplicates

Above the table, a Duplicates panel lists open fix pull requests that should be closed: one a retarget replaced (Superseded), and extra open ones of the same defect (Same defect; the one the defect waits on is kept). An auto-fix admin closes one with Close … on GitHub, after a confirmation. GAOS reads the pull request first (one already closed or merged is recorded as it is), closes it, keeps its branch and records the close; the defect is not changed. A retarget closes the pull request it replaced by itself, so a superseded finding appears only when that close failed.

What GAOS never does

  • Marks a pull request ready, approves it or merges it, or pushes to a default branch. It closes only its own gaos/fix- drafts that a retarget replaced or an admin closed as a duplicate (D-108).
  • Lets the agent hold the write token or open the pull request.
  • Fixes a medium, complex, regression or end-to-end defect automatically, or opens a pull request from a card that fails the record-based check, however it was dispatched or relabelled.
  • Starts a fix under GAOS_RUNNER=on when a product's switch is off: the scheduler never dispatches a defect card in any mode.
  • Runs the tests. The “after” in the pull request is the agent's report, and the body says so (OQ-39).
  • Puts a defect's text in an event, a card title or the WhatsApp line.

Private source files GAOS fetches for the packet go to the model provider, as D-091 records; a secret detector hit refuses the dispatch.

Operating notes (learned on the first live run)

  • Globs. * matches one path segment and ** any number of them. *.go matches only a file in the repository's root; a fix under pkg/graph/… needs pkg/graph/**/*.go. A verdict naming a file outside allowedGlobs is downgraded to medium (autofix-files-outside-globs), so a too-narrow glob looks like a triager that never says easy. Test globs likewise: **/*_test.go.
  • The triager's source slice. Search hits come from the QA tool's operation names, the defect's own operation first. Up to twelve files are read and at most six kept (64 KiB): hand-written Go source before tests before everything else, a file that defines a function named for an operation before one that only mentions it, and a file that holds a secret-shaped string is left out. If the verdict says the implementing code is not in its packet, look at the operations the QA tool sent.
  • CI. Forbid, in forbiddenGlobs, the directories that trigger a workflow which uses a secret, and say so in ciConfirmed. GAOS applies a workflow's paths filter to the files the fix changes; a workflow with no filter, a negated pattern or an unreadable file still blocks.
  • The pull-request body. The repository's own template is not fetched. Put it in prTemplate with the slots; GAOS keeps every section and fills the ones it knows. Without one the neutral English body is used.
  • One page for every pull request. The fix pull requests also appear on the Pull requests page, next to the ones GAOS reviews and the ones the QA tool opens.
  • Refusals are logged. A ready card that is not dispatched is logged once per card and reason (autofix: … is ready but not dispatched: …): a cap, a live turn on the product (one at a time), the egress pass, the Blueprint drift gate.
  • The pull request is a draft, always. The “after” in its body and comment is the agent's prediction. Read the added test: an agent may write a test that restates the condition instead of calling the code.
