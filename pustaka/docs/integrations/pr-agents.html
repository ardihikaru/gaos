Integrations

Pull-request agents

A product's main repository receives pull requests, and somebody has to review them and prove they still work. With the Brain Town reader on, GAOS opens the cards for that work when a pull request opens, when it merges and when the staging deploy finishes. Two of the four are agents; two are jobs GAOS hands to the QA tool.

What opens what

TriggerGAOS opensWorked by
A pull request opens (not a draft, not from a fork)A PR review cardThe pr-reviewer agent
The same eventAn e2e automation cardThe QA tool (a job GAOS starts and polls)
A pull request mergesA unit-test card; a review or e2e card that has not started is canceledThe unit-test agent
The staging deploy finishesAn e2e run cardThe QA tool

The cards live on a separate PR workflow of the product, so a pull request never resets the product's own plan. A replay plans nothing: the card carries its key, owner/repo#n:role, and a second event with the same key is a no-op. A draft, a pull request from a fork and one from an author who is not an owner, member or collaborator open nothing; GAOS_PR_MAX_OPEN (default 5) bounds the open cards of a product; GAOS_PR_ALLOW_FORKS=1 admits forks.

Which agents a product has

On the Agents page an admin (an account in GAOS_AUTOFIX_ADMINS) assigns agents to a product, and one agent can serve several products. The page filters by product. A product whose assignments were never saved runs every flow above, as before. Once they are saved, a flow runs only when an agent of its role is assigned: no pr-reviewer, no review card; no qa, and the staging callback answers 422 unassigned. Saving also turns on changes requested for medium and worse findings (below). Reset returns the product to “not configured”. Assignment switches a role on; it does not choose which agent runs a card (D-102). The details, the severity board and the runbook are on Agents, severity and review fixes.

The labels

A card carries at most one label per family, and the vocabulary is closed: another word is refused with 422. An operator changes a label on the board, and the change is a TaskLabeled event naming the account's alias.

The review

The pull request's title, description and diff are untrusted text and reach the agent as data in the packet, behind the egress pass: a secret in the diff refuses the dispatch, and the card waits for a person. The reviewer's instructions are Blueprint content, never a file from the pull request.

The agent ends its reply with one block, and GAOS, not the agent, posts it. The GitHub token is in the dashboard process and nowhere else.

```gaos-pr-review
severity: none | low | medium | high | critical
body: the review, at most 6000 characters, each finding with a file:line and a Reason:
```

The body is screened by the egress detectors before it is posted; a body that carries a secret is not posted and the card goes to a person. It is posted as a comment, never an approval — except on a product whose assignments are configured, where a medium, high or critical finding asks for changes. GAOS reviews a pull request once and never dismisses its review, so that body ends with a line asking a maintainer to dismiss it once the points are addressed. When the author is the review account itself, or either login is unknown, GAOS comments instead. The review posts under the account of GAOS_GITHUB_TOKEN_FILE; a bot account's token is recommended for a product that turns this on. GitHub's answers map to a reason on the card: github-token (401, 403, 404: the token may not write there), github-refused (422), github-rate, github-error.

They are gitignored and must exist before up; an empty one leaves that part off.

The pull requests GAOS opens itself for an easy defect are a separate flow with its own write token: see Defect auto-fix.

A low finding fixed by an agent

A low finding can become a review fix: the fixer agent edits the files the pull request already changes, and GAOS opens a draft pull request into the reviewed pull request’s own branch, on top of the commit the reviewer read. The fix follows the source’s root branch: a branch cut from staging gets its fix in that branch, and the fix reaches staging when the branch merges. GAOS posts one line on the reviewed pull request linking the draft.

It happens only when a fixer is assigned to the product, auto-fix is on, the branch matches one of the auto-fix setting reviewFixHeads (patterns such as feature/*; * alone is refused), the repository is an auto-fix target, and the day’s reviewFixCap (default 3) is not reached. Before the agent runs, and again before any branch exists, GAOS refuses the fix when the pull request closed, its head moved, it comes from a fork, its branch is the default, the auto-fix base, an allowed retarget base or a protected branch, its file list is incomplete, it changes .github/, or the fixer was unassigned. A refused card is Blocked with the reason. GAOS never merges and never closes a pull request; a review fix is never retargeted.

The staging callback

Jenkins calls GAOS when the staging deploy has finished:

POST /api/v1/products/{id}/staging
Authorization: Basic base64(user:password)
Content-Type: application/json

{"repo":"acme-org/sample-service","branch":"staging","commit":"0123456789abcdef","environment":"staging"}
AnswerWhen
202 {"accepted":true,"taskId":…}The e2e run card was planned.
200 {"duplicate":true,…}The same commit again: nothing new was planned.
401 with WWW-Authenticate: Basic realm="gaos"No credential, or a wrong one.
404A credential that belongs to another product, or a product that does not exist.
422The repository is not one of the product's, the commit is not a full 40- or 64-character hex sha, or the environment is not staging.
429 with Retry-AfterFive failed attempts from one source lock it for five minutes.
409The product already holds its cap of open PR cards.
503The callback is not configured.

This is the one machine route that answers HTTP Basic instead of a bearer token, because a Jenkins credential step speaks Basic. The credential is per product and is compared in constant time.

The QA tool does the e2e work

The QA tool already writes, runs, repairs and pushes an automation spec in its own automation repository. GAOS does not repeat that with a model: a job runner calls POST /api/v1/gaos/automation with {product, caseCode, mode}, polls GET /api/v1/gaos/jobs/{id} every 15 seconds for up to 40 minutes, and closes the card from the job's own status. A new automation names its case with a line QA-case: <code> in the pull request description; without one the card waits, blocked, for a person. A staging run asks for every automated case.

When the job's status is awaiting_approval, a person must approve the spec in the QA tool. That is a human wait: the card moves to Needs you with a reason carrying qa-job:<id>, and the 40-minute work clock stops. The wait budget is cumulative per job (GAOS_QA_APPROVAL_WAIT_HOURS, 24 hours by default, at most 720); past it the card fails with qa-approval-timeout, after the last poll has been read, so an approval given in the final interval is seen. One notice of kind e2e:approval is sent per job, always to the pinned group and never to a committer. More than five waits fail the card with qa-job-flapping. After a restart GAOS re-adopts a running or waiting e2e card from the job id in its reason and starts no second job. Whenever GAOS gives up on a job (the work timeout, the approval timeout, the flapping cap) or an operator cancels the card, it cancels the job at the QA tool (POST /api/v1/gaos/jobs/{id}/cancel), which stops the run and rejects the open approval, so nothing can be approved later and no pull request opens. It is best effort: a failed cancel is logged and never keeps the card open. The case in flight inside a run-all is not interrupted. A card id carries 12 characters of the commit; an id already held by a card with another key gets a suffix.

The two routes live in the QA tool

They are a change in the QA tool's repository, not in GAOS. Until they exist the e2e card fails with qa-routes-missing, which is visible and harmless (OQ-38).

WhatsApp and the contacts

A review finding of medium or worse, a held review, a failed test or e2e run, and a card a person must review — an operator’s pr-review:manual or pr-review:needs-manual (D-101) — send one line and the card's id. A client that asks the API for a manual review is announced to the group, naming the client. The findings stay on the card; no code is pasted into a chat. The line goes to the contact of the pull request's author (a review) or of the last committer (a failure). When that login has no contact at all and the product is bound to TaskMgr, it goes to the TaskMgr person with that checked GitHub login (D-104); otherwise, and always for a contact whose filter refuses the kind, to the pinned group. e2e:approval and the bundle kinds keep the group; bundle:planned goes to the TaskMgr task’s QA.

  • A 200 whose code is not SUCCESS is a failure. A 200 means WhatsApp accepted the message, never that it was delivered.
  • The group is the pinned id from its file, checked once at boot against the device's group list. A group that is not there turns notifications off; a group is never found by its name.
  • One retry after two seconds, for a transport error only. A 400 and a 429 are never retried.
  • A failed send never fails the card. The failure is one ContactNotified event carrying the contact's alias, the kind and the outcome — never the destination and never the text.

The contacts are managed at the foot of the back office's Integrations view: a GitHub account, a name, a product (or all), a destination and what it wants (review:medium, review:high, review:manual, review:needs-manual, pr:no-task-code, pr:unknown-task-code, bundle:planned, e2e:failure, e2e:approval, unit:failure; a review severity includes the worse severities, and the manual kinds match only themselves). The registry is its own Contact record: it is not part of the product, so it is never rendered into a Blueprint or a workspace, and it is in no event. The list shows each destination masked.

Bundles from the PR template

For a product listed in GAOS_PR_TEMPLATE_PRODUCTS (off by default), GAOS reads the body of every pull request it follows as the team’s PR template (D-100). It reads the ticked source box, the code after Kode (jika dari task manager), the pull-request links in Cross-repo checklist and Dependency terhadap PR lain, and the section Apa saja yang perlu dites oleh QA?. Placeholders and the template’s hints are never values, and notes that look like a credential are dropped.

  • A bundle is the pull requests that share a key. The key is taskmgr:<code> when a pull request names a code, and otherwise pr:<owner/repo#n> of the pull request that links the others. A linked pull request with no code of its own joins its linker’s bundle, and a pull request opened later joins through the stored links. A link to a repository the product does not follow, or a stranger’s pull request, is listed as a reference only and never holds the bundle back.
  • When it is complete. Every member is merged or closed and at least one is merged. Ten minutes after the newest member joined, GAOS plans one Test plan card (role test-planner). The agent reads the members’ titles, changed file names, the authors’ notes and the product’s epics, all fenced as data, and proposes the cases QA should create or link. GAOS checks each one against the QA tool’s values and its own catalog, and sends them to the QA tool’s POST /api/v1/gaos/case-proposals. That route creates draft cases and links existing ones to the pull-request URLs; nothing is written to the automation repository. A planned bundle is final, and at most two test plans are open per product.
  • A missing code. A pull request that uses the template with no code and no other source ticked (after ten minutes), or that uses no template and is linked by no other pull request (after an hour), gets one GitHub comment and one WhatsApp line, once. The Pull requests page shows the chip no task code.
  • An unknown code (D-104). For a product bound to TaskMgr, a code TaskMgr does not know, a deleted or archived task, or another product’s task gets one unknown-task-code comment and line — one text for every case — even when the row was alerted for a missing code before. The bundle is unchanged. When the test plan ends DONE, the task’s QA gets a bundle:planned line and the TaskMgr task gets one note.

When something is down

FailureWhat happens
Brain Town is downNo events, no cards; nothing else is affected.
The GitHub token may not writeThe review card fails with github-token; it is not closed silently.
The QA tool is down or lacks the routesThe e2e card fails with qa-job-timeout or qa-routes-missing.
WhatsApp is downThe card is unchanged; one failed ContactNotified is recorded.
Jenkins never calls backNo staging card; the Integrations view shows the last callback per product.
GAOS restartsThe reader resumes from its cursor and the card keys make the replay a no-op. An event handed over but not yet planned when the process dies is lost.
