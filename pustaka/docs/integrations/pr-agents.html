Integrations

Pull-request agents

A product's main repository receives pull requests, and somebody has to review them and prove they still work. With the Brain Town reader on, GAOS opens the cards for that work when a pull request opens, when it merges and when the staging deploy finishes. Two of the four are agents; two are jobs GAOS hands to the QA tool.

What opens what

TriggerGAOS opensWorked by
A pull request opens (not a draft, not from a fork)A PR review cardThe pr-reviewer agent
The same eventAn e2e automation cardThe QA tool (a job GAOS starts and polls)
A pull request mergesA unit-test card; a review or e2e card that has not started is canceledThe unit-test agent
The staging deploy finishesAn e2e run cardThe QA tool

The cards live on a separate PR workflow of the product, so a pull request never resets the product's own plan. A replay plans nothing: the card carries its key, owner/repo#n:role, and a second event with the same key is a no-op. A draft, a pull request from a fork and one from an author who is not an owner, member or collaborator open nothing; GAOS_PR_MAX_OPEN (default 5) bounds the open cards of a product; GAOS_PR_ALLOW_FORKS=1 admits forks.

The labels

A card carries at most one label per family, and the vocabulary is closed: another word is refused with 422. An operator changes a label on the board, and the change is a TaskLabeled event naming the account's alias.

LabelMeaning
pr-review:autoAn agent reviews the pull request. The default.
pr-review:manualA person reviews it. The scheduler never dispatches the card.
pr-review:needs-manualThe agent found something high or critical, or its reply could not be posted. A person takes over.
e2e:automation, e2e:runThe QA-tool jobs. Never dispatched to an agent.
unit:testThe unit-test card.

The review

The pull request's title, description and diff are untrusted text and reach the agent as data in the packet, behind the egress pass: a secret in the diff refuses the dispatch, and the card waits for a person. The reviewer's instructions are Blueprint content, never a file from the pull request.

The agent ends its reply with one block, and GAOS, not the agent, posts it. The GitHub token is in the dashboard process and nowhere else.

```gaos-pr-review
severity: none | low | medium | high | critical
body: the review, at most 6000 characters, each finding with a file:line and a Reason:
```

The body is screened by the egress detectors before it is posted; a body that carries a secret is not posted and the card goes to a person. It is posted as a comment, never an approval. GitHub's answers map to a reason on the card: github-token (401, 403, 404: the token may not write there), github-refused (422), github-rate, github-error.

The settings

SettingMeaning
GAOS_GITHUB_TOKEN_FILEA file, mode 600, holding a token with pull_requests: write on the product's repositories. A Brain Town or GAOS token is refused. Unset or empty: no review is posted and no fork check is made.
GAOS_STAGING_BASIC_AUTH_FILEA file, mode 600, one line per product: productId:user:password, password of at least 12 characters. Unset or empty: the callback answers 503.
GAOS_WA_URLThe WhatsApp gateway's address. https by default, no default host. An http address is refused unless GAOS_WA_ALLOW_HTTP=1; any other scheme always is. Unset: no notifications.
GAOS_WA_ALLOW_HTTP1 lets the gateway be http on a private link only (loopback, RFC 1918, CGNAT, link-local), checked on every connection. any also allows a public address, which sends the login in clear text. The status always says the link is unencrypted. Unset: https only.
GAOS_WA_PRODUCTSThe products the notifier serves, group and contacts alike, comma separated. Empty: none, and it stays silent. With none linked, the boot group check (which would send the login) is skipped. A v0.48 deployment that sets GAOS_WA_URL must now set this too.
GAOS_QA_APPROVAL_WAIT_HOURSThe total time one QA job may wait for a person to approve its spec. Default 24, at most 720.
GAOS_WA_BASIC_AUTH_FILE, GAOS_WA_GROUP_FILEFiles, mode 600: the gateway login user:password and the pinned group id (…@g.us).
GAOS_PR_MAX_OPEN, GAOS_PR_ALLOW_FORKSThe cap on open PR cards (5) and whether forks open cards (no).

In production the four files are deploy/stacks/prod.pr-github-token, prod.pr-staging-auth, prod.pr-wa-auth and prod.pr-wa-group. They are gitignored and must exist before up; an empty one leaves that part off.

The staging callback

Jenkins calls GAOS when the staging deploy has finished:

POST /api/v1/products/{id}/staging
Authorization: Basic base64(user:password)
Content-Type: application/json

{"repo":"acme-org/sample-service","branch":"staging","commit":"0123456789abcdef","environment":"staging"}
AnswerWhen
202 {"accepted":true,"taskId":…}The e2e run card was planned.
200 {"duplicate":true,…}The same commit again: nothing new was planned.
401 with WWW-Authenticate: Basic realm="gaos"No credential, or a wrong one.
404A credential that belongs to another product, or a product that does not exist.
422The repository is not one of the product's, the commit is not a full 40- or 64-character hex sha, or the environment is not staging.
429 with Retry-AfterFive failed attempts from one source lock it for five minutes.
409The product already holds its cap of open PR cards.
503The callback is not configured.

This is the one machine route that answers HTTP Basic instead of a bearer token, because a Jenkins credential step speaks Basic. The credential is per product and is compared in constant time.

The QA tool does the e2e work

The QA tool already writes, runs, repairs and pushes an automation spec in its own automation repository. GAOS does not repeat that with a model: a job runner calls POST /api/v1/gaos/automation with {product, caseCode, mode}, polls GET /api/v1/gaos/jobs/{id} every 15 seconds for up to 40 minutes, and closes the card from the job's own status. A new automation names its case with a line QA-case: <code> in the pull request description; without one the card waits, blocked, for a person. A staging run asks for every automated case.

When the job's status is awaiting_approval, a person must approve the spec in the QA tool. That is a human wait: the card moves to Needs you with a reason carrying qa-job:<id>, and the 40-minute work clock stops. The wait budget is cumulative per job (GAOS_QA_APPROVAL_WAIT_HOURS, 24 hours by default, at most 720); past it the card fails with qa-approval-timeout, after the last poll has been read, so an approval given in the final interval is seen. One notice of kind e2e:approval is sent per job, always to the pinned group and never to a committer. More than five waits fail the card with qa-job-flapping. After a restart GAOS re-adopts a running or waiting e2e card from the job id in its reason and starts no second job. The QA tool has no cancel call: a spec approved after GAOS failed the card still opens its pull request, and the QA tool's reject is the remedy. A card id carries 12 characters of the commit; an id already held by a card with another key gets a suffix.

The two routes live in the QA tool

They are a change in the QA tool's repository, not in GAOS. Until they exist the e2e card fails with qa-routes-missing, which is visible and harmless (OQ-38).

WhatsApp and the contacts

A review finding of medium or worse, a held review and a failed test or e2e run send one line and the card's id. The findings stay on the card; no code is pasted into a chat. The line goes to the contact of the pull request's author (a review) or of the last committer (a failure), else to the pinned group.

  • A 200 whose code is not SUCCESS is a failure. A 200 means WhatsApp accepted the message, never that it was delivered.
  • The group is the pinned id from its file, checked once at boot against the device's group list. A group that is not there turns notifications off; a group is never found by its name.
  • One retry after two seconds, for a transport error only. A 400 and a 429 are never retried.
  • A failed send never fails the card. The failure is one ContactNotified event carrying the contact's alias, the kind and the outcome — never the destination and never the text.

The contacts are managed at the foot of the back office's Integrations view: a GitHub account, a name, a product (or all), a destination and what it wants (review:medium, review:high, e2e:failure, e2e:approval, unit:failure; a review value includes the worse severities). The registry is its own Contact record: it is not part of the product, so it is never rendered into a Blueprint or a workspace, and it is in no event. The list shows each destination masked.

When something is down

FailureWhat happens
Brain Town is downNo events, no cards; nothing else is affected.
The GitHub token may not writeThe review card fails with github-token; it is not closed silently.
The QA tool is down or lacks the routesThe e2e card fails with qa-job-timeout or qa-routes-missing.
WhatsApp is downThe card is unchanged; one failed ContactNotified is recorded.
Jenkins never calls backNo staging card; the Integrations view shows the last callback per product.
GAOS restartsThe reader resumes from its cursor and the card keys make the replay a no-op. An event handed over but not yet planned when the process dies is lost.
