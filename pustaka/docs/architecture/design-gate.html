Architecture

The design gate

The review step between a design and its implementation. The agent that holds the context writes the specification; a fresh reviewer with no memory of that conversation reads the specification alone and attacks it. This page is the method, the two places GAOS applies it, the mechanism that isolates a platform reviewer, and what it costs.

Both halves are built

Built, as of v0.34.0: the harness — GAOS's own development loop now starts a feature-sized change as a design document under docs/designs/, five zero-context reviewer agents read it alone, every finding is triaged, and the fixes go into the design rather than into the code. Built, as of v0.35.0: the platform half, the gate inside the product — D-068, D-069 and M17. A plan can carry a review task; the reviewer's prompt holds the design and the rubric and nothing else; and the implementation waits for the review to resolve.

The problem it answers

Nothing in GAOS reviewed a design before it was built. The readiness rubric judges a product record; the egress pass screens a packet; the handoff contract judges a reply. All three act on work that already exists. The plan for a task and the code that implements it were written by the same author, in the same session, holding the same assumptions — and the failure mode is not stupidity. It is that an assumption made in the first ten minutes is never questioned by anyone who did not share it.

This is the Elephant-Goldfish Model, open-sourced by Google in October 2026 and Apache-2.0 licensed. The name is the whole idea: the Elephant holds the project context and drafts the specification; the Goldfish are fresh sessions with no memory of that conversation, each given the document and nothing else. If a Goldfish cannot follow the document, the document is not done.

Layer 1 is built. A feature-sized change to GAOS itself starts as a document in docs/designs/. Five reviewer agents — comprehension, zoom-out, critic, readiness and a security lens — read that document alone, each with its own rubric and its own severity scale. Every finding gets exactly one disposition, the fixes are applied to the design, and the operator approves before anything is implemented. The rubric is GAOS's own rules, so a reviewer checks the design against the same rules an implementer must satisfy.

Layer 2 is the same gate inside the product: a design task produces a design artifact, a review task reviews it, and the implementation does not start until the review resolves. It is written down — the rulings, five business rules, a milestone and seven forward specifications — and built as of v0.35.0. The isolation mechanism was decided by D-069 and is described below; the event catalog stayed closed (BR-05), so no event name was added and the gate speaks in TaskMoved's rule and in artifacts.

The isolation, and its honest limit

Under Claude Code the reviewers carry omitClaudeMd: true, so the author's project memory never enters the reviewer's context — by the runtime. Under every other harness it is excluded by instruction, and a planted canary is the only evidence: one unique string per standing file, planted before the run, and the check is that no canary reached any report. A reviewer that read the memory and never quoted it would still pass that check, so the claim the probe supports is precise — the canary did not reach a report — and not the broader one it is often mistaken for.

The probe is specified so that it can fail: one control run with the exclusion deliberately disabled must produce a report that does contain a canary, and a leftover canary is caught by deploy/check-workspace.sh rather than by a later git diff.

How a platform reviewer is isolated

Answered on 2026-11-04 by D-069, which closed OQ-32. The answer in one line: the isolation boundary is the packet, not the workspace — and the standing files are the rubric rather than contamination, so they stay whole.

Amended 2026-11-04 by D-071: the boundary is the packet and the workspace. A product now has a second workspace, its own reviewer workspace, holding the published Blueprint byte-identical in its own root — so the standing files are still the rubric, whole, and the reviewer's folder holds none of the author's files. The folder is reset before every review turn, so it holds nothing but the standing files, and the run record says which workspace a turn used, so a reviewer's turn never marks the author's workspace drifted. The limits stay named: the standing files still carry the product's stories and decisions, and the two folders are siblings under one managed root, so the gateway's write boundary is not a read boundary between them.

The question was framed in a way that turned out to be wrong in a useful way. The Blueprint — the workspace GAOS generates for a product, a CLAUDE.md plus its .claude/rules/*.md — loads on every turn of that workspace, so a new session is not a zero-context turn: the reviewer's context carries the product's problem statement, its 50 domain rules and its whole decision history whether or not it asked for them. The natural reading is that the standing files are the leak, and that a reviewer needs a workspace without them. Reading the code says otherwise. Those files are the rubric — the domain rules are rendered into .claude/rules/10-brd.md — so a reviewer that could not see them could not judge the design against them. And a workspace holding the rubric but not the Blueprint is a drifting workspace under BR-39, which refuses dispatch. Cutting the standing files down was never one of the options; it was the wrong question.

What the code does show is that the author's state is sitting in the packet, and that it arrives by default. A packet is frozen per desk, and the previous stage's handoff is inherited by the next stage at that desk — deliberately, so that a workflow's stages chain. A review is a stage at that desk. Without a change, a reviewer would inherit the author's handoff, the failure lesson drawn from it and the operator's answer: precisely the assumptions the gate exists to strip out. So the ruling draws the line between the product's context and the author's process.

Two consequences follow, and both are engineering rather than policy. First, the design has to travel: GAOS reads no folder, and the allowlist admits only the instruction files, so a design that lives in a repository cannot reach a reviewer at all. It is therefore a GAOS-held artifact, carried in a new design packet part. Second, the findings travel back the same way — at .gaos/packet/context/findings.md, as context, the same way the previous handoff travels — which is what makes the implementer genuinely see the review that rejected it. The gate itself needs nothing new: it is the planner's own DEPENDS_ON edge, the existing BLOCKED status and the scheduler's existing dependency block, so no closed vocabulary widens.

The content half of the question has the same answer. What the standing files may contain is what they already contain. What may not leave the review is the matched text of anything: a finding records where a detector fired and never what it matched, so a reviewer cites a standing file by path and line exactly as it cites the design.

The honest limit

The egress pass screens what leaves. It does not screen what comes back: a reply is stored verbatim as an artifact, with no inbound screening. So a finding that quotes a secret is already in the append-only store by the time the outbound pass refuses the next dispatch. The egress pass is the backstop, not the cure, and inbound screening is a separate piece of work that this design does not claim.

The rules it is bound by

A BRD §9.7 carries five rules. Every implementation task has a design artifact and a review, and the review happens before the first dispatch. A reviewer sees the design and the rubric, and not the brief, the goal, the handoff, the failure lesson, the operator's answer or the acceptance criteria — and it records path and line, never the matched text. The isolation boundary is the packet and the workspace: the standing files stay whole in the reviewer's own workspace, and the author's session state and files are what is withheld. A design reaches a reviewer only as a GAOS-held artifact, because there is no other route, and the findings travel back the same way. An open Blocker stops the dispatch and the task goes to the operator's queue — and the clearance is refused until the back office has a real identity to check, because signedIn() today accepts a cookie from any request.

The term is design gate, distinct from the BRD's existing design review, which is a meeting after a failure and records a Decision. All six of that phrase's occurrences say which they mean.

What it costs

Five lenses means five parallel sessions per design, and the harness has no budget cap: the operator pays that bill, and nothing in the repository bounds it. Layer 1's reviewers are parallel; Layer 2's review is one task on a product's single live turn, so it queues behind everything else in that product. Two numbers are measured from the append-only review reports: the blockers caught per design, and the share of findings that need triage rather than action. The upstream project's author, Dave Rensin, estimates roughly 30% of Goldfish suggestions are worth acting on; that is the baseline, and the measured ratio is the real number.

Where it lives

The policy is docs/rules/gaos-design-review.md and it is the source of truth for the procedure. The rubric is .claude/rules/, path-scoped so it loads on demand rather than at every session start. The runbook is the gaos-design-review skill. The design documents are in docs/designs/, with their reports beside them in docs/designs/reviews/ — append-only and numbered, because the sequence of rounds is the record of how the design converged. And deploy/check-workspace.sh keeps the drift from coming back: it checks that the paths the project rules name exist, that no skill is an orphan, that every count agrees with its register, that no rule is forked between two files, that no canary was left behind, and that no secret reached the report store.
