Architecture

The gateway

How a task leaves GAOS and comes back. GAOS does not run a model; it asks ai-manager to run one turn inside the product's workspace, and ai-manager hands the turn to ai-claude-cli. This page is the contract between them, the error mapping, the session policy, and the upstream change that makes one workspace per product possible.

Built, as of v0.30.0

Decided by D-055 to D-062. Built: the upstream provisioning API (last section, live on prod since 2026-11-02), and the ai-manager adapter with the reply handoff and the error mapping below (GAOS_MODEL_MODE=aimanager), and since v0.25.0 one workspace per product with its sync, the drift gate and one live turn per product, and since v0.27.0 a session per task and recovery by request id (M14.5), proved by one real turn through live-aim-run.sh. Since v0.28.0 the board (M14.6); since v0.29.0 this is the only path, because M14.7 deleted the CLI adapter of BRD §7.6, the packet on disk and the detached runner; and since v0.30.0 the context the worker observed is compared with the pinned Blueprint after every turn (T-156).

Three layers, one job each

The product owner's wording is the specification: ai-claude-cli works the task with context; ai-manager shapes it with a workspace; GAOS shapes it with the product, the task details and the product's Blueprint. Each layer has something it alone owns and something it must never do, in the same form as the six layers.

LayerOwnsMust never
GAOSThe product record, its Blueprint and versions, readiness, the task graph and status machine, the brief, egress screening, the event stream, the durable prompt, reply and handoff of every attempt, the boardSpawn a model tool; hold a provider credential; send a filesystem path
ai-managerAuthentication, the list of workspaces chat may use, sessions, async request-reply, cost and usage accountingChoose a folder from client input; replace a lost session silently
ai-claude-cliThe folder under one managed root, the instruction files allowed in it, running claude with resume, reporting what it observed at startupWrite outside the managed root, or write a file outside the allowlist

One product has exactly one workspace, with the id gaos-<tenant>-<product code>. The id is derived once, stored on the Workspace vertex, and never renamed, because ai-claude-cli keys stored transcripts by it.

The request id is deterministic for a reason. ai-manager treats a second POST with the same X-Request-ID as a no-op, so a request whose 202 was lost can be sent again without starting a second turn. The same id is what recovery polls after a restart.

The last step exists because a turn can change the workspace it ran in: a model may rewrite its own CLAUDE.md. So after every turn GAOS asks for the workspace digest again and compares the context the worker reports in metadata.context.workspace with the pinned Blueprint version. Drift leaves the finished attempt's outcome alone; it records a DispatchRefused with rule observed-drift and refuses the next dispatch in that product until a sync puts the published Blueprint back (BR-39). Drift is detected, not prevented.

Sessions: one per task

ai-manager keeps a conversation as a session: GAOS sends only the new message, and the worker restores the transcript before every turn. GAOS opens one session per task (D-056), not one per product.

Why not one long session per product

ai-manager runs one turn at a time per session and answers a second with 409, so a product session would queue every task behind every other. Each turn re-reads the whole transcript, so cost would grow with the product's age. And sessions expire thirty days after their last turn, so the product's memory would vanish on a timer. Knowledge that must outlive a task belongs in the Blueprint, which every session loads from the workspace, and in earlier handoffs cited into the brief.

The session is transport, not the record (BR-41). For every attempt GAOS stores the rendered prompt, the full reply, the parsed handoff and the metadata ai-manager returned. All of it stays readable after the session expires or answers 410.

When GAOS restarts mid-turn

There is no process to adopt any more; there is a request id. At boot GAOS polls the id of every TaskRun still marked STARTED or RUNNING.

pseudocode
for run in taskRuns where status in (STARTED, RUNNING) and requestId != "":
    r = GET /v1/requests/{run.requestId}

    if r.status in (completed, failed):
        finish(run, result(r))          # adopt: the same Attempt a supervised run gets
    elif r.status in (pending, processing):
        keep_polling(run)               # lease held, heartbeats continue
    else:  # 404 -- ai-manager restarted, or the record aged out
        emit TaskOrphaned(rule=request-lost)
        hold lease until run.submittedAt + GAOS_AIM_TURN_DEADLINE
        requeue(run.task, new_session=true)

The last branch is the important one. ai-manager keeps request records in memory, so a 404 may mean the turn is still running in the worker with nobody listening. Nothing in ai-manager can cancel it (OQ-26), so GAOS keeps the workspace leased until the turn must have ended — GAOS_AIM_TURN_DEADLINE, default 660 seconds, longer than ai-manager's own 600-second provider timeout — and only then hands the workspace to another turn. This is D-054's rule kept and its mechanism replaced: a turn that cannot be proved dead is made dead, by waiting rather than by a signal.

When the agent needs the operator

Added in v0.31.0 (D-064, I-11). Some decisions are the operator's: a product choice the record does not settle, a trade-off with a cost GAOS cannot see. Guessing wastes the turn and the retry after it, so the agent may ask — and because a turn cannot pause (no stdin, no cancel, OQ-26), asking ends the turn.

  1. GAOS sends every turn with ask_user: true and caller: "gaos". The worker adds the question protocol to the system prompt and turns off Claude Code's own AskUserQuestion, which has nobody to answer it headless.
  2. The model ends its reply with one ai-question block — exactly three options, the one it recommends first; the operator's own words are always a fourth — and writes no handoff. A block with any other number of options is not a question, and the turn is judged as usual.
  3. ai-manager stores the question in its temp bucket and returns it on the reply: finish_reason: "awaiting_input", question: {id, question, context, options}.
  4. GAOS moves the task to AWAITING_INPUT, stores the question as an artifact, writes QuestionAsked, and lists it in the "Needs you" inbox. The task holds no lease and the scheduler never picks it (BR-44).
  5. The operator answers — POST /products/{id}/tasks/{taskId}/answer, {choice: 1..4, text}. GAOS writes QuestionAnswered and the task goes to READY.
  6. The next attempt is an ordinary turn with its own request id, sent through POST /v1/questions/{id}/answer: ai-manager marks the question answered and resumes the session that asked, with the operator's answer and GAOS's reply contract as the prompt. If that route refuses — already answered, expired, the store switched off — GAOS sends the turn through /v1/chat instead; the answer is in the frozen slice as context/answer.md either way.
  7. A question is open as long as the session that asked it exists — thirty days from the asking turn (D-066). The answer turn resumes that session even past GAOS's twenty-five-day rotation; at thirty days the task moves to BLOCKED with rule question-expired.

Which vendor runs a turn

ai-manager has two session vendors: claude (ai-claude-cli) and antigravity, a round-robin pool of ai-antigravity-cli accounts on several hosts that fails over only between its own accounts. Each product's vendor policy (D-067) — Claude CLI only, Antigravity only, or mixed by role — decides which one a task's turn names, and the product picks the Antigravity model from the models that GET /v1/providers lists.

VendorThe turn sendsThe workspace
Claude CLIno provider (ai-manager's session default) and GAOS_MODEL — the body every turn had before M16Admin calls with no ?provider, as before
Antigravityprovider: antigravity on the first turn and on every resume, and the product's model or noneAdmin calls with ?provider=antigravity, fanned out to every account; agy reads the same files through AGENTS.md, GEMINI.md and .agents/rules links

The run records the vendor (TaskRun.provider), so a retry knows where its session lives; a retry whose vendor changed opens a new one (BR-45). The Blueprint gate asks every vendor the policy uses. When the pool's copies disagree ai-manager answers 409, and GAOS's sync repairs it: provision, which creates the missing copies and leaves the rest, then one pruning write without if_match. Nothing falls back between vendors: a failed Antigravity turn fails and is retried on Antigravity.

The upstream change: provisioning a workspace

Measured on 2026-11-02, ai-claude-cli has no API to create a workspace and reads configs/workspaces.json once at startup; ai-manager can only switch an existing one on or off. D-059 extends both. This is the specification M14.1 builds in the ardi-personal-workspace-ai repository.
