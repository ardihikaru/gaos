Architecture

The system

GAOS is a graph-native agent operating system. Six layers, five control loops, and one thesis that decides every other design question: the graph is the primitive, not the prompt.

Two invariants everything else follows from

State lives in the graph. The orchestrator holds no authoritative state. Kill it mid-run and it rebuilds from vertices, edges and events. Anything an orchestrator keeps in process memory is state that a restart silently invents a new version of.

Every change emits an event. An event that was never written is a state change that never happened. This is not a logging convention — it is what makes replay possible at all, and it is why the event catalog is closed rather than open.

Why the graph and not a prompt chain

A prompt chain has no addressable intermediate state. You cannot ask it what a task depended on, which requirement justified a decision, or what exactly was sent to the model on attempt two — because none of that was ever a thing, only a substring. In a graph each of those is a vertex with edges, and the question is a traversal.

Three layers outside the six

Since D-055 the model is not run by any of the six layers above. GAOS hands one turn at a time to ai-manager, which runs it through ai-claude-cli in the product's workspace. ai-claude-cli works the task with context; ai-manager shapes it with a workspace; GAOS shapes it with the product, the task details and the product's Blueprint. The contract between them is The gateway; what GAOS writes into the workspace is the Blueprint.

What happens when the orchestrator restarts

Because execution does not die with orchestration, a restart finds tasks that claim to be running. The recovery is a reconciliation, not a reset:

pseudocode
for task in tasks where status in (DISPATCHED, RUNNING):
    lease = task.workspace.leaseUntil
    beat  = task.lastHeartbeatAt

    if lease > now and beat > now - heartbeat_timeout:
        adopt(task)                    # the process is alive; reattach
    elif lease > now:
        kill(task); requeue(task)      # lease held, SUPERVISOR gone -- see below
    else:
        emit TaskOrphaned(rule=lease-expired)

A task that cannot be proved alive is not assumed alive. The heartbeat and the lease are two independent signals precisely so that a hung process and a dead one are distinguishable.

The middle branch used to say “process gone”. It does not know that.

It knows the beat is stale, and a stale beat means the supervisor died — which says nothing whatever about the child, because work is detached precisely so it outlives its supervisor. Requeuing on that basis starts a second run in a workspace that may still have a live one in it: the exact silent corruption the exclusive lease exists to prevent, reached through the recovery routine. So requeue kills first. A run that can be proved neither alive nor dead is made dead before its workspace is handed to anybody (D-054). The event this branch emitted was also named TaskFailed here, which is not in the closed catalog — it is TaskOrphaned, and both corrections landed with the code that made them matter.

Through the gateway, there is no process to adopt

Once M14.5 lands, the routine above is replaced by a poll on the request id each attempt persisted before it was sent: a finished request is adopted, a running one is kept, and a lost one — ai-manager keeps request records in memory — holds the workspace until the turn must have ended, then requeues on a new session (D-060). The principle above is unchanged; the turn is made dead by waiting, because nothing can signal it. The gateway §recovery.

Autonomy begins when the scheduler can find a READY task without a human naming it. That requires four things at once: an acyclic dependency graph, a capable agent for the role, an acquirable workspace lease, and a readiness gate that passed. Miss any one and the work queues instead of starting — which is the correct failure, and the one the room-occupancy meters on the floor are there to make visible.

Scoring, and when to stop trying

Every completed run is scored on five dimensions and reduced to one number:

formula
final = 0.45·correctness
      + 0.20·completeness
      + 0.15·safety
      + 0.10·quality
      + 0.10·efficiency
ScoreVerdict
85–100accept
70–84accept, and plan a cleanup task
50–69iterate with a widened context slice
30–49escalate one model tier
0–29stop, and call a design review
safety < 60immediate stop, regardless of the total

The guardrails are what stop a loop, not the scoring

max_retry_count 3 per task · max_escalation_count 2 per task · same_failure_signature_limit 2 · exponential cooldown with a cap · a budget cap per workflow and per tenant · human intervention at two escalations or any safety veto. A scoring function alone will happily retry forever at 68.

The failure signature — a hash of the normalised error — is what decides retry versus design review. Two attempts failing the same way is not bad luck; it is a problem the model cannot see, and a third attempt at a higher tier will fail identically.

A record also decays. The effective score is the raw score minus a drift penalty:

formula
drift_penalty = min(25,
      4 × months_since_last_review
    + 6 × (boundary_files_changed > 0)
    + 8 × (open_contradictions > 0))

Crossing a band downward emits ReadinessDropped. A document that was accurate a year ago and has not been read since is not a specification; it is a historical artifact, and the planner should treat it as one.

Replay

formula
state(t) = fold(reduce, events.filter(e => e.ts <= t), snapshot_before(t) ?? empty)

reduce must be pure, total, and order-stable by (ts, seq). Pure so it can be re-run; total so an unknown event type cannot crash a replay of last month; order-stable so two events in the same second cannot produce two different pasts.

Replay scopes are Workflow, Task, Meeting, and Comparison. Route replay through a read-only store handle, not a flag — a flag is one forgotten branch away from a replay that writes.

Build order

Ten deliverables, sequenced. Mission Control is number nine, and that is deliberate.

  1. Graph schema and event store
  2. Task state machine
  3. Product master and readiness scoring
  4. Planner producing a static task graph
  5. Runner with one detached process
  6. Review, scoring and retry policy
  7. Context assembly
  8. Approval gates
  9. Mission Control and replay
  10. Meetings, knowledge extraction, multi-repo

Resist starting with the visual layer

It is the most rewarding to build and the least load-bearing. This repository has done exactly that anyway — see the changelog — but for a stated reason: the first thing worth proving was the deployment path, and a dashboard is the only component that exercises all of it. Steps 1, 2 and 9 are done and step 5 is half done; what moves the desks on that floor is still a simulation rather than work, and the page says so.
