Architecture

The graph

33 vertex types, 3 document types, 38 edge types in ArcadeDB — one engine covering graph, document and event store. This is the shape, the conventions every type obeys, and the handful of decisions that are expensive to reverse.

Six modelling principles

  1. Schema-full where machines read, schema-less where humans write. Task, Event and Review are strict. Requirement and Artifact are hybrid — a human filling a record should not hit a validation error for writing a sentence.
  2. A business id alongside the physical RID. ArcadeDB gives every record a #bucket:position. Events reference the business id, never the RID — a RID is a storage address, and an event stream that encodes storage addresses cannot survive a migration.
  3. One edge type per relationship. Never a generic REL with a type property. This is described in the source document as the single biggest performance decision in the model, and it is: a typed edge is an index; a property filter on a generic edge is a scan of everything.
  4. The event stream is a first-class type. Append-only, never updated, time-partitioned.
  5. Heavy payloads go EXTERNAL. ContextSlice.rendered, Prompt.template, Artifact.body — or to object storage.
  6. Tenancy is a database boundary first, a property second. One ArcadeDB database per tenant — and keep tenantId on every vertex anyway.

Two supertypes

Every vertex extends GaosVertex; every edge extends GaosEdge. The audit and identity properties are defined once.

Three of these carry BUCKETS 8 because they are the high-volume ones: Task, TaskRun, and the code-graph types.

Why Task and TaskRun are separate

Folding attempts into the task destroys per-retry evidence. Each attempt has its own cost, its own model, its own failure signature and its own log — and the retry policy is a function of exactly those. Collapse them and the second attempt overwrites the reason the first one failed.

v0.52.0 adds six events and two types (D-091): DefectReported (a defect of a case was recorded, by its key and kind, never its text), DefectTriaged (the verdict and, for a downgrade, its code), DefectStateChanged (a defect moved between open, triaged, fixing, fixed and closed, by a rule), FixPROpened (GAOS opened a draft pull request: repository, number and branch), FixPRStateChanged (the pull request went draft, ready, merged or closed) and AutoFixConfigured (an operator changed a product's auto-fix settings: the alias, the new values and the kind of write token, never the template text). The new types are Defect, one record per reported defect, and FixPR, one per pull request GAOS opened; neither is in an event beyond its key. Task gains autoAt.

v0.48.0 adds five events and one type (D-088): PullRequestOpened, PullRequestMerged and StagingDeployed (a pull-request event or the staging callback was planned into cards), ContactNotified (a notification was attempted: the contact's alias, the kind and the outcome, never the destination) and TaskLabeled (an operator changed a card's label). The new type is Contact, a GitHub account mapped to a notification destination, which is in no event; Task gains labels and dedupKey.

v0.42.0 adds two events and no type (D-082): ConversationArchived (a finished card's conversation archived or restored, by the signed-in account, which now also fills Event.actor) and ConversationPruned (the prune's certificate: which attempts' prompt, reply and question documents were emptied, each one's SHA-256 and length, what survives, and how the gateway sessions fared — never a session id). A prune sets Artifact.body to an empty string; the artifact's row, every event, run record and context slice stay.

Since v0.41.0 an event carries the wall-clock time it was emitted at (D-081): an at key, unix seconds on the dashboard's clock, beside the reducer's delta in payload. ts stays the database's own write time; a row written before v0.41.0 has no at and is read at its ts, corrected by the database's zone. The board reads a card's TaskPlanned and TaskMoved events by that clock to say how long the card spent in each status and how much of it no AI was working on it — a read, never a stored rollup.

Event carries a seq LONG that is monotonic and gapless per tenant. That invariant is what makes a single writer per tenant a requirement rather than a preference — a gap in the sequence is an event that was lost, and a fold cannot tell the difference between a gap and a deletion.

Two directions that are easy to get backwards

DEPENDS_ON points from the dependent to its prerequisite, so out('DEPENDS_ON') is the set of things that must finish first. Reverse it and the READY-task scan silently returns the wrong tasks.

USES_CONTEXT hangs off ContextSlice, not Task. Each attempt keeps its own context evidence; attaching it to the task means attempt two overwrites what attempt one was actually given.

Invariants, each with a detection query

These are checked continuously and feed a health panel, rather than being assumed:

  • A task holds at most one unexpired workspace lease
  • DEPENDS_ON is acyclic — enforced by the planner, on every write
  • Every exited TaskRun has exactly one Review
  • Every Knowledge links to at least one piece of evidence
  • Every STOP verdict carries a reasonCode
  • A gated task cannot reach DONE without a GRANTED Approval
  • Event.seq is gapless per tenant
  • Product.readinessScore matches a recomputation

The one query to understand first

Everything the scheduler does starts here — find work whose prerequisites are all done:

sql · ArcadeDB
SELECT FROM Task
WHERE tenantId = :tenant
  AND status = 'PENDING'
  AND out('DEPENDS_ON')[status <> 'DONE'].size() = 0
ORDER BY priority DESC
LIMIT 20

This is why DEPENDS_ON's direction is not a matter of taste, and why Task (tenantId, status, priority) is the index the whole system's throughput rests on.

What is not built yet

Both tiers now carry this schema, and the dashboard reads and writes it. dashboard/store_arcade.go landed on 2026-08-17 as the implementation dashboard/store.go declared the interface for, and the binary applies the DDL itself from an embedded copy on every boot — idempotent, so a restart is a no-op. The half above it is there too: dashboard/scheduler.go decides as a pure function of the graph, and since v0.29.0 every attempt is one turn through ai-manager (the gateway), written as a TaskRun with the ContextSlice it was given and the Blueprint version it is pinned to, and recorded with its request id before it is sent. Real models have answered those turns (deploy/acceptance/live-aim-run.sh). What is not built is what judges the result — nothing reviews what a run produced, and no guard ends a retry loop. The board that renders over the graph moves only when a task does: since v0.30.0 every task status change is a TaskMoved event, folded by dashboard/taskfold.go, and the simulated floor that used to stand in for work was deleted in v0.29.0.

The event stream is no longer a window over its own tail. Until v0.11.0 it was a ring buffer of a hundred and sixty entries, with each entry carrying a photograph of the whole floor and the replay cursor shifted whenever the window moved — everything older than the window was unreachable, which is the opposite of what BR-04 asks an append-only record to be. It is now the whole record, unbounded, and an event carries the delta a reducer folds rather than a floor. Replay is a fold from the nearest snapshot forward, snapshots are an optimisation the fold is tested without, and the read-only handle replaced the flag the architecture document named as the thing that will eventually be forgotten. The fold test — TC-050 and TC-051, one of the three acceptance tests BRD §4.1 names — ran for the first time on 2026-08-17.

The DDL itself is no longer only a document. On 2026-08-16 it was extracted into ten runnable files under dashboard/schema/ and applied to a scratch ArcadeDB 26.7.2, the version D-043 pins: 321 statements at the time, applied clean and idempotent on a second run — 323 today, since D-037's deferred task state brought two TaskRun properties with it. That first run is where the value was — 53 statements failed, and reconciling them produced two amendments to the data model, with a third following on 2026-08-17 when the store first wrote to the graph (D-047). D-045 is a dialect difference: edge uniqueness is a unique index on (`@out`, `@in`), not a UNIQUE keyword on the type, which this version rejects outright. D-046 is not a dialect difference but an error in the model: partitioned('tenantId') requires tenantId to be unique, which would have permitted one Task per tenant, so it is withdrawn.

The complete DDL, the query cookbook and the full property lists are in artifacts/v1/gaos-arcadedb-model.html, amended in place at §04, §09 and §13 with a callout on each. The runnable, reconciled copy is dashboard/schema/, applied by deploy/schema/apply.sh, and dashboard/schema/RECONCILIATION.md records every deviation with the commands to reproduce the measurement.
