Living beside other products

GAOS is not alone on the private VM. Several unrelated products share the same machine, the same tunnel and the same databases — held apart by a port register, a naming convention, and network boundaries that are structural rather than promised.

One VM, many products

Each product owns a stack, its own proxy, and exactly one tunnel port per environment. Nothing is shared at the routing layer: one product's misconfiguration cannot capture another product's traffic, because the two proxies never see each other's containers.

That per-product proxy is worth the roughly 30–40 MB it idles at. The alternative — one shared ingress reading every container on the host — means a mislabelled container in one product can silently start answering for another, and the failure presents as a 404 with a healthy backend and nothing in any log.

The port register

Ports are derived, not remembered. The pattern is 1<env><product>1: the second digit is the environment — 18xx1 production, 19xx1 non-production — and the middle pair identifies the product.

A product's development port therefore falls out of its production port without a lookup. The register is the only thing preventing two products from claiming the same number, so claiming a slot means writing it down, not just using it.

One namespace per product

Each product gets a wildcard namespace and one line in the edge's host map. Adding a subdomain inside that namespace costs nothing at the edge — no DNS change, no certificate change, no nginx change — because the wildcard and the map entry already cover it.

Wildcards match exactly one level

*.gaos.mfardiansyah.id covers dev.gaos.mfardiansyah.id, but it does not cover a.b.gaos.mfardiansyah.id. Every namespace level needs its own DNS record and its own certificate SAN. The classic symptom is one product working while another answers with a bare connection reset: a third-level wildcard was never created, or its SAN never made it onto the certificate.

What is shared and what is not

Only what needs data joins the data network

In GAOS's stacks, only the dashboard joins the shared network. The proxy, the PWA, the panel and these docs cannot resolve — let alone reach — the neighbouring products' databases. Least privilege as a topology, not a policy.

The shared stack is nobody's to restart

The database stack belongs to the environment, not to a product. A product declares the network as external so it can never create it, and can therefore never quietly bring up a half-configured replacement of something its neighbours depend on.

A product touches only its own data

GAOS owns its own database and nothing else in the shared stack — the other schemas and buckets there belong to other projects. Sharing a network is not a licence to read what is on it.

Credentials come from the environment

No shared credential is ever copied into a product's repository. Values are referenced by name and supplied on the host, so a leak in one repository cannot expose infrastructure the other products depend on.

Never bulk-import the shared environment file

An env_file injects every line it finds. Appending the shared infrastructure .env into a product's file hands that product's containers the credentials of every other project on the host. Copy the handful of names actually needed, one line at a time.

A neighbour GAOS calls: ai-manager

Every other neighbour on this page is something GAOS must stay apart from. Since D-055 one is something it depends on: model work goes to ai-manager, which runs it through ai-claude-cli in a workspace per product. Both belong to the owner's AI stack, not to GAOS, and GAOS reaches ai-manager over HTTPS at its public address rather than by joining its network — the same boundary rule as everything above, applied to a dependency.

Adding a product

The routine work is three steps at the edge, and then nothing at the edge ever again.

  1. Claim the next free slot in the port register and write it down.
  2. Add the DNS record for the new wildcard namespace, and add the same name as a SAN on the certificate the edge renews.
  3. Add one line to the edge's host map, ordered so the more specific pattern wins.

Everything after that belongs to the product: its own compose stack, its own proxy on its own tunnel port, its own routing table, its own secrets. Subdomains within its namespace are its own business and cost nothing to add.

The checks that catch a bad neighbour

Two things go wrong quietly when a new stack lands: a port published without the tunnel address, which puts the stack on the local network; and a stack joining the wrong environment's shared network, which is undetectable at runtime because it simply works. Assert both mechanically. A smoke test will never find either one.
