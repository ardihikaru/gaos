Infrastructure

Development and production

Two tiers of the same four services, on product slot 03. This is what differs between them, what must not, and how to bring either one up and prove it works.

The same shape, twice

Each tier is four services behind its own Traefik: the landing page, Mission Control, these docs, and the proxy itself. Both are served from a single origin, routed by path.

PathServicePrefix stripped?
/the landing page, static, via nginx — owns the origin's 404n/a
/app/Mission Control, Go + HTMXyes
/docs/these docs, pustakayes
/api/the dashboard's JSON surface — /api/healthzyes

One origin is not cosmetic: there is no CORS to configure between anything served here, and it is what lets Mission Control reference every asset, fragment and form action relatively.

Both stripped services depend on a header, and fail silently without it

Neither the dashboard nor pustaka has a base-path option. /app and /docs work solely because Traefik's stripPrefix also sets X-Forwarded-Prefix, and both read it back — the dashboard into a single <base href>, pustaka onto its root-absolute login redirects.

Replace stripPrefix with a rewrite that drops that header and you get 200 on every document and 404 on every asset. No error is logged and no status-code check sees it.

The trailing-slash redirects run before the strip, for the same reason. At /app with no slash the document base resolves one level up, so static/app.css becomes /static/app.css — which the landing page answers with its own 404, while the document itself still returns 200.

A difference outside this table is a bug rather than a decision. The two compose files are deliberately the same shape, and deploy/check-stacks.sh asserts the entries that are dangerous to get wrong.

The expensive mistake is invisible

A development stack pointed at the production database starts cleanly, passes every smoke test and behaves normally. Nothing about it looks wrong until it writes something. That is why the network name and the database host are asserted mechanically rather than reviewed.

What must not differ

SettingBoth tiersWhy
GAOS_COOKIE_SECURE 1 The browser reaches both tiers over real TLS at the edge. The flag is env-driven, never derived from the scheme — these containers only ever see plain HTTP inside the tunnel, so deriving it would drop the flag in production.
GAOS_ARCADE_DB gaos Same database name in two different instances. Renaming one tier's database is how you end up with a migration that only ever ran once.
Traefik trustedIPs 10.10.0.0/24 Shared file, one list. See the real client IP — a wrong list looks perfectly healthy.

A cookie-aware client will refuse to store the session over the tunnel

That is correct. Check the Secure flag is present in Set-Cookie, defer the login round-trip to HTTPS, and do not “fix” it by turning the flag off.

Bringing a tier up

Development first, always. There is no bootstrap step in this release — no schema is applied yet — so the sequence is short:

bash
cd /home/ardi/devel/projects/gaos
./deploy/check-stacks.sh                     # the invariants a running stack hides

S=deploy/stacks/compose.dev.yaml             # then repeat with compose.prod.yaml
docker compose -f $S build
docker compose -f $S up -d
docker compose -f $S ps --format '{{.Service}}\t{{.Status}}\t{{.Ports}}'

If compose says the external network cannot be found

The infrastructure stack is down. Start it there. Never docker network create it here — that produces an empty network with the right name, and a stack that comes up and then cannot resolve anything.

Four gitignored files hold everything secret, split per service and per tier so the docs container never holds the database password:

The compose files reference them with env_file:, not ${…} interpolation — there is no flag to forget, and a missing file is a hard error rather than a silently empty password. The committed *.env.example files document every name.

Fill them by name, one line at a time

Never cat an infrastructure .env into one of these. env_file injects every line it finds, which hands GAOS's containers every other project's credentials on that host.

Generate the docs cookie secret on the host

openssl rand -hex 32 into PUSTAKA_AUTH_SECRET. Left blank, the server invents a random one per process — so every deploy and every restart signs everyone out. Do not copy a value out of another project's compose file: a secret in version control is not a secret.

Verifying over the tunnel

Nothing is bound publicly. One row per tier, and it must read 10.10.0.2 — never 0.0.0.0:

bash
ss -ltnp | grep -E ':(18301|19301)'
curl -sS --connect-timeout 3 http://LAN_IP:19301/    # must be REFUSED

Through the tunnel, from the edge — the real test:

bash
ssh clino "curl -sS -H 'Host: dev.gaos.mfardiansyah.id' http://10.10.0.2:19301/api/healthz"
ssh clino "curl -sS -H 'Host: gaos.mfardiansyah.id'     http://10.10.0.2:18301/api/healthz"
# {"ok":true,"database":"gaos","store":"memory",...}
What you getWhat it means
502The dashboard container is not running at all.
503 · "database":"unreachable"The ArcadeDB leg is wrong — network name, container alias or credentials.
"database":"unconfigured", ok:trueNo GAOS_ARCADE_URL is set. Correct for the local stack, wrong for a deployed tier.

Then the routing. / answers 200 from the landing page; /app and /docs both answer 301 to their trailing-slash form.

Check the base href actually survived the strip

This is the failure that returns 200 on the document and 404 on every asset:

bash
ssh clino "curl -sS -H 'Host: gaos.mfardiansyah.id' \
  http://10.10.0.2:18301/app/" | grep -o '<base href="[^"]*">'
# must read <base href="/app/"> — NOT <base href="/">

Finally, the real client IP. Traefik believes X-Forwarded-For only from a peer in its trust list; from anyone else it discards the header and substitutes the peer's own address — so a wrong list collapses every caller on earth into one identity while everything looks healthy. The procedure is on the overview page, and it is not optional.
