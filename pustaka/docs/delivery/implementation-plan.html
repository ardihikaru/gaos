Delivery

Implementation plan

Every business requirement in the BRD, mapped against the code that is actually committed, and broken into fourteen modules of work you can pick up one at a time. One hundred and forty-one tasks: forty done, sixteen standing on fixtures, eighty-five not started.

How to read this

The BRD says what GAOS must do and marks each requirement Designed, Built, Decided or Open. That is the right vocabulary for a business document and the wrong one for a Monday morning: the statuses are spread across twelve tables, a requirement can be one sentence or a whole subsystem, and nothing on the page says which file the work lands in. This page is the other half — the same requirements, cut into modules and sub-modules, each task small enough to finish and pointed at the code.

FlagWhat it means
✅Running in this repository today, and the row names the file. Nothing is flagged done that cannot be pointed at.
🟡Exists, but only over fixtures or the simulator. The shape is right and the requirement is not met.
❌Not started.

The middle flag is not padding. The BRD itself marks A-7, C-6, F-5 and H-5 as Built (against fixtures), and dashboard/sim.go implements the whole of Domain E's scoring policy without ever calling a model. Forcing those into ✅ or ❌ would make this page lie in one direction or the other.

What ✅ does not mean

Forty tasks are done. Ten of them are the operator surface, five are the schema, and three are the store seam that now reads and writes it — M0.2 closed on 2026-08-17, so a restart no longer returns the fixtures. The rest are the foundations that landed with it: five the event store and its reducer, four replay, two the closed catalog, two the state machine, one the determinism proof, three the readiness rubric and the floor it feeds (M2, 2026-08-20), and three the whole of M13, which is now complete. What is still missing is the whole of execution: there is no scheduler, no runner and no model call anywhere in the repository, and the floor that renders above the graph is still moved by a simulation rather than by work. That inversion is deliberate and logged as D-019 — it is also why the remaining order matters.

M0 · Foundations — schema, event store, state machine

Build-order steps 1 and 2, and the module every other module was waiting on. Eighteen tasks, seventeen done, and the one that is not is not blocked on this module. Two invariants live here and nowhere else: state lives in the graph (BR-01) and every change emits an event (BR-02). Since M0.2 closed both hold — the graph is authoritative, every mutation writes an event before it commits, and a restart rebuilds the floor from ArcadeDB rather than from the fixtures. Since M0.3 they hold well: the stream is the whole record rather than a window over its tail, an event carries the delta a reducer folds rather than a photograph of the floor, and M0.5 means a transition nobody declared is refused at the boundary instead of being prevented by nothing having tried it yet.

M0.1 — Schema and DDL (T-001–T-005)

Done, on 2026-08-16. The data model specifies 25 vertex types, 3 document types and 32 edge types with their indexes and retention, and all of it now lives as ten runnable files under dashboard/schema/, applied by the idempotent deploy/schema/apply.sh — 323 statements today, run against ArcadeDB 26.7.2, the version pinned by D-043. Until this ran, the schema was a document rather than a database, which is what R-03 was about.

The model document told itself to verify the dialect before relying on it, and it was right to: 53 of the 314 statements failed the first time. Two amendments came out of that, both logged and both marked in place on the model document. D-045 is dialect — UNIQUE is not a CREATE EDGE TYPE modifier on this version, and edge uniqueness is carried by an index on (`@out`, `@in`) instead. D-046 is not: partitioned('tenantId') requires a unique tenantId, which permits one Task per tenant, so it is withdrawn. That one is an error in the committed model rather than a difference between versions, and it is the reason this task was worth doing before anything was built on top of it. dashboard/schema/RECONCILIATION.md records both, with the commands to reproduce the measurement.

Three rules constrain the DDL rather than the code: one edge type per relationship with no generic edge (BR-24), heavy payloads stored EXTERNAL so the scheduler never traverses them (BR-25), and tenantId declared and indexed whatever the tenancy strategy turns out to be (BR-26).

M0.2 — The store seam (T-006–T-008)

Done, on 2026-08-17. dashboard/store.go was written to be the seam and said so: store_arcade.go in the next one speaks the ArcadeDB HTTP API and THIS FILE DOES NOT CHANGE. It did not change. dashboard/store_arcade.go implements all twenty-four methods against it, dashboard/arcade.go gained the query path it never had — parameterised query, command and transaction, stdlib only, because dashboard/go.mod still has no dependencies — and dashboard/store_conformance_test.go runs thirty-two cases against both implementations, which is what the task asked for and what stops the seam from rotting.

This is where BR-01 and BR-02 start holding. Be precise about how far: the graph is authoritative and every mutation writes an event before it commits, but reads are served from an in-memory projection rebuilt from the graph on boot. BR-01 permits exactly that — anything cached in memory must be reconstructible — and TC-126 is the case that keeps it honest, reopening a store on the same tenant and demanding the floor, the events and the master record come back. The measured version: a product created through the back office, the process killed, a fresh process on the same database still serving it.

Three things were found by writing it rather than by reading the model, all recorded in dashboard/schema/RECONCILIATION.md. D-047 is the substantive one: the model gave an identity index to seven of the twenty-five vertex types, and 26.7.2 refuses a write keyed by business id against a type without one — so seven more were added and the DDL now applies 321 statements rather than 314. The other two are dialect: retry is a reserved word, and an UPSERT cannot set a createdAt that must not move without ifnull.

Two things this deliberately did not do. The event stream is still the 160-entry window Events() has always returned, because Replay(eventIdx) addresses that slice and both stores must agree on what it is — unbounding it is T-013. And the floor still moves by simulation rather than by work, which is M4. The simulation runs only under MemStore: ArcadeStore holds real state and a floor that moved on its own would be writing events nobody asked for.

M0.3 — Event store and the fold (T-009–T-013)

Done, on 2026-08-17. An Event used to carry a deep copy of the entire floor, and the stream was a ring buffer capped at 160 entries with the replay cursor shifted whenever the window moved. That is a screen recording, not an event store: it satisfied the UI and none of H-1, H-2, BR-04 or BR-21.

The ring is gone and nothing replaces it. The stream is append-only and unbounded, and the retention D-012 asks for is by age, enforced where the events live, rather than by discarding the beginning of history in memory. The replay cursor is an event seq rather than an offset into a slice — which is what made the shifting necessary in the first place, and what made the oldest moments unreachable. dashboard/fold.go holds the reducer: one case per event type that moves the floor, a default that changes nothing, and no clock, no random and no I/O anywhere in it. Events carry a typed delta instead of a photograph, in absolute values rather than increments, because a fold that replays an increment twice is wrong in a way that is very hard to see. FloorOpened is the single exception and carries the seeded floor, because the fixtures are a state no event produced — that is §08's ?? empty made concrete.

BR-03 turned out to be a guard rather than a change: writeEvent already stored the business id and never the RID. So T-010 is a test that would notice if that stopped being true, run against both stores.

Writing the reducer found a real disagreement, which is the point of writing it

Two code paths emitted RetryRequested and only one of them cleared the score: the operator's retry in store_mem.go did, the review loop's retry in sim.go did not. Nothing had ever noticed, because nothing had ever had to say what the event meant in one place. A reducer case cannot honour both readings, so the question had to be answered — the verdict belongs to the attempt that earned it, and a retry is a new attempt — and sim.go now clears it too. That is what the architecture document means when it says building replay forces the event model to be honest.

M0.5 — The task state machine (T-017–T-018)

Done, on 2026-08-17. Build-order step 2, and the reason BR-06 was only half-satisfied. dashboard/store.go already returned a Result or a rejection reason through reject(), so no route answered a bare 200 — the shape was right. M2 · Readiness gating

Domain B, requirements B-1…B-5, plus BR-07…BR-10. Nine tasks, three done on 2026-08-20. This is the module that turns is the brief good enough? into a number, and it is build-order step 3. The rubric and the refusal are the half that does not need a scheduler; what is left in this module does.

M2.1 — The rubric (T-030–T-031)

Eleven of the twelve can be earned today, so the ceiling is 95. Verification strategy asks how correctness is proven; the graph schema has somewhere to put that answer (AcceptanceCriterion.verifiedBy) and the in-memory record does not, so the signal is listed, scores zero and says why. M3.2 — The task graph (T-041–T-042)

PlanWorkflow was already a pure function, which is the property that matters and the one that is hardest to retrofit. What it produced was a chain — every task carrying the previous one as its single prerequisite — which is acyclic the way a straight line is, and which left the cycle check with nothing to catch and DEPENDS_ON as decoration. T-042 closed that on 2026-08-22. M4 · Execution

Domain D, requirements D-1…D-13 — the largest module by requirement count and by task count. Twenty tasks, three done and two partial. Most of what is here is still played by dashboard/sim.go, a 1400 ms ticker that moves desks through states and emits catalog events without ever calling a model.

M4.1 — The scheduler (T-048–T-049)

D-1 asked for something stronger than a working scheduler: a pure function of the graph, such that two replicas computing it independently reach the same answer. That property is the reason the orchestrator can hold no authoritative state, and it is far cheaper to build in than to add later — which is why it was built in on 2026-08-22 rather than retrofitted.

dashboard/scheduler.go takes a SchedulerInput and returns a ScheduleDecision. The clock arrives as a field, read once by the impure shell on the store and passed down as a value; every collection is sorted on entry, because two replicas reading the same ArcadeDB are promised nothing about row order across buckets and a scheduler that inherited slice order would agree in a naive test and disagree in production. The purity is enforced structurally rather than behaviourally: the file's import list is closed at fmt, sort and strings, and an AST test refuses a fourth import or any declaration with a receiver. A clock read that happened to return the same value twice would pass every behavioural test there is.

The decision returns both halves. Ready is what a runner would start — with the agent and the workspace named, so two tasks cannot be handed the same seat by a decision that never recorded making one. Blocked is the other half, and it is §7.4's requirement rather than a convenience: five reasons, no more and no fewer, reported by precedence rather than by whichever check ran first. A cycle is a dependency block naming its members, not a sixth reason. M10.3 does not exist, so the budget zone is always normal — the branch is covered by a test that constructs a throttled input directly, because a reason with no producer rots before its module arrives. T-109 renders these; nothing dispatches from them yet, which is M4.2.

M4.2 — Runner, lease and reconciliation (T-050–T-053)

Work runs in detached processes that survive the orchestrator (D-2), each holding an exclusive workspace lease with an expiry and a heartbeat (D-3). On boot, every task claiming to be dispatched or running is reconciled against its lease and heartbeat and is adopted, requeued or orphaned (D-4). This is build-order step 5 and its own acceptance test: kill the orchestrator mid-task and the work survives.

The lease landed first, on 2026-08-22, because the other three are unsafe without it. dashboard/lease.go holds it as an O_EXCL lockfile inside the workspace rather than as a row: the thing being protected is a directory, and the only primitive that excludes atomically at that granularity between processes on one host is the filesystem. The record stays in the graph — Task.leaseUntil and Task.lastHeartbeatAt are what boot reconciliation reads — but the enforcement has to survive the orchestrator, which is what D-2 is for, and a file carrying its own expiry explains itself to a process that was not running when the lease was taken. This does not put authoritative state in process memory, so BR-01 is intact: it is state on the resource.

One decision fell out of it and is logged as D-053: an expired lease is never taken by the acquirer. It reads like an oversight — the expiry passed, so surely the next runner may have it — but an expiry says the supervisor stopped renewing, and the supervisor is not the thing editing the repository. Taking it would start the second run D-3 exists to prevent. Clearing one is BreakLease, which only T-053 may call and only on the branch that kills first. The same decision fixes the four intervals and separates the heartbeat's write from the Heartbeat event, so a twenty-minute run adds five pills to the timeline rather than forty.

M4.3 — The attempt record (T-054–T-056)

Task and TaskRun are separate records so per-attempt evidence survives a retry (BR-22), and the exact context slice sent to a model is frozen and stored per attempt with USES_CONTEXT hanging off the slice rather than the task (BR-23) — because the slice differs per attempt. GET /tasks/{id}/context already exists and answers in HTML or JSON; it computes a slice live instead of returning the frozen one, which is the difference between a demonstration and an audit trail.

M4.4 — The model gateway (T-057–T-060)

Partly built, on 2026-08-22. T-057 is 🟡 rather than ✅ and the distinction is the honest one: dashboard/adapter_cli.go exists, spawns a pinned tool in its own process group with the workspace as its working directory, refuses the boot when the version drifts, and reads its outcome from the handoff document — but no scheduler calls it and no real provider has ever been invoked. It is exercised against a stand-in tool in dashboard/testdata/fakecli, which exists to reproduce one measured behaviour: D-050's finding that a task the model could not do exits 0, byte-identical to one it did. The three obligations D-049, D-050 and D-051 created are discharged: the boot smoke test runs, the exit code classifies only crash-versus-ran, and cost comes from the tool's own report as measured. What is missing is everything M4.2 owns — a lease, a heartbeat, and a scheduler to decide when. T-058, T-059 and T-060 are untouched.

Two interchangeable adapters, a provider's command-line tool spawned as a detached subprocess and a direct HTTP call, selected by one deployment-wide setting in the master configuration (§7.6.1, D-12). Never a per-task choice. BR-33 is the rule that keeps them interchangeable: the mode may be recorded on the attempt as TaskRun.invocation and no component above the adapter may branch on it.

M4.5 — Packet and handoff (T-061–T-064)

The frozen slice is materialised as a task packet of files in the leased workspace, and the packet — not a prompt string — is what the adapter hands over (D-8). Every invocation must produce a handoff document at a declared path in a declared shape; a missing or unparseable one is a failed attempt with the signature handoff-missing, never a silent pass (D-9, BR-30). The BRD is explicit that this is the load-bearing assumption of the whole CLI approach, which is why the validator is a task and not a nicety.

M4.6 — Cost basis (T-065–T-066)

BR-31: every cost figure carries its basis, measured or estimated, and the distinction survives every aggregation. CLI mode usually reports nothing, so a flat subscription produces estimates and an API call produces measurements — mixing them silently would make every budget number meaningless, which is why M10 depends on this sub-module.

M4.7 — Retiring the simulator (T-067)

dashboard/sim.go ends with its own deletion instruction: when the scheduler and the runner are real, this file is deleted and nothing else changes. That claim is worth testing rather than trusting — every field the simulator mutates is meant to be a field the Task/TaskRun/Review vertices carry.

M5 · Review, scoring & retry

Domain E, and the one domain with no requirement IDs — §8.5 specifies it as a formula, a five-row score-band table and six guard limits. Thirteen tasks, three partial. The BRD calls it the most dangerous loop in the system: every path through it must terminate and every termination must record a reason code.

M5.1 — The score (T-068–T-069)

final = 0.45·correctness + 0.20·completeness + 0.15·safety + 0.10·quality + 0.10·efficiency (BR-13). The weights are already in dashboard/fixtures.go and applied by sim.go, over invented inputs. The real work is the first term: correctness from tests that actually ran, rule checks that actually evaluated, and a reviewer verdict against the acceptance criteria.

M5.2 — The safety veto (T-070–T-071)

BR-14 makes safety a veto evaluated before anything else: below 60 the work stops regardless of the total, emits SafetyVeto and goes to a human queue. The event name is declared and never written.

M5.3 — Score bands (T-072–T-073)

85–100 accept; 70–84 accept and spawn a cleanup task; 50–69 iterate with a widened context slice at the same tier; 30–49 escalate a tier and re-run; 0–29 stop and call a design review. sim.go review() already implements this shape, which is why the sub-module is 🟡 — what it lacks is a real cleanup task and a slice that actually widens.

M5.4 — The failure signature (T-074–T-075)

Hash the normalised error — failing test name, error class, offending file — and compare across attempts. A changed signature means progress, so retry. An identical signature twice means the approach is wrong, and escalating a tier would reproduce the same wrong answer more expensively, so it routes to a design review instead (BR-16). This is what separates an intelligent retry from a superstitious one.

M5.5 — The six guards (T-076–T-079)

BR-17 makes all six hard: 3 retries, 2 escalations, 2 identical signatures, a capped exponential cooldown, per-workflow and per-tenant budget caps, and human intervention at two escalations or any safety veto. Exactly one runs today — store_mem.go refuses a fourth retry, and TestRetryGuardExhausts covers it. GuardExhausted is declared and never emitted.

M5.6 — Termination (T-080)

BR-18: every termination records a reason code, and a silent stop is a defect. This is also the acceptance condition for the unsatisfiable-task test, which is registered in the QA plan as a forward spec and blocked on this module.

M8 · Replay & audit

Domain H, requirements H-1…H-5. Six tasks, five done and one partial. The mechanism underneath the operator-facing half landed with M0.3: replay folds the event stream rather than reading back a stored floor, which is what BR-21 has always required and what the prototype's snapshots were standing in for.

M8.1 — The fold (T-097–T-098)

Done, on 2026-08-17. State at any past moment is a fold over the event stream from the nearest snapshot forward (H-1), through a reducer that is pure, total and order-stable, skipping unknown event types rather than failing on them (H-2). The reducer is dashboard/fold.go, built in M0.3 and proven here: this is where the fold test lives, which is one of the three acceptance tests BRD §4.1 names and the first of them ever to run.

Fold-from-genesis and fold-from-nearest-snapshot are compared at every rung of the snapshot ladder and at moments between the rungs, because between is where a broken ladder hides: a snapshot only ever asked for its own sequence is never asked to be folded forward from. Each of the three reducer properties has its own case — an invented event type interleaved through the whole stream must leave the floor unchanged, the same stream shuffled must fold to the same floor, and folding twice must give one answer.

M8.2 — Read-only by construction (T-099–T-100)

Done, on 2026-08-17. BR-20 says replay is routed through a read-only store handle and never a flag, and the architecture document gives the reason in the same breath: a flag will eventually be forgotten and will overwrite live state with a historical one. MemStore had exactly that flag.

readOnly in dashboard/store.go is the handle. It wraps a Store and refuses every mutation with one sentence, passing reads — including Replay and Focus, since moving the cursor and following it are what looking at the past consists of — straight through. Handlers reach for it through server.mut(), which picks the narrowed handle whenever the floor is parked in the past, so a mutating route added later is protected by calling what its neighbours call rather than by remembering a rule. This is the one change dashboard/store.go has taken since it was written to say this file does not change; a read-only handle is a thing the seam has to be able to express.

T-100 demotes snapshots to an optimisation, and the test says so by deleting all of them and demanding the identical floor. If that test ever needs the ladder to pass, the ladder has become the record and the event stream has stopped being it.

M8.3 — Scopes (T-101)

H-4 asks for four replay scopes: workflow, task, meeting, and a comparison between two runs of the same task on different models. /replay/{workflow} serves the first and is the reason this is 🟡; the comparison scope is the one that needs TaskRun from M4.3 to exist first. This is now the only unfinished task in the module.

M8.4 — The timeline (T-102)

H-5 is done: the operator timeline with a replay scrub and speed control, in dashboard/handlers_floor.go and templates/timeline.html, with TestReplayFreezesTheFloor and TestTheEventStreamIsUnboundedAndKeepsGenesis behind it. A pill addresses its moment by event seq rather than by position, so a link stays pointed at the moment the operator clicked however much the stream grows behind it.

M10 · Tenancy, capacity & cost control

Domain J, requirements J-1…J-13. Twelve tasks, none started. Tenancy is a database boundary first and a property second, and the budget guard is the reason this module blocks the first run in API mode.

M10.1 — The boundary (T-112–T-114)

One database per tenant is the default recommendation (J-1, BR-26), enforced at the API gateway and never only further down (J-2). Today the tenant is a cookie label and store_mem.go hardcodes the string loop-eng into the stat strip. D-042 settles the strategy at scale by refusing to pick one: all three sit behind a repository interface and the choice becomes deployment configuration, so what this milestone owes is the interface, not a strategy — with database-per-tenant as the default it implements first, and nothing above the repository layer knowing which is in use.

M10.2 — Quota, accounting and retention (T-115–T-118)

Tenant carries plan, maxConcurrentTasks and budgetCapUsd, where plan names a local quota profile and not a billing tier — D-032 withdrew self-service billing entirely, and J-7 is struck in the BRD rather than deleted so the withdrawal stays visible. Retention is per type (J-6): events full-fidelity for 90 days then archived with the fold checkpoint kept, samples raw for 14 days.

M10.3 — The budget guard (T-119–T-123)

Three zones rather than one limit (§8.10.1, D-037): normal, throttled where dispatch pauses and work defers, and exhausted where dispatch is refused. Spend is paced across the period, so the ceiling in force at any moment is the fraction of the period elapsed — a month's budget cannot be spent in an afternoon. Two rules make deferral safe: a deferred task keeps its place in the graph and consumes no retry, no escalation and no failure signature (BR-34), and reaching the hard cap refuses to dispatch but never kills a run already in flight, because that forfeits money already spent (BR-35).

M11 · Data protection, egress & residency

Domain L, requirements L-1…L-11. Nine tasks, two done. L-1 and L-10 are already answered as decisions (D-034) and need no code, so they are not tasks here. Everything else is, and BR-32 puts the core of it before the first real model call.

M11.1 — Inventory and provider profiles (T-124–T-125)

The egress inventory in §8.12.1 ships as product documentation and staying accurate is a release obligation, not a best effort (L-2). Each configured provider carries a data-handling profile the operator fills in: who the provider is, whether prompts are retained, and for how long (L-3).

M11.2 — The pre-dispatch pass (T-126–T-128)

Done, on 2026-08-22 — T-126 and T-127. dashboard/egress.go is a pure function of the packet and the policy: ten detectors across secrets, credentials and credential-bearing filenames, path allow and deny lists, a per-file and a whole-slice byte limit, and L-6's no-egress check. It runs on every dispatch, and the gate is a type rather than a call order — an adapter's Dispatch takes a Cleared, and the pass is the only thing that returns one, so skipping it does not compile. The honest limit is written down beside it: this is one Go package, so the type stops a caller forgetting rather than a caller deciding, and the deliberate version is caught by a test that walks the package's syntax tree. One line is worth reading twice: a finding records the file and the byte offset and never the matched text. The refusal becomes an append-only event rendered into a browser, so a payload carrying the credential would write it permanently into the record whose purpose is to prove it never left. T-128's product-level no-egress mode is still ❌ — the mechanism exists as a policy field, but nothing lets an operator set it per product.

Landing this needed one thing nobody had planned for: a caller. The events L-5 requires cannot be emitted by sim.go, because dashboard/events.go calls that inventing evidence. So a thin operator-triggered POST /tasks/{id}/dispatch landed with it, with a Dispatch button in the inspector — no scheduler, no lease, no heartbeat. It also forced a correction to the state machine: BR-32 makes idle → blocked legal, which dashboard/state_test.go had asserted was impossible with the reason "nothing is running, so nothing can be blocked". A refused dispatch is exactly that counter-example, and the row was inverted rather than deleted.

BR-32 is unambiguous: nothing reaches a model provider without passing the egress check first, and a detection refuses the dispatch rather than reporting the leak afterwards. Secret and credential detection, path allowlists and denials. Redactions and refusals are events — ContextRedacted and a refused dispatch with its reason — and appear on the timeline (L-5). L-6 adds a no-egress mode at product level for locally-hosted models only.

M11.3 — Deletion (T-129–T-130)

Deleting a tenant, product or run destroys the referent of every EXTERNAL payload and object-storage blob (L-7) and produces a certificate saying what was deleted, when, by whom, and what deliberately survived (L-8) — the event stream being append-only, something always does.

M11.4 — Transport and statement (T-131–T-132)

Encryption in transit for every hop the operator does not physically own, with a documented at-rest posture (L-9), and a data-handling statement template the operator completes and hands to their own stakeholders (L-11) — their regulator is not ours.

M12 · Non-functional proofs

The six properties of §8.13, each stated with how it is proven. Six tasks, one done and one partial. This module is not built so much as demonstrated: every row here is a test that cannot be written until the module it depends on exists, which is why the first of them landed the same day M0.3 did.

M12.1 — Depends on the event store (T-133–T-135)

Determinism is done, on 2026-08-17. It is proven by folding from genesis and requiring the same state every time, and the reducer M0.3 was waiting on now exists: the same stream folds to one answer, an unknown event type does not change it, and the order the events arrive in does not either. Auditability is proven when GET /tasks/{id}/context matches what the model actually received — which needs M4.3's frozen slice. Recoverability is proven by killing the orchestrator mid-run and losing nothing, which needs M4.2.

M12.2 — Isolation, explicability, termination (T-136–T-138)

Isolation means a tenant cannot see another tenant's data even if a query forgets to filter — database-per-tenant first, tenantId as the second line. Explicability is the one partial: every mutation already returns a new state or a rejection reason rather than a bare 200, and TestNoTemplateErrorEscapesAsSuccess guards the rendering half of it, but the states being explained are simulated. Termination means no loop runs forever and no stop is silent, which is M5.5 and M5.6 seen from the outside.

M13.2 — Deploy provenance (T-141)

deploy/STACKS.md listed it under its own known gaps: both stacks built from this working tree, so production tracked whatever happened to be checked out rather than a tag. The --allow-dirty refusal narrowed the blast radius and did not close it — a clean tree is not a named tree, and what is running in prod? had no answer a month later.

Closed 2026-08-20. rebuild-restart.sh --tag <ref> checks the ref out into a detached worktree and re-runs itself inside it, so the invariant check, the test gate and docker compose build all read the tagged tree; prod refuses without it, and --from-tree is the deliberate escape hatch. It needs no path rewriting because both compose files address their build contexts relatively. Two details earned their comments: the tier's env files are symlinked into the worktree, because they are secrets that exist in no commit and compose would otherwise stop at env file not found; and --tag is not forwarded to the inner run, whose script is the tag's own copy of this file and may predate the flag — which is exactly what lets --tag build a ref older than the feature itself.
