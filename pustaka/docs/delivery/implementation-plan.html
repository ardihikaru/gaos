Delivery

Implementation plan

Every business requirement in the BRD, mapped against the code that is actually committed, and broken into fourteen modules of work you can pick up one at a time. One hundred and forty-one tasks: sixteen done, fifteen standing on fixtures, one hundred and ten not started.

How to read this

The BRD says what GAOS must do and marks each requirement Designed, Built, Decided or Open. That is the right vocabulary for a business document and the wrong one for a Monday morning: the statuses are spread across twelve tables, a requirement can be one sentence or a whole subsystem, and nothing on the page says which file the work lands in. This page is the other half — the same requirements, cut into modules and sub-modules, each task small enough to finish and pointed at the code.

FlagWhat it means
✅Running in this repository today, and the row names the file. Nothing is flagged done that cannot be pointed at.
🟡Exists, but only over fixtures or the simulator. The shape is right and the requirement is not met.
❌Not started.

The middle flag is not padding. The BRD itself marks A-7, C-6, F-5 and H-5 as Built (against fixtures), and dashboard/sim.go implements the whole of Domain E's scoring policy without ever calling a model. Forcing those into ✅ or ❌ would make this page lie in one direction or the other.

What ✅ does not mean

Sixteen tasks are done. Ten of them are the operator surface and five are the schema, which now exists as applied DDL rather than as a document — but nothing yet reads or writes it. GAOS still renders a floor, an inspector, a timeline and a back office over an in-memory store seeded from fixtures; there is still no scheduler, no runner and no model call anywhere in the repository. That inversion is deliberate and logged as D-019 — it is also why the remaining order matters.

Sequencing

The build order is not ours to invent: it is prescribed in ten steps by the architecture document and logged as D-018, each step testable before the next one exists. D-019 already inverted it once by building step 9 first, knowingly, which is exactly why the remaining steps must not be reordered again.

M0 · Foundations — schema, event store, state machine

Build-order steps 1 and 2, and the module every other module is waiting on. Eighteen tasks, six done. Two invariants live here and nowhere else: state lives in the graph (BR-01) and every change emits an event (BR-02). Neither holds today, because there is no graph — MemStore keeps the whole system in RAM and a restart returns the fixtures.

M0.1 — Schema and DDL (T-001–T-005)

Done, on 2026-08-16. The data model specifies 25 vertex types, 3 document types and 32 edge types with their indexes and retention, and all of it now lives as ten runnable files under dashboard/schema/, applied by the idempotent deploy/schema/apply.sh — 314 statements, run against ArcadeDB 26.7.2, the version pinned by D-043. Until this ran, the schema was a document rather than a database, which is what R-03 was about.

The model document told itself to verify the dialect before relying on it, and it was right to: 53 of the 314 statements failed the first time. Two amendments came out of that, both logged and both marked in place on the model document. D-045 is dialect — UNIQUE is not a CREATE EDGE TYPE modifier on this version, and edge uniqueness is carried by an index on (`@out`, `@in`) instead. D-046 is not: partitioned('tenantId') requires a unique tenantId, which permits one Task per tenant, so it is withdrawn. That one is an error in the committed model rather than a difference between versions, and it is the reason this task was worth doing before anything was built on top of it. dashboard/schema/RECONCILIATION.md records both, with the commands to reproduce the measurement.

Three rules constrain the DDL rather than the code: one edge type per relationship with no generic edge (BR-24), heavy payloads stored EXTERNAL so the scheduler never traverses them (BR-25), and tenantId declared and indexed whatever the tenancy strategy turns out to be (BR-26).

M0.2 — The store seam (T-006–T-008)

dashboard/store.go was written to be the seam and says so: store_arcade.go in the next one speaks the ArcadeDB HTTP API and THIS FILE DOES NOT CHANGE. That file does not exist yet. dashboard/arcade.go is a reachability probe and nothing more — it calls /api/v1/ready for /healthz and issues no queries. Keeping MemStore afterwards is deliberate: it is the fast test double, and running both implementations against one interface suite is what stops the seam from rotting.

M0.3 — Event store and the fold (T-009–T-013)

Today an Event carries a deep copy of the entire floor, and the stream is a ring buffer capped at 160 entries with the replay cursor shifted when the window moves. That is a screen recording, not an event store: it satisfies the UI and none of H-1, H-2, BR-04 or BR-21. The work is to make the stream append-only and unbounded, reference business ids rather than physical RIDs (BR-03), and replace the snapshot with a pure, total, order-stable reducer that skips unknown event types instead of failing on them.

M0.4 — Closing the catalog (T-014–T-016)

The catalog is closed by BR-05 and encoded as Go constants so a typo is a compile error (D-020). Thirteen of its names are declared and marked // pass 2 — ReadinessDropped, RunStarted, Heartbeat, RunExited, TaskOrphaned, SafetyVeto, GuardExhausted, ApprovalRejected and five more — and no code path writes them. The four UI-lifecycle names are correctly fenced into their own block already, which is the one task in this sub-module that is done. Because the catalog is closed, the four new names the milestone list is waiting on must land in the data model, dashboard/events.go and the fold together, or not at all.

M0.5 — The task state machine (T-017–T-018)

Build-order step 2, and the reason BR-06 is only half-satisfied. dashboard/store.go already returns a Result or a rejection reason through reject(), so no route answers a bare 200 — the shape is right. What is missing is the machine behind it: transitions are enforced by the code path that happens to run, not by a boundary that refuses an illegal one.

M1 · Product master & knowledge ingestion

Domain A, requirements A-1…A-7. Eleven tasks, one done and four partial — the highest partial count of any module, because the back office is complete and everything under it is memory. The record is the thing agents read instead of a prompt, so nothing above this module means much until the record survives a restart.

M1.1 — The record (T-019–T-022)

dashboard/model.go already carries the right shapes: Master with a BRD of problem, goals, scope, out-of-scope, rules and metrics; Story in as / want / so form with acceptance criteria; Diagram with a renderer in dashboard/seq.go. Four requirements are therefore 🟡 rather than ❌ — the structure is designed and demonstrated, and none of it is scoped to a tenant or written anywhere.

M1.2 — Repository indexing (T-023–T-025)

A-5 is untouched. Nothing indexes a linked repository into files and functions, nothing identifies an entrypoint, and impact analysis from a diff — which the architecture describes as a traversal — has no graph to traverse. This is the requirement that makes the difference between an agent that reads a brief and an agent that reads the code the brief is about.

M1.3 — Injection (T-026–T-027)

Inject() is the sharpest gap in the repository and is honest about it in its own comment: it emits the event, reports the projection, and the write itself lands with store_arcade.go. The back office therefore reports a vertex and edge count that no database ever received. A-6 also requires the rescore to happen in the same operation, for the reason the BRD gives: a record that is edited but not injected is a lie the planner will believe.

M1.4 — The surface (T-028–T-029)

A-7 is done. dashboard/handlers_bo.go and templates/backoffice.html give the record author product CRUD, the BRD pane, stories, diagrams, knowledge, agents and the readiness checklist. The remaining task is the one the module is named after: make what it writes survive.

M2 · Readiness gating

Domain B, requirements B-1…B-5, plus BR-07…BR-10. Nine tasks, none done. This is the module that turns is the brief good enough? into a number, and it is build-order step 3.

M2.1 — The rubric (T-030–T-031)

The rubric is 100 points across twelve machine-checkable signals, specified in full in §8.2 — problem statement 8, goals 8, domain rules 12, out of scope 6, stories 10, criteria coverage 12, behaviour diagram 10, data model 8, repository linked 8, decisions 8, success metrics 5, verification strategy 5. What ships is seven booleans, and dashboard/model.go marks the real rubric as pass 2 in a comment. Scoring on a schedule additionally needs a scheduler, which is M4.

M2.2 — Bands and refusal (T-032–T-034)

Four bands govern autonomy: Insufficient 0–44, Minimum 45–69, Working 70–89, Complete 90–100. Two of them are business rules rather than preferences — below 45 the planner refuses and returns the missing list (BR-07), and band gates are mandatory rather than advisory, so Minimum caps the model at mid tier and forbids auto-merge (BR-08). None of this exists; the planner plans whatever it is given.

M2.3 — Drift (T-035–T-036)

effective = raw − drift_penalty, with the penalty capped at 25 (BR-09) and driven by three inputs: months since the last review, boundary files changed since injection, and open contradictions. This is the answer to a record scored 92 six months ago that describes a codebase which no longer exists.

M2.4 — Band crossing (T-037)

Crossing a boundary downward is an event, not a silent recalculation: ReadinessDropped is emitted and the stricter band's gates apply immediately (B-5, BR-10). The event name exists in the catalog and is never written. Autonomy must be withdrawn as loudly as it was granted.

M2.5 — Publication (T-038)

B-3 is the one partial here: /products/{id}/readiness answers, and the checklist renders in the back office, but from the seven-boolean stand-in rather than the rubric. A refusal that does not say what is missing is a dead end, so the missing list is part of this task and not a follow-up.

M3 · Planning

Domain C, requirements C-1…C-6. Nine tasks, one done and two partial. Build-order step 4 — one goal must yield an acyclic DAG with roles and dependencies.

M3.1 — Workflow shape (T-039–T-040)

WorkflowDraft carries an objective and a scope, so C-1 is partly there. The gate policy is not: the wizard never asks for one, which means every workflow created today has no answer to the question M6 is built around.

M3.2 — The task graph (T-041–T-042)

PlanWorkflow is already a pure function, which is the property that matters and the one that is hardest to retrofit. What it produces is a fixed shape rather than an expansion of the objective, with no real dependencies and no cycle check — so C-2 is 🟡 on the strength of its signature, not its output.

M3.3 — Atomicity (T-043)

BR-11 makes atomicity a rejection rather than a guideline: one concern, one workspace, at least one acceptance criterion, or the task does not enter the graph. The BRD's reason is worth keeping in view — no criterion means no verdict, and the reviewer will invent one and it will drift.

M3.4 — Routing (T-044–T-045)

BR-12 fixes the order: capability is a hard filter, risk overrides cost, and cost decides only between options that are already acceptable. Never cost first. C-5 adds the constraint that makes it non-trivial — senior roles such as architect and security have explicit capacity across all products, not per workflow.

M3.5 — The wizard (T-046–T-047)

C-6 is done: dashboard/handlers_cw.go runs three steps with a plan preview and moves coverage on creation. The draft round-trips through hidden form fields with no server session, which is a defensible choice for a prototype and a data-loss bug once a workflow is worth keeping.

M4 · Execution

Domain D, requirements D-1…D-13 — the largest module by requirement count and by task count. Twenty tasks, none done, none partial. Everything here is currently played by dashboard/sim.go, a 1400 ms ticker that moves desks through states and emits catalog events without ever calling a model.

M4.1 — The scheduler (T-048–T-049)

D-1 asks for something stronger than a working scheduler: a pure function of the graph, such that two replicas computing it independently reach the same answer. That property is the reason the orchestrator can hold no authoritative state, and it is far cheaper to build in than to add later.

M4.2 — Runner, lease and reconciliation (T-050–T-053)

Work runs in detached processes that survive the orchestrator (D-2), each holding an exclusive workspace lease with an expiry and a heartbeat (D-3). On boot, every task claiming to be dispatched or running is reconciled against its lease and heartbeat and is adopted, requeued or orphaned (D-4). This is build-order step 5 and its own acceptance test: kill the orchestrator mid-task and the work survives.

M4.3 — The attempt record (T-054–T-056)

Task and TaskRun are separate records so per-attempt evidence survives a retry (BR-22), and the exact context slice sent to a model is frozen and stored per attempt with USES_CONTEXT hanging off the slice rather than the task (BR-23) — because the slice differs per attempt. GET /tasks/{id}/context already exists and answers in HTML or JSON; it computes a slice live instead of returning the frozen one, which is the difference between a demonstration and an audit trail.

M4.4 — The model gateway (T-057–T-060)

Two interchangeable adapters, a provider's command-line tool spawned as a detached subprocess and a direct HTTP call, selected by one deployment-wide setting in the master configuration (§7.6.1, D-12). Never a per-task choice. BR-33 is the rule that keeps them interchangeable: the mode may be recorded on the attempt as TaskRun.invocation and no component above the adapter may branch on it.

M4.5 — Packet and handoff (T-061–T-064)

The frozen slice is materialised as a task packet of files in the leased workspace, and the packet — not a prompt string — is what the adapter hands over (D-8). Every invocation must produce a handoff document at a declared path in a declared shape; a missing or unparseable one is a failed attempt with the signature handoff-missing, never a silent pass (D-9, BR-30). The BRD is explicit that this is the load-bearing assumption of the whole CLI approach, which is why the validator is a task and not a nicety.

M4.6 — Cost basis (T-065–T-066)

BR-31: every cost figure carries its basis, measured or estimated, and the distinction survives every aggregation. CLI mode usually reports nothing, so a flat subscription produces estimates and an API call produces measurements — mixing them silently would make every budget number meaningless, which is why M10 depends on this sub-module.

M4.7 — Retiring the simulator (T-067)

dashboard/sim.go ends with its own deletion instruction: when the scheduler and the runner are real, this file is deleted and nothing else changes. That claim is worth testing rather than trusting — every field the simulator mutates is meant to be a field the Task/TaskRun/Review vertices carry.

M5 · Review, scoring & retry

Domain E, and the one domain with no requirement IDs — §8.5 specifies it as a formula, a five-row score-band table and six guard limits. Thirteen tasks, three partial. The BRD calls it the most dangerous loop in the system: every path through it must terminate and every termination must record a reason code.

M5.1 — The score (T-068–T-069)

final = 0.45·correctness + 0.20·completeness + 0.15·safety + 0.10·quality + 0.10·efficiency (BR-13). The weights are already in dashboard/fixtures.go and applied by sim.go, over invented inputs. The real work is the first term: correctness from tests that actually ran, rule checks that actually evaluated, and a reviewer verdict against the acceptance criteria.

M5.2 — The safety veto (T-070–T-071)

BR-14 makes safety a veto evaluated before anything else: below 60 the work stops regardless of the total, emits SafetyVeto and goes to a human queue. The event name is declared and never written.

M5.3 — Score bands (T-072–T-073)

85–100 accept; 70–84 accept and spawn a cleanup task; 50–69 iterate with a widened context slice at the same tier; 30–49 escalate a tier and re-run; 0–29 stop and call a design review. sim.go review() already implements this shape, which is why the sub-module is 🟡 — what it lacks is a real cleanup task and a slice that actually widens.

M5.4 — The failure signature (T-074–T-075)

Hash the normalised error — failing test name, error class, offending file — and compare across attempts. A changed signature means progress, so retry. An identical signature twice means the approach is wrong, and escalating a tier would reproduce the same wrong answer more expensively, so it routes to a design review instead (BR-16). This is what separates an intelligent retry from a superstitious one.

M5.5 — The six guards (T-076–T-079)

BR-17 makes all six hard: 3 retries, 2 escalations, 2 identical signatures, a capped exponential cooldown, per-workflow and per-tenant budget caps, and human intervention at two escalations or any safety veto. Exactly one runs today — store_mem.go refuses a fourth retry, and TestRetryGuardExhausts covers it. GuardExhausted is declared and never emitted.

M5.6 — Termination (T-080)

BR-18: every termination records a reason code, and a silent stop is a defect. This is also the acceptance condition for the unsatisfiable-task test, which is registered in the QA plan as a forward spec and blocked on this module.

M6 · Gates & approvals

Domain F, requirements F-1…F-6. Nine tasks, one done. Build-order step 8, and the module that holds the only requirement in the whole BRD explicitly marked Not built rather than Designed.

M6.1 — Policy (T-081–T-082)

A gate policy is set per workflow at creation time (F-1), and three categories are gated at every readiness band including Complete: money arithmetic, authentication and schema changes (F-3). The first of these is also M3.1's missing wizard step.

M6.2 — Enforcement and record (T-083–T-085)

BR-19 is absolute: a gated task cannot merge through any path, the API included — not a UI check. Approval and rejection are recorded as vertices with a decider, a timestamp and a reason (F-4), which is also where ApprovalRejected finally gets written; ApprovalGranted and ApprovalRequested already are.

M6.3 — Operator controls (T-086)

F-5 is done. dashboard/handlers_floor.go serves approve, retry and cancel from the inspector, each with a real guard behind it — TestApproveRequiresAGate and TestCancelReleasesTheDesk cover the rejections.

M6.4 — Authentication (T-087–T-089)

F-6 is the BRD's only Not built, cross-referenced to risk R-02 and OQ-11. dashboard/handlers_bo.go states the position in a header comment: a cookie, no password comparison, no session store, and every back-office route checks the cookie so there is exactly one place to change. The login form ships working credentials as value= attributes, which must go with it. The shape to lift is next door — pustaka's HMAC-signed cookie, credential fingerprint and per-IP throttle with lockout, already covered by fifteen of its own tests.

M7 · Memory & learning

Domain G, requirements G-1…G-5. Seven tasks, one partial. Build-order step 10, last for a reason — and also the module the product's one success measurement depends on, since the second run needs fewer retries is only true if extraction works.

M7.1 — Writing back (T-090–T-092)

Every completed workflow writes Knowledge back to the product — lessons, decisions, failure patterns (G-1). Decisions are ADRs carried into every later prompt with supersession tracked (G-2), which is what DecisionSuperseded is reserved for. KnowledgeExtracted and DecisionRecorded are emitted today by the simulator, from a script.

M7.2 — Meetings (T-093–T-094)

G-3 makes a multi-agent meeting a first-class record: agenda, participants, proposals with confidence, and the decision it produced. The overlay renders all of that from meetingScript in dashboard/fixtures.go — a scripted design review — so the requirement is 🟡 on its surface and ❌ underneath. ProposalRecorded is declared and never written.

M7.3 — Recall and contradiction (T-095–T-096)

Knowledge is recalled during planning by tag and reuse count (G-4), which is what makes the second workflow plan faster than the first and what KnowledgeReused records. G-5 is the harder half: detecting a decision that conflicts with a requirement, or an acceptance criterion no test maps to.

M8 · Replay & audit

Domain H, requirements H-1…H-5. Six tasks, one done and one partial. The operator-facing half is finished and the mechanism underneath it is not — replay today reads stored snapshots, which is precisely what BR-21 forbids as a source of truth.

M8.1 — The fold (T-097–T-098)

State at any past moment is a fold over the event stream from the nearest snapshot forward (H-1), through a reducer that is pure, total and order-stable, skipping unknown event types rather than failing on them (H-2). No reducer exists; M0.3 is where it is built, and this is where it is proven — fold from genesis must match fold from snapshot on a real workflow.

M8.2 — Read-only by construction (T-099–T-100)

BR-20 says replay is routed through a read-only store handle and never a flag. MemStore has a replayAt field and checks it — the exact construction the rule names, chosen deliberately for the prototype and due to be replaced. The companion rule, BR-21, demotes snapshots to an optimisation.

M8.3 — Scopes (T-101)

H-4 asks for four replay scopes: workflow, task, meeting, and a comparison between two runs of the same task on different models. /replay/{workflow} serves the first and is the reason this is 🟡; the comparison scope is the one that needs TaskRun from M4.3 to exist first.

M8.4 — The timeline (T-102)

H-5 is done: the operator timeline with a replay scrub and speed control, in dashboard/handlers_floor.go and templates/timeline.html, with TestReplayFreezesTheFloor and TestEventsAreCappedAndTheReplayCursorFollows behind it.

M9 · Operator surface

Domain I, requirements I-1…I-7. Nine tasks, six done — the only module where that is true. Build-order step 9, built first, which the decision log records as a knowing inversion. What remains is one requirement and two pieces of infrastructure the surface is standing on.

M9.1 — The five views (T-103–T-107)

I-1…I-5 are all done and all covered: the floor with occupancy per room, the inspector with retries, escalations, cost and the score breakdown, the event timeline with scrub-to-replay, the design-review overlay, and the back office. TestEveryRouteAnswers walks 33 route and status cases across them, and TestNoZgotmplZ checks the style-attribute trap on seven surfaces.

M9.2 — The prohibition (T-108)

I-6 is architectural rather than a feature: the UI never invents state the graph does not have. It holds today — static/app.js handles theme, sheets, wizard picks and keyboard shortcuts and renders no markup at all — and it is listed as a task because it is the one that is easiest to break while doing everything else.

M9.3 — What the surface still owes (T-109–T-111)

I-7 requires the five blocking reasons for an idle desk to be displayed explicitly, including deferred — budget window with the time it resumes — which cannot be shown before M10.3 produces it. Two infrastructure items sit here too: store_mem.go's emit() was cut as the SSE seam and the broker was never built, so the floor polls every 1400 ms; and the embedded static assets are unfingerprinted, noted as pass 2 in main.go.

M10 · Tenancy, capacity & cost control

Domain J, requirements J-1…J-13. Twelve tasks, none started. Tenancy is a database boundary first and a property second, and the budget guard is the reason this module blocks the first run in API mode.

M10.1 — The boundary (T-112–T-114)

One database per tenant is the default recommendation (J-1, BR-26), enforced at the API gateway and never only further down (J-2). Today the tenant is a cookie label and store_mem.go hardcodes the string loop-eng into the stat strip. D-042 settles the strategy at scale by refusing to pick one: all three sit behind a repository interface and the choice becomes deployment configuration, so what this milestone owes is the interface, not a strategy — with database-per-tenant as the default it implements first, and nothing above the repository layer knowing which is in use.

M10.2 — Quota, accounting and retention (T-115–T-118)

Tenant carries plan, maxConcurrentTasks and budgetCapUsd, where plan names a local quota profile and not a billing tier — D-032 withdrew self-service billing entirely, and J-7 is struck in the BRD rather than deleted so the withdrawal stays visible. Retention is per type (J-6): events full-fidelity for 90 days then archived with the fold checkpoint kept, samples raw for 14 days.

M10.3 — The budget guard (T-119–T-123)

Three zones rather than one limit (§8.10.1, D-037): normal, throttled where dispatch pauses and work defers, and exhausted where dispatch is refused. Spend is paced across the period, so the ceiling in force at any moment is the fraction of the period elapsed — a month's budget cannot be spent in an afternoon. Two rules make deferral safe: a deferred task keeps its place in the graph and consumes no retry, no escalation and no failure signature (BR-34), and reaching the hard cap refuses to dispatch but never kills a run already in flight, because that forfeits money already spent (BR-35).

M11 · Data protection, egress & residency

Domain L, requirements L-1…L-11. Nine tasks, none started. L-1 and L-10 are already answered as decisions (D-034) and need no code, so they are not tasks here. Everything else is, and BR-32 puts the core of it before the first real model call.

M11.1 — Inventory and provider profiles (T-124–T-125)

The egress inventory in §8.12.1 ships as product documentation and staying accurate is a release obligation, not a best effort (L-2). Each configured provider carries a data-handling profile the operator fills in: who the provider is, whether prompts are retained, and for how long (L-3).

M11.2 — The pre-dispatch pass (T-126–T-128)

BR-32 is unambiguous: nothing reaches a model provider without passing the egress check first, and a detection refuses the dispatch rather than reporting the leak afterwards. Secret and credential detection, path allowlists and denials. Redactions and refusals are events — ContextRedacted and a refused dispatch with its reason — and appear on the timeline (L-5). L-6 adds a no-egress mode at product level for locally-hosted models only.

M11.3 — Deletion (T-129–T-130)

Deleting a tenant, product or run destroys the referent of every EXTERNAL payload and object-storage blob (L-7) and produces a certificate saying what was deleted, when, by whom, and what deliberately survived (L-8) — the event stream being append-only, something always does.

M11.4 — Transport and statement (T-131–T-132)

Encryption in transit for every hop the operator does not physically own, with a documented at-rest posture (L-9), and a data-handling statement template the operator completes and hands to their own stakeholders (L-11) — their regulator is not ours.

M12 · Non-functional proofs

The six properties of §8.13, each stated with how it is proven. Six tasks, one partial. This module is not built so much as demonstrated: every row here is a test that cannot be written until the module it depends on exists.

M12.1 — Depends on the event store (T-133–T-135)

Auditability is proven when GET /tasks/{id}/context matches what the model actually received — which needs M4.3's frozen slice. Recoverability is proven by killing the orchestrator mid-run and losing nothing, which needs M4.2. Determinism is proven by folding from genesis, which needs M0.3.

M12.2 — Isolation, explicability, termination (T-136–T-138)

Isolation means a tenant cannot see another tenant's data even if a query forgets to filter — database-per-tenant first, tenantId as the second line. Explicability is the one partial: every mutation already returns a new state or a rejection reason rather than a bare 200, and TestNoTemplateErrorEscapesAsSuccess guards the rendering half of it, but the states being explained are simulated. Termination means no loop runs forever and no stop is silent, which is M5.5 and M5.6 seen from the outside.

M13 · Repository hygiene

Three small items found while mapping the BRD against the code. None of them belongs to a domain, all of them are real, and all three are cheap enough to take on a day when nothing larger fits.

M13.1 — Two loose ends (T-139–T-140)

deploy/stacks/compose.dev.yaml, compose.prod.yaml and check-stacks.sh all cite test/stacks_test.go as the thing that asserts their invariants. That file does not exist; the assertions live in check-stacks.sh itself, and are registered as TC-001…TC-016 in the QA plan. Either write the file or correct the three references. The second item is a redistribution obligation already named in the BRD's milestone list: vendor the upstream licence texts for the fonts and the charting library beside the assets they cover.

M13.2 — Deploy provenance (T-141)

deploy/STACKS.md lists it under its own known gaps: both stacks build from this working tree, so production tracks whatever happens to be checked out rather than a tag. The --allow-dirty refusal on prod narrows the blast radius and does not close it.

What this page deliberately leaves out

Domain K — the commercial model — has no rows here. K-1…K-10 are business rulings, decided and logged as D-026…D-031, D-035 and D-038; they constrain what gets built without themselves being buildable. The one that is still open is a question, not a task: K-6's rate-card numbers wait on OQ-21. The FAQ is where those live.

Two more omissions, both intentional. J-7 — tenant self-service signup and billing — is withdrawn by D-032 and struck rather than deleted in the BRD, so it appears in neither the register nor M10. L-1 and L-10 are answered by D-034 as statements of posture — residency is the operator's own machines, and support engagements get no standing access — and need documentation rather than code, so M11 starts at L-2.

Finally, this page tracks work, not risk. The twelve-entry risk register and the nine unvalidated assumptions stay in BRD §11, where R-02 and R-10 can be argued about without a task ID implying someone has agreed to fix them.
