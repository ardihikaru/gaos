System architecture and operating flows

How a product goes from an empty record to agents working on it without supervision — and the five control loops that decide what runs, who runs it, when to stop, when the knowledge is good enough, and how any of it can be replayed.

01 What this document is

A companion to the Mission Control prototype: the same system described as something you can build, with each control loop drawn as a flowchart you can implement directly.

GAOS makes one bet: the graph is the primitive, not the prompt. Every other decision follows from it. Scheduling is a traversal. Context assembly is a traversal. Impact analysis is a traversal. Recovery is a fold over the event stream, not memory inside a process.

That bet only pays off if two invariants hold everywhere in the codebase:

State lives in the graph

The orchestrator holds no authoritative state. Kill it mid-run, start it again, and it rebuilds from vertices, edges, and events. Anything cached in memory must be reconstructible.

Every change emits an event

An event that was never written is a state change that never happened. Replay, audit, and recovery all read the same stream; there is no second path.

How to read the flowcharts. Rectangles are work, diamonds are decisions, rounded ends are entry and exit, and double-ruled boxes are durable states the system can sit in. Dashed amber edges are loops back into an earlier step — those are the ones that need termination conditions.

02 System architecture

Six layers. The three at the bottom are the ones that must be right first; the top three can be replaced without touching the model of the system.

LayerOwnsMust never
UI / Mission ControlProjection of graph state; operator actions.Invent state the graph does not have.
API gatewayAuth, tenant scoping, request validation, event fan-out.Let a tenant boundary be enforced further down only.
OrchestrationPlanner, scheduler, review engine, retry policy.Hold long-lived state in process memory.
ExecutionDetached processes, workspace leases, heartbeats.Die with the orchestrator.
Model gatewayAdapters, routing, cost and token accounting.Leak provider-specific shapes upward.
ArcadeDBGraph, documents, events, full-text, time series.Be bypassed by a side channel.

Why the orchestrator is stateless

The scheduler is a pure function of the graph: given the current vertices, edges, leases, and quotas, the set of READY tasks is fully determined. Two replicas computing it independently reach the same answer, so leader election protects against duplicate dispatch rather than against divergent state. Restart becomes uninteresting — the loop reads the graph and continues.

Recovery on boot
read tasks WHERE status IN (DISPATCHED, RUNNING)
  → for each, check lease and heartbeat
     → heartbeat fresh   : adopt, keep monitoring
     → lease expired     : mark orphaned, release workspace, requeue
     → process gone      : write TaskFailed(reason=orphaned), apply retry policy
then resume the normal scheduler loop

04 Setup → autonomous run

The full path: an operator fills in a product record, and the system reaches a point where it dispatches, reviews, and advances work without anyone watching.

Where autonomy actually begins

Autonomy is not a switch. It starts at the moment the scheduler can find a READY task without a human naming it, which requires four things to already be true: the dependency graph is acyclic, a capable agent exists for the role, a workspace lease can be acquired, and the readiness gate has passed. Miss any one and the floor looks idle for reasons nobody can explain — so surface all four in the UI as the blocking reason.

Readiness checkFixes what is missingScores the record, refuses below the floorreadiness_score, ReadinessEvaluated event

The failure mode to design against. A team fills in the record once, the system runs, and nobody ever updates the record again. Knowledge decays silently against a moving codebase. Section 07 handles this with a staleness rule — build it in from the start rather than adding it after the first bad plan.

05 Task split and role selection

Two separate decisions that are easy to conflate: how the goal breaks into tasks, and which agent and model each task gets. Keep them apart — the first is about the work, the second is about capacity and risk.

What makes a task atomic

A task is atomic when it can be verified on its own. That is a stricter test than "small". Three practical rules:

  • One concern. A task that changes a migration and a UI form has two failure modes and one score, so the score tells you nothing.
  • One workspace. If it needs two repositories checked out simultaneously, it is a workflow, not a task.
  • One acceptance criterion, at minimum. No criterion means no verdict; the reviewer will invent one and it will drift.

Ordering matters here. Selecting on cost first produces a system that routes a security-critical migration to the cheapest model because it happened to be free. Capability is a hard filter, risk overrides cost, and cost only decides between options that are already acceptable.

Task signalRequired roleModel floorExtra reviewer
Schema migration, money arithmetic, authBackend + SecurityTop tierAlways
Public API contract changeArchitectTop tierFrontend + QA notified
New feature within an existing boundaryBackend or FrontendMid tierQA
Test authoring, docs, mechanical refactorQA / anyLow tierNone
Retry after a failed attemptSame roleOne tier above the last attemptSenior on second retry
Role capacity is a scheduling constraint, not a suggestion. Senior roles — architect, security — are shared across every product. Model them with explicit capacity or they become the bottleneck that nobody sees until three workflows are all waiting on the same reviewer.

06 Scoring and the retry loop

The most dangerous loop in the system. Every path through it must terminate, and every termination must record a reason code.

The score

final = 0.45·correctness + 0.20·completeness + 0.15·safety + 0.10·quality + 0.10·efficiency

correctness   tests pass, rule checks, reviewer verdict against acceptance criteria
completeness  every criterion addressed; no silently skipped file
safety        no secret leakage, no unsafe command, no out-of-scope change
quality       complexity, duplication, coverage delta
efficiency    tokens, latency, retries consumed

Correctness dominates deliberately. A beautiful implementation of the wrong behaviour should score below an ugly implementation of the right one, because the second is cheap to improve and the first is expensive to discover.

Thresholds and what each one does

85–100Accept—Review, Knowledge if novel
70–84Accept, spawn a cleanup taskSameReview, follow-up Task
50–69Iterate with a widened context sliceSame tierRetryRequested + reason
30–49Escalate a tier and re-runOne aboveModelEscalated
0–29Stop; call a design reviewMeetingMeetingStarted, later Decision
safety < 60Stop immediately, regardless of total—SafetyVeto, human queue

Guardrails that make it terminate

GuardTypical valueWhat it prevents
max_retry_count3 per taskGrinding on the same approach forever.
max_escalation_count2 per taskWalking up the model tiers until the budget is gone.
same_failure_signature_limit2Retrying an identical failure and expecting a different result.

The failure signature is what makes retries intelligent rather than superstitious. Hash the normalised error — failing test name, error class, offending file — and compare across attempts. Signature changed means progress: the model fixed one thing and hit the next, so retry. Signature identical twice means the approach itself is wrong: escalating a tier will usually reproduce the same wrong answer more expensively, so route it to a design review instead.

Acceptance test for this loop: run a task that can never succeed — a criterion that contradicts a domain rule. A correct implementation stops within the guard limits, records a reason code, and leaves a human queue item. If it loops or fails silently, the loop is not finished.

07 Knowledge maturity: when is a product ready?

The question this section answers: is the information given to the agents enough yet? Make it a number, publish the rubric, and let the planner refuse below the floor.

The readiness rubric

One hundred points, checkable by a machine. Nothing here requires judgment, which is the point — a subjective bar gets argued away.

SignalptsPasses when
Problem statement8Present, ≥ 40 characters, names a real symptom.
Goals8At least one, phrased as an outcome not a task.
Domain rules12≥ 3 rules the reviewer can score against.
Out of scope6≥ 1 explicit exclusion.
Stories exist10≥ 1 story in as / want / so form.
Criteria coverage12Every must story has ≥ 2 acceptance criteria.
Behaviour diagram10≥ 1 sequence or flow showing the call order.
Data model8Entities and cardinality recorded.
Repository linked8Repo indexed; entrypoint identified.
Decisions8≥ 1 ADR carried into every prompt.
Success metrics5≥ 1 measurable outcome.
Verification strategy5How correctness is proven: tests, replay, manual check.

The four bands

0–44 · InsufficientPlanner refuses and returns the missing list. Nothing is dispatched.
45–69 · MinimumPlanning allowed. Every task gated, model capped mid tier, no auto-merge.
70–89 · WorkingNormal autonomy. Gates only on risk signals. Full model range.
90–100 · CompleteLow-risk tasks may merge without a human. Gates remain on money, auth, schema.

Minimum knowledge is the 45-point floor: enough for the planner to produce a defensible task graph, but not enough to trust unsupervised merges. Complete knowledge at 90 is not perfection — it means every question an agent routinely asks has a recorded answer, so the remaining risk is in the code rather than in the brief.

Staleness: why the score must decay

A record scored 92 six months ago describes a codebase that no longer exists. Recompute on a schedule and on repo events:

effective = raw − drift_penalty

drift_penalty = min(25, 4 × months_since_last_review
                      + 6 × (boundary_files_changed_since_injection > 0)
                      + 8 × (open_contradiction_count > 0))

contradiction = a Decision that conflicts with a Requirement,
                or an acceptance criterion no test maps to

Falling below a band boundary is an event, not a silent recalculation: emit ReadinessDropped, show it on the product card, and re-apply the stricter band's gates immediately.

Closing the loop. Every completed workflow writes Knowledge back to the product — lessons, decisions, failure patterns. That is what makes the second workflow on a product cheaper than the first, and it is the only mechanism that raises readiness without a human typing.

08 Replay

Replay is not a recording. It is the same fold over the event stream that recovery uses, stopped at an earlier timestamp — which is why building it forces the event model to be honest.

Why fold, not snapshot

Snapshots are an optimisation, never the source. If the UI can only replay from stored snapshots, then any moment between two snapshots is unreachable and any bug in snapshot writing is invisible. Fold from the nearest snapshot forward, and keep a periodic test that folds from genesis and compares — that test is what proves the event model is complete.

state(t) = fold(reduce, events.filter(e => e.ts <= t), snapshot_before(t) ?? empty)

reduce(state, event) must be:
  pure          same inputs, same output, no clock, no random
  total         an unknown event type is skipped, never fatal
  order-stable  ties broken by (ts, seq) so replays are identical
Replay scopeReconstructsPrimary use
WorkflowDesk state, task statuses, scores, gates at time t"Why did this ship in that shape?"
TaskPrompt, context slice, logs, diff, review findingsDebugging a single bad output
MeetingProposals, evidence, confidence curve, decisionUnderstanding why an ADR was chosen
ComparisonTwo runs of the same task, different modelsModel routing decisions backed by evidence
Guard the write path during replay. The reconstructed state must be structurally impossible to save. Route replay through a read-only store handle rather than a flag someone can forget to check — a flag will eventually be forgotten and will overwrite live state with a historical one.

10 Build order

Sequenced so each step is testable before the next one exists. Resist starting with the visual layer — it is the most rewarding to build and the least load-bearing.

#DeliverableDone when
1Graph schema + event storeEvery write emits an event; a fold reproduces current state exactly.
2Task state machineIllegal transitions are rejected at the boundary, not by convention.
3Product master + readiness scoringThe rubric runs on ingestion; below 45 the planner refuses with a list.
4Planner producing a static task graphOne goal yields an acyclic DAG with roles and dependencies.
5Runner with one detached processKill the orchestrator mid-task; the work survives and is re-adopted.
6Review, scoring, retry policyThe unsatisfiable-task test terminates with a reason code.
7Context assembly from the master recordGET /tasks/{id}/context matches what the model actually received.
8Approval gatesA gated task cannot merge, through the API or otherwise.
9Mission Control + replayFold-from-genesis matches fold-from-snapshot on a real workflow.
10Meetings, knowledge extraction, multi-repoThe second workflow on a product plans faster than the first.
The one measurement that tells you it works. Run the same objective on the same product twice, a week apart. If the second run needs fewer retries and less human intervention, knowledge is accumulating and the loop closes. If it does not, the extraction step is decorative and everything above it is expensive theatre.
