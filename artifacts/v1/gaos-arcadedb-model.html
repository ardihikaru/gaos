The ArcadeDB data model

Every screen in Mission Control and every flow in the architecture document reduces to the types below. This is the schema that makes those two documents executable: 25 vertex types, 3 document types, 32 edge types, the indexes that keep the scheduler fast, and the invariants that keep the graph honest.

01 Modelling principles

Six decisions that shape everything after them. Each one is reversible only at high cost, so they are worth arguing about now.

1 · Schema-full where it is read by machines, schema-less where it is written by humans

ArcadeDB supports schema-less, schema-full and hybrid operation, and inserting into a declared type accepts additional undeclared properties as long as no declared constraint is violated. Use that deliberately: Task, Event, and Review are strictly declared because the scheduler and the replay fold depend on their shape. Requirement and Artifact carry a declared spine plus free-form fields, because product records grow shapes nobody predicted.

2 · A business id alongside the RID

ArcadeDB gives every record a RID (#bucket:position) which is fast but physical. Every vertex also carries a id string that the API, the UI, and the event stream use. Events reference id, never RID — otherwise a restore into different buckets breaks the history.

3 · Edges carry meaning, not just connection

An edge type per relationship, not one generic REL with a type property. Traversal by edge type is an index-free adjacency lookup; filtering a generic edge by property is a scan of every neighbour. This is the single biggest performance decision in the model.

4 · The event stream is a first-class type, not a log file

Replay, recovery, and audit all read Event. It is append-only, never updated, partitioned by time, and it is the only type whose retention policy differs from everything else.

5 · Heavy payloads go outside the record

Properties are serialized inline in the same page as the vertex topology, so traversal-only queries pay for heavy properties in cache misses even when the projection never touches them; properties marked EXTERNAL are stored in a paired external bucket instead. Prompt bodies, diffs, and log blobs are exactly that problem: large, rarely projected, and sitting on vertices the scheduler traverses constantly. Mark them EXTERNAL or keep them as a reference to object storage.

6 · Tenancy is a database boundary first, a property second

ArcadeDB runs many databases in one server. One database per tenant gives a boundary that cannot be forgotten in a WHERE clause. Keep tenantId on every vertex anyway — it survives exports, makes cross-tenant analytics possible on purpose rather than by accident, and costs nothing.

Version check before you run this. The DDL below follows the ArcadeDB SQL dialect as documented at the time of writing. Constraint syntax and index options do move between releases, so run the schema against your target version in a scratch database first and adjust rather than assuming.

The runnable, reconciled schema now lives at dashboard/schema/ — ten files, applied by deploy/schema/apply.sh — and dashboard/schema/RECONCILIATION.md records every deviation, with the commands to reproduce the measurement. 08 DDL · events and telemetry

Append-only, time-partitioned, and the only types with their own retention policy.

07-events.sql
-- Event is a DOCUMENT type, not a vertex. It has no traversal role: it is
-- always read by (entityId, ts) or by (tenantId, seq). Making it a vertex
-- would add edge-list overhead to the highest-volume type in the database.

-- seq is a monotonic per-tenant counter. ts alone is not enough: two events
-- in the same millisecond must still fold in a deterministic order, which is
-- the "order-stable" requirement from architecture §08.

CREATE DOCUMENT TYPE Event IF NOT EXISTS BUCKETS 16;
CREATE PROPERTY Event.id         STRING   (mandatory true, notnull true);
CREATE PROPERTY Event.tenantId   STRING   (mandatory true, notnull true);
CREATE PROPERTY Event.seq        LONG     (mandatory true, notnull true, min 0);
CREATE PROPERTY Event.type       STRING   (mandatory true, notnull true);
CREATE PROPERTY Event.entityId   STRING   (mandatory true, notnull true);
CREATE PROPERTY Event.entityType STRING   (notnull true);
CREATE PROPERTY Event.actor      STRING;   -- agent id, user id, or 'system'
CREATE PROPERTY Event.payload    MAP;
CREATE PROPERTY Event.ts         DATETIME (mandatory true, notnull true);

13 Storage, tenancy and operations

The decisions that only matter once there is real data — which is exactly when they are expensive to change.

Buckets and partitioning

A type is stored in buckets, the number can be set with the BUCKETS option at creation time, and multiple buckets are recommended when working with multiple cores to improve insert concurrency. The high-volume types above declare 8 or 16 buckets for that reason. A partitioned bucket selection strategy is recommended when you have a unique id, and is set with ALTER TYPE.

Amended by D-046 — the three partitioned('tenantId') lines are withdrawn. This is the one deviation in the whole schema that is an error in this document rather than a dialect difference, and the citation directly above is where it shows: a partitioned bucket strategy is recommended when you have a unique id, and tenantId is the opposite of one — it is the discriminator every record of a tenant shares. ArcadeDB 26.7.2 requires a UNIQUE index on exactly (tenantId) before it will accept the strategy, and that index means one Task per tenant. Measured on 2026-08-16, not reasoned about: with the index in place, a second Task for tenant loop-eng fails with DuplicatedKeyException.

Nothing is lost that the model does not already provide elsewhere. BR-26 asks for tenantId declared and indexed whatever the tenancy strategy turns out to be, and §10 does that — Task (tenantId, id), TaskRun (tenantId, id) and Event (tenantId, seq) unique, plus Task (tenantId, status, priority). Isolation rests where D-042 puts it: database-per-tenant as the default, with tenantId as the second line rather than the first.

Migrations

Every DDL block on this page is idempotent, so the migration story is a numbered directory of files applied in order, with a SchemaVersion document recording the last applied number. Two rules make it survive:

  • Additive first. Add the new property, backfill it, switch readers, then drop the old one in a later release — never in the same one.
  • Never rename an edge type in place. Create the new type, copy edges, switch traversals, drop the old. A rename is invisible to running orchestrators until they crash on an unknown edge.

Backup and HA

Use ArcadeDB's backup command on a schedule, and treat the event stream as the second recovery path: a restore that is missing the last few minutes can be rolled forward by replaying events from an external broker if you publish them there too. That redundancy is cheap and it is the difference between losing five minutes of agent work and losing an afternoon of it.

What does not need DDL

The product's modules, epics, the catalog revision CatHead and the state of the last pull and push ride on the Product record as the document qaState (D-009, as vendorPolicy does). An empty result is stored as an absent property, because the property is constrained. catRev counts planning changes: a write that changes a planning field sets the case's catRev to ++CatHead, and the cases feed pages by it.

Events: nothing new, one meaning widened

A QA write that changes something emits one RecordUpdated and no other event name is added (BR-05). The one change of meaning is TaskPlanned: it now announces a plan, or an addition to one. When the QA tools create a case in a new epic, GAOS adds one card, Automate: <epic>, to the product's current workflow, announced by one TaskPlanned and one TaskMoved; it is always born BLOCKED with the rule qa-epic-added. The task fold therefore continues a workflow's ordinals (ordinal = the tasks already in that workflow plus the index) instead of restarting at 0; a first plan is unchanged. QA data never changes any existing task (BR-54).
