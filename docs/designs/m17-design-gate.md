## What this document is

M17 was specified in `docs/designs/egm-design-review.md` and ruled on in D-068
and D-069. It was not built: the event catalog is closed (BR-05), so a new
event name cannot be declared without the code that emits it.

**This document specifies the implementation.** It is the Go-level design for
T-184…T-188 — the files that change, the data model that grows, the two
contracts the model must answer with, the state machine the gate uses, and the
tests that prove each of it. Every claim carries a file and a line, and a
reader with no knowledge of the conversation that produced it can judge it.

Where D-069 already decided something, this document implements it and says
where. Where this document needed a decision D-069 did not make, the decision
is under **The decisions**, and each names the alternative it rejected.

## What revision 2 changed

The first review round ran **four** of the five lenses against revision 1 — the
comprehension lens exceeded the round's time budget and is recorded as **not
run**, not as a lens that found nothing — and they found **77 findings, 17 of
them blockers**, of which six were not wording but the mechanism failing.

A **second** round ran against revision 2, the version that was implemented.
It found four more blockers, of which two were in the code and not in the
document: the design part was never rendered into the prompt, and the task
kind was never persisted to ArcadeDB. The second round's reports are in
`docs/designs/reviews/`, and its triage in
`docs/designs/reviews/m17-design-gate-consolidated-2.md`. They are kept in
`docs/designs/reviews/m17-design-gate-review-1.md` and its siblings, and the
consolidated triage is in
`docs/designs/reviews/m17-design-gate-consolidated-1.md`.

Six of the blockers were not wording. They were the mechanism failing:

1. **The gate could not open.** A dependency is satisfied only by `DONE`
   (`dashboard/scheduler.go:363-376`), and the only production write of
   `StatusDone` is the operator's approval (`dashboard/board.go:263`). Revision
   1 gave the review task an automatic `REVIEW → DONE` and left the design
   task's in the operator's hands — so the review was never dispatched. **Now:
   a design task and a review task both reach `DONE` on their own verdict, and
   nothing else changes.**
2. **The findings went nowhere.** Revision 1 attached them to the implement
   task's next packet while that task was `BLOCKED` — and a blocked task is
   never dispatched, so the packet was never built. **Now: the implement task
   is released to `READY` the moment the review clears, and the packet it is
   then given carries the design and the findings.**
3. **The gate was a property of the plan, and the plan is an input.**
   `CreateWorkflow` takes the plan as an argument (`dashboard/store_mem.go:1843`)
   and `validatePlan` checked only ids, dangling prerequisites and cycles
   (`dashboard/graph.go:129-164`). **Now: `validatePlan` refuses a plan whose
   implementation task has no review.**
4. **The operator's dispatch route ignored the dependency.**
   `dispatchNow` (`dashboard/board.go:322-352`) applies the lease, the drift
   gate and the egress pass, and never consults the graph, so a back-office
   cookie could dispatch an unreviewed implementation. **Now:
   `dispatchNow` refuses a dispatch whose prerequisites are not `DONE`.**
5. **The design artifact vanished on restart.** The artifact load path reads
   `WHERE kind = :k` with `k = ArtifactHandoff`
   (`dashboard/store_arcade.go:1380-1383`), so only handoffs came back. **Now:
   the load path reads handoffs, designs and reviews.**
6. **The change list was short five files and its counts did not follow.**
   **Now: the change list is generated by the phases, and every count is
   derived from it.**

The rest of revision 2's changes are the smaller ones the lenses found, and
they are in the consolidated triage.

## The problem

GAOS dispatches agents that write code. Nothing in the product reviews a
*design* before it is built. The readiness rubric judges a product record; the
egress pass screens a packet; the handoff contract judges a reply
(`pustaka/docs/architecture/design-gate.html#the-problem`). The plan for a task
and the code that implements it are written by the same author, in the same
session, holding the same assumptions.

D-068 and D-069 decided the gate and, more importantly, decided **how a
platform-run reviewer becomes genuinely zero-context**. The answer: the
isolation boundary is the packet, not the workspace; the standing files are the
rubric and stay whole; what is withheld is the author's session state.

That answer is a *specification*. Nothing in the code implements it. Today:

- `freezePacketFor` (`dashboard/store_mem.go:1316`) is **per desk, not per task
  kind**. It has no branch that could shape a different packet for a review,
  so every task gets the same four to seven parts, all desk-scoped
  (`dashboard/store_mem.go:1349-1445`).
- `latestHandoffFor` (`dashboard/store_mem.go:1248`) is **desk-scoped on
  purpose**, so the next stage at a desk inherits the previous stage's
  handoff. A review is a stage at that desk. Without a change, a reviewer
  inherits the author's handoff — the contamination the gate exists to prevent.
- `TaskRecord` (`dashboard/model.go:674-698`) has **no `kind` property**, and
  `Task.role` is a closed seven-value regexp
  (`dashboard/schema/04-execution.sql:29-30`). There is no carrier for "this
  task is a review".
- The code writes exactly four artifact kinds — `handoff`, `prompt`, `reply`,
  `question` (`dashboard/model.go:874-884`, written at
  `dashboard/runner.go:195-224`) — so a design artifact cannot be written.

## Goals

- A plan can contain a **review task**, and a review task's **prompt** carries
  the design and the rubric and **nothing else**: no brief, no goal, no
  handoff, no failure lesson, no operator answer, no stories, no acceptance
  criteria. The frozen *packet* also keeps the contract part, as the evidence
  of what the model was told; the prompt drops it and re-renders the contract
  at the end.
- The review runs on a **fresh session** with its own reason, so it cannot
  resume the author's (D-056 makes a retry resume; a reviewer must not).
- The implementation task **does not start** until the review resolves with no
  open Blocker, and the findings **travel back** to the implementer.
- The gate needs **no new task status**, **no new agent role** and **no new
  event type**: it is the planner's own `DEPENDS_ON` edge and the existing
  `BLOCKED` status (D-069 clause 7). It does add blocking *reasons* — free text
  on `Task.blockReason`, which is not a closed vocabulary — and D6 names every
  one of them.
- The gate **cannot be bypassed**: a hand-made plan without a review is
  refused, and the operator's dispatch route refuses a task whose review has
  not resolved.
- A review turn is **metered like any other turn**, and a design written under
  a superseded Blueprint is **reported** (T-188).

## Non-goals

- **No new task status, no new agent role, no new event type.** The gate does
  add blocking reasons, as free text on `Task.blockReason`; D6 names them. The
  `Task.status` vocabulary (eleven values,
  `dashboard/taskstate.go:31-47`), the `Task.role` vocabulary (seven values)
  and the event catalog (BR-05) all stay as they are. D-069 clause 9 names
  exactly three vocabularies that grow, and this change grows those three.
- **No change to the egress pass's policy.** The new `design` packet part is
  screened by the existing detectors like every other part
  (`dashboard/egress.go:513` runs the content detectors over the survivors of
  **every** kind).
- **No inbound screening of replies.** A reply is stored verbatim today
  (`dashboard/runner.go:195-203`) and this change does not alter that. D-069
  clause 10 records the limit: the egress pass is a backstop, not the cure.
- **No change to the M5 review engine.** The `Review` vertex
  (`dashboard/schema/06-judgment.sql:14-26`) and its six-value `verdict`
  regexp are untouched; D-069 clause 8 replaces the gate's record with an
  `Artifact` of kind `review`.
- **No automated triage of the findings.** The four dispositions
  (`docs/rules/gaos-design-review.md`) are the *operator's* vocabulary for
  triaging a reviewer's findings. M17 records the findings so they can be
  triaged; it does not triage them.

## The decisions

Eight decisions D-068 and D-069 did not make. Each names what it rejects.

### D1 — The gate is enforced, not assumed

Three enforcement points, because a plan is an input and the operator has a
dispatch route of their own.

1. **`validatePlan` refuses a plan that does not wire the gate.**
   (`dashboard/graph.go`) Three rules, all before the first write. This is where
   the check belongs: the planner cannot build a cycle, so checking its own
   output proves nothing, but `CreateWorkflow` is public and any caller may
   hand it a graph (see the comment at `dashboard/store_mem.go`).

   - a task whose kind is outside `implement|design|review` is **refused**, not
     normalised. The fail-open direction here is contamination: a task the gate
     cannot see is a task that gets the author's brief and no review.
   - a plan with **no design task or no review task** is refused. A plan with no
     gate in it at all is refused, whatever else it contains.
   - **every story that carries an implementation task must have at least one
     implementation task in that story that waits directly on a review task.**
     The story is `PlanTask.Story`. A plan with no story at all must still wire
     one review before an implementation.

   The rule is per story, and that is the whole of the guarantee: a story-less
   implementation task is indistinguishable from a workflow task — the planner's
   own `p1`, `arch`, `sec` and `dev` are story-less and are not gated — so the
   guarantee is over the stories, not over every task.
2. **The scheduler's dependency block holds the task.** Unchanged: a
   prerequisite is satisfied only by `DONE`
   (`dashboard/scheduler.go:363-376`).
3. **`dispatchNow` consults the same helper.** The operator's board route
   (`dashboard/board.go:322-352`) applies the lease, the drift gate and the
   egress pass, and today no dependency check. It must refuse a dispatch whose
   prerequisites are not `DONE`, and the board must refuse to unblock a gated
   task whose review dependency is unmet.

*Rejected:* a dispatch-time check on the implement task's kind alone. It would
live in one route and be absent from the other, and it would duplicate what
the dependency already does.

### D2 — The review task's role is `qa`, and its model is set outright

`Task.role` is closed at seven values, so a review task reuses one: `qa` —
"QA Reviewer" (`dashboard/fixtures.go:13-23`). The *kind* is what makes it a
design review; the *role* is what seats it.

The `qa` role's default model is `claude-haiku-4.5`, and a review that cannot
follow the design proves nothing (D-068's method). So the plan builder sets
the review task's model to `claude-opus-5` **directly**.

*Rejected:* taking the `gate` flag to get the override. `PlanTask.Gate` is
persisted as the task's `approvalRequired` (`dashboard/store_arcade.go:667`)
and the wizard counts those flags for the operator
(`dashboard/handlers_cw.go:160-167`); reusing it would promise the operator an
approval gate the gate does not have. *Rejected:* a new role, which needs a
DDL widening of a closed regexp and a `roles` map entry.

### D3 — The plan grows two tasks per story

```
p1   planner             kind=implement  deps=[]
arch architect          kind=implement  deps=[p1]      (unchanged from today)
per story:
  des architect         kind=design     deps=[arch]
  rev qa                kind=review     deps=[des]
  imp <the story's role> kind=implement deps=[rev]      <-- THE GATE
  ver qa                kind=implement  deps=[imp]
sec  security           kind=implement  deps=[all ver]
dev  devops             kind=implement  deps=[sec], gate
```

`des` writes the story's design; `rev` attacks it; `imp` waits for the
review. `arch` is left exactly as it is today: it is an ordinary task, it
produces no design artifact, and nothing reads one it does not produce.

**The arithmetic, derived from the planner in `dashboard/store_mem.go`:**
`4 + 2N` tasks today, `4 + 4N` after, for a plan with at least one picked
story. Two stories: 8 → 12. Ten stories: 24 → 44. A plan that picks no story
takes the planner's fallback branch — a design, a review, an implementation and
a verification with no story — which is **8** tasks, not 4.

The implementation task's role is fixed at **`backend`**, as it is today; the
story's own role is not read for it. A frontend story is therefore implemented
by the backend seat, and the capability filter gives it that seat.

*Rejected:* one design and one review for the whole workflow. It is cheaper
(one review instead of N) but BR-46 says *every implementation task has a
design artifact and a review*, and a per-story implementation against a
workflow-wide design is the weaker guarantee. *Rejected:* making the review
part of the implement task's own run. Impossible: D-056 makes a retry resume
its session, so a reviewer that resumed the author's session would carry the
author's context — the exact thing the gate forbids.

**The cost is real and is named.** Under BR-38 one live turn per product
workspace, each of those is serial. §"Risks" carries it.

### D4 — The design is a `gaos-design` block; the review is a `gaos-review` block

A reply carries a fenced block the parser reads. `HandoffFence` is
`gaos-handoff` (`dashboard/handoff_reply.go:24`), `handoffBlocks`
(`dashboard/handoff_reply.go:44-61`) finds the blocks and `ExtractHandoff`
(`dashboard/handoff_reply.go:66-96`) takes the last one and checks it names
this run and this task.

Two more fences follow the same shape, and the block reader is generalised to
take the tag rather than copied:

- **`gaos-design`** — a task of kind `design` must end its reply with one, in
  addition to the ordinary `gaos-handoff` block. Its body is the design
  document. It is recorded as an `Artifact` of kind `design` and travels to
  the reviewer at `.gaos/packet/design.md`.
- **`gaos-review`** — a task of kind `review` must end its reply with one, in
  addition to the ordinary `gaos-handoff` block. It carries the findings.

**Every invocation still owes a handoff** (BR-30 is unchanged), so the
standing contract in the Blueprint's `00-gaos-contract.md`
(`dashboard/blueprint_render.go`) stays true and the handoff extraction stays
unconditional. The two new blocks are *additional*, and the handoff is
last — the handoff contract says "Copy it as the last thing in your reply"
(`dashboard/handoff_reply.go`), and the handoff parser takes the last
`gaos-handoff` block. The design and review blocks come **before** it.

*Rejected:* a review task that owes no handoff. It would contradict BR-30 and
the standing contract the design insists stays whole, and the attempt would be
marked failed by the unconditional handoff extraction.

### D5 — The contracts, exactly

**`gaos-design`.**

```
```gaos-design
---
task: wf-1-t-3
run:  wf-1-t-3-a1
role: architect
---
# The design

...the document, verbatim...
```
```

The front matter is mandatory and carries the identity. The document is
everything after the closing `---`, so a document may contain `---` of its own
without confusing the parser: only the FIRST closing `---` ends the front
matter.

**`gaos-review`.**

```
```gaos-review
---
task: wf-1-t-4
run:  wf-1-t-4-a1
role: qa
findings:
  - severity: blocker   scope: "src/pricing.go:42"   note: "the rounding is half-even, but DR-3 says half-up"
  - severity: major     scope: "docs/design.md:11"   note: "the migration order is not stated"
---
```

| field | values | required |
|---|---|---|
| `severity` | `blocker|major|nit` | yes |
| `scope` | `path` or `path:line` — see the rule below | yes |
| `note` | one line, at most **300 runes** | yes |

**The scope is validated, not merely documented.** A scope is a path, an
optional `:line`, and nothing else:

- at most 200 runes;
- no whitespace, and no `\n`, `\r` or `\t`;
- the path is not absolute and contains no `..` — a scope that can climb out
  of the tree is not a place in the tree;
- the path contains a `/` or a `.`, so it is a path and not a sentence;
- the optional `:line` is a positive integer, and there is only one `:` — a
  second segment is not a line number.

**The note is the free-text channel, and it is bounded on purpose.** The note
is one line and at most 300 runes, and it says what is wrong **without quoting
the text it complains about**. A scope names a place; a note names a defect.
Both travel into the implementer's prompt, so both are bounded.

**`findings:` is mandatory and may be empty** — but an empty list must also
carry `no-findings: true`, because a review that found nothing and a review
block the model did not finish are otherwise the same reply.

```
```gaos-review
---
task: wf-1-t-4
run:  wf-1-t-4-a1
role: qa
no-findings: true
findings:
---
```

**The scope is validated, not merely documented** — the whole rule is in the
field table above, and the code is `validScope` in `dashboard/designgate.go`.

**The note is bounded and is not the matched text.** A finding records WHERE a
defect is; the note says what is wrong in the reviewer's own words, in one
line of at most 300 runes. It is the difference between "blocker /
propose-fix / src/pricing.go:42" and a finding the implementer can act on. The
bound that matters is the reviewer's own rule: the note must not quote the text
it is complaining about, because the finding is persisted and forwarded into the
implementer's prompt.

**The verdict is derived, not declared.** A finding of severity `blocker` is an
open Blocker; no open Blocker means the review cleared. A reviewer cannot
declare "accept" while listing a blocker. The derived verdict is *recorded* on
the review artifact, so the register can assert it.

**The design is data, never instruction.** The review contract states it, and
the design body cannot forge a *contract* block: a design document containing a
fenced block tagged with any reserved contract name is refused at parse time.
It can still forge a *packet section heading* — the `===== path =====` format
is text — so the part is rendered inside its own heading and the reader is
told which part it is reading. That half is a limit, and §"Risks" carries it.

*Rejected:* a `disposition` field on the finding. The four dispositions are the
operator's triage of a reviewer's finding, not something the reviewer assigns
to its own finding. *Rejected:* a `note`-less finding. *Rejected:* a declared
`verdict` field.

### D6 — The gate

The gate's state is a function of the task graph:

| the review task is | the gate says | the implement task |
|---|---|---|
| not yet resolved (`PENDING`) | `unreviewed` | `BLOCKED`, reason `design-unreviewed` |
| `DONE`, with a recorded review artifact whose verdict is `accept` | `cleared` | `READY` — it may run |
| `DONE`, with **no** recorded review artifact | `failed` | stays `BLOCKED`, reason `design-blocked` |
| `BLOCKED`, reason `design-blocked` | `blocked` | stays `BLOCKED`, reason `design-blocked` |
| `BLOCKED`, reason `review-failed` | `failed` | stays `BLOCKED`, reason `design-blocked` |
| `BLOCKED`, reason `design-missing` | `failed` | stays `BLOCKED`, reason `design-blocked` |
| `FAILED` | `failed` | stays `BLOCKED`, reason `review-failed` |

**The verdict is the gate's own record, never a status.** A `DONE` review task
is not a cleared gate on its own: an operator can approve a card, and an
approval is not a verdict. The gate reads the review **artifact** — the record
the gate itself wrote — and clears only when that artifact exists and its
derived verdict is `accept`. A review task that reached `DONE` by any other
route leaves the gate closed.

**Who writes what.**

| when | the review task | the implement task |
|---|---|---|
| the graph is written | — | `BLOCKED`, reason `design-unreviewed`, rule `gate-unwired` |
| the design task produces its document | `DONE`, rule `design-delivered` | — |
| the design task's document is refused by the screening | `BLOCKED`, reason `design-screened-out`, rule `design-screened` | — |
| the design task produces no readable design block | `BLOCKED`, reason `design-missing`, rule `design-screened` | — |
| the review task has no design to attack | `BLOCKED`, reason `design-missing`, rule `review-failed` | stays `BLOCKED`, reason `design-blocked` |
| the review task produces findings and no Blocker is open | `DONE`, rule `review-cleared` | `READY`, rule `review-cleared` |
| the review task produces findings and a Blocker is open | `BLOCKED`, reason `design-blocked`, rule `design-blocked` | stays `BLOCKED`, reason `design-blocked` |
| the review task produces no review block | `BLOCKED`, reason `review-failed`, rule `review-failed` | stays `BLOCKED`, reason `design-blocked` |
| the review task's record is refused by the screening | `BLOCKED`, reason `review-screened-out`, rule `review-screened` | stays `BLOCKED`, reason `design-blocked` |

**Every screening refusal is recorded.** A design or a review the screening
refuses leaves no artifact, so a silent no-op would look exactly like a task
that finished. Every such refusal is a `BLOCKED` task with a reason and a rule,
and it appears in the timeline like any other state change. The *operator's*
refusal to clear a gated task is a different thing: it is a refused **move**,
and a refused move writes no event — the house pattern for the board, where a
refusal answers 409 and the timeline records the state that did not change.

**The release is conditioned on the review's actual status**, not on the gate's
intention: a review whose own move was refused — `FAILED`, say — has not
resolved, and an implementation released on the strength of an intention is an
implementation that ran with no review.

**The rule vocabulary**, all of it, in one place: `gate-unwired`,
`design-delivered`, `design-screened`, `review-screened`, `review-cleared`,
`design-blocked`, `review-failed`. They travel in `TaskMoved`'s `Rule` and are
visible in the timeline.

**The blocking reasons**, all of them: `design-unreviewed`, `design-blocked`,
`review-failed`, `design-missing`, `design-screened-out`, `review-screened-out`.
They are free text on `Task.blockReason`, which is not a closed vocabulary, and
they are written on the record rather than moved — a same-status move is
refused by the state machine, so a reason change is a field write.

Every move above is legal under the existing transition table
(`dashboard/taskstate.go:79-95`): `REVIEW` may go to `DONE` or `BLOCKED`;
`PENDING` and `BLOCKED` may go to `BLOCKED`; `BLOCKED` may go to `READY`.

**The reason is written on the task, not as a move.** `TaskRecord.BlockReason`
(`dashboard/model.go:687`) is a field, and `moveTaskLocked`
(`dashboard/runner.go:373-384`) refuses a same-status move. So the gate
writes the reason on the record itself — the way the question-expiry path does
(`dashboard/questions.go:213-227`) — and the *move* carries the rule that says
who acted.

**A failed review is not a verdict** (D-068 clause 7). A review task whose
reply carries no readable `gaos-review` block moves to `BLOCKED` with reason
`review-failed`; it consumes **no retry, no escalation and no failure
signature** (BR-34), so `TaskRecord.Retry` and `TaskRecord.Esc` are left
untouched and the operator's retry is the only thing that counts one.

**`REVIEW → DONE` is the gate's own write.** Today the only production write
of `StatusDone` is the operator's approval (`dashboard/board.go:263`). The
gate writes it for two kinds only — a design task whose document arrived, and
a review task whose verdict cleared — and it carries its own rule string so
it is distinguishable in the timeline. Every other task keeps today's
behaviour: its run ends in `REVIEW` and the operator approves it.

**The implement task is released by the gate, not by the scheduler.** The
scheduler holds a task whose dependency is not `DONE`; the gate is what makes
the review task `DONE`. So the implement task's dependency becoming met is the
release, and the gate's `BLOCKED → READY` move is the same event seen from the
task's side.

### D7 — The findings travel back, and the design goes with them

The implement task's next packet carries:

| path | kind | body |
|---|---|---|
| `.gaos/packet/design.md` | `design` | the design it is implementing, verbatim |
| `.gaos/packet/context/findings.md` | `context` | the review's findings, re-rendered in the gate's own record format |

The findings are the `Artifact` of kind `review` produced by the review task
the implement task depends on; the design is the `Artifact` of kind `design`
produced by the design task the review task depends on. **Both are found by
dependency**, so no new field is needed on the task: *a task reads the artefact
of the task it depends on.*

D-069 clause 6 makes the findings concrete, and it is what makes D-056's
promise — the implementer sees the review that rejected it — true rather than
aspirational.

### D8 — The drift report, and the budget

**The drift.** A design is written under a published Blueprint version, and
the product's Blueprint moves on. GAOS reads no folder — `repoParts` is nil in
every deployment (`dashboard/store_mem.go:168-173`) and BR-42's allowlist
admits only `CLAUDE.md` and `.claude/rules/*.md` — so GAOS **cannot** compare
a design against the code.

What it can compare is the design against the **version it was written under**.
The pin is already recorded: the run carries `BlueprintVersion`
(`dashboard/runner.go:114`) and the artifact carries its `RunID`
(`dashboard/model.go:871-881`), so the pin is a join, not a new field. **The
drift report is written into the review artifact**: when the design's pin
differs from the version the review itself runs under, the review artifact
carries a drift line naming both.

This is weaker than comparing code, and the document says so. It is the
strongest statement GAOS can make without reading a folder.

**The budget.** A review turn is **metered like any other turn**. The desk's
running cost and the tenant's spend (`dashboard/runner.go:268-274`)
accumulate the review turn's measured cost exactly as they accumulate an
implement turn's, and the per-workflow and per-tenant caps of BR-17 apply to
it because the budget guard reads the same accumulators. No exemption, no
separate bucket. The budget guard itself (M10.3) is not built, so this is the
accounting that will be.

## The mechanism, in one page

```
    PlanWorkflow  ──▶  p1 ──▶ arch
                             │
                             ▼
                    per story:  des(kind=design) ──▶ rev(kind=review) ──▶ imp(kind=implement) ──▶ ver
                                        │                       │
                                 writes design            reads design,
                                 artifact              writes findings
                                                                  │
                                                                  ▼
                                                    imp's next packet carries
                                                    the design + the findings
```

| the turn | its packet | its reply |
|---|---|---|
| `des` | the ordinary packet | a `gaos-handoff` block **and** a `gaos-design` block |
| `rev` | **exactly** the design and the rules | a `gaos-handoff` block **and** a `gaos-review` block |
| `imp` | the ordinary packet **plus** the design and the findings | a `gaos-handoff` block |

**The frozen packet and the rendered prompt are two different objects, and
the isolation guarantee is over the prompt.**

The review task's *packet* holds three parts: `.gaos/packet/handoff.md` (the
contract), `.gaos/packet/rules.md` and `.gaos/packet/design.md`. The contract
part is the **evidence of what the model was told** — T-062 puts it in the
frozen slice so a replay can prove what the run was asked for as well as what
it was given — and `RenderPrompt` drops it and re-renders the contract at the
end of the prompt.

The review task's *prompt* holds exactly two parts: `.gaos/packet/design.md`
and `.gaos/packet/rules.md`. It carries **none** of:

- `.gaos/packet/task.md` — the brief and the goal (`dashboard/store_mem.go:1349`)
- `.gaos/packet/handoff.md` — the contract (`dashboard/store_mem.go:1360`)
- `.gaos/packet/context/answer.md` — the operator's answer (`dashboard/store_mem.go:1379`)
- `.gaos/packet/context/handoff-previous.md` — the previous stage's handoff (`dashboard/store_mem.go:1389`)
- `.gaos/packet/context/failure-previous.md` — the failure lesson (`dashboard/store_mem.go:1391`)
- `.gaos/packet/context/record.md` — every story, every acceptance criterion, every decision (`dashboard/store_mem.go:1418-1432`)

That list is D-069 clause 3's "the author's session state", spelled out at the
paths it lives at.

**The `rules` part is already there.** `freezePacketFor` builds it at
`dashboard/store_mem.go:1403-1416` for every task; the review branch keeps it
and drops the rest. The rubric needs no new kind — it already travels as
`rules` (`dashboard/egress.go:43`).

**The `design` part is new.** `KindDesign = "design"` joins the packet-kind
block (`dashboard/egress.go:41-48`). `Screen` needs no change: it tests the
kind exactly once, for `KindRepo` (`dashboard/egress.go:477`), and everything
else goes through the content detectors (`dashboard/egress.go:513`).

**The session.** A review runs on a fresh session. `sessionForLocked`
(`dashboard/turns.go:97-136`) returns the task's last session when it may be
resumed; a review task has no last session on its first attempt, so it opens
one with the reason **`reviewer`** — a new constant beside `SessionFirst`,
`SessionEscalation`, `SessionLostReason`, `SessionRotation` and
`SessionVendor` (`dashboard/turns.go:38-46`), written into the `SessionOpened`
event's `Rule` (`dashboard/turns.go:152`). The reason is selected in
`sessionForLocked`, which reads the task's kind: a task of kind `review`
always opens a new session, whatever its history.

A review's **retry** must not resume the author's session, and it does not:
the review is a different task from the author, and D-056's resume rule
applies within a task. A retry of the review resumes the *review's own*
session, which is the reviewer's own prior turn — not the author's context.

## The data model

New file `dashboard/schema/14-design-gate.sql`, the next free number
(`13-vendors.sql` is the newest). `schemaFiles()` sorts by filename and
applies in order (`dashboard/schema_embed.go:116-132`), so a `14-*.sql` runs
last — which is what an `ALTER` wants.

```sql
CREATE PROPERTY Task.kind IF NOT EXISTS STRING (regexp '^(implement|design|review)$');

ALTER PROPERTY Artifact.kind REGEXP 'sequence|erd|flow|diff|commit|report|log|upload|handoff|prompt|reply|question|design|review';

ALTER PROPERTY USES_CONTEXT.role REGEXP 'requirement|rule|boundary|story|criterion|diagram|decision|lesson|code|diff|policy|design';
```

Three changes, and three closed vocabularies grow — exactly D-069 clause 9's
three.

**Which declaration is authoritative.** `Artifact.kind` is declared in three
places: the `CREATE` at `dashboard/schema/02-master.sql:55-57`, the `ALTER`
at `dashboard/schema/11-blueprint.sql:83` and the `ALTER` at
`dashboard/schema/12-questions.sql:20`. The **newest `ALTER` is the current
list** — it is applied last and replaces the regexp — and the `CREATE` is
widened to the same list, because that is the house pattern
(`TestTheQuestionDDLWidensWhatTheCreateDeclares`,
`dashboard/questions_test.go:247-262`). The two historical `ALTER`s are left
as they are: they record what M14 and M15 did, and a later `ALTER` supersedes
them.

**`Task.kind` is not mandatory and not defaulted.** A property added to a type
that already exists in deployed databases does not backfill the rows written
before the migration — the precedent is `Task.rank`
(`dashboard/schema/11-blueprint.sql:63`) and `TaskRun.provider`
(`dashboard/schema/13-vendors.sql:15`), both optional. A task with no kind
reads as `implement`, in Go (`taskKind` in `dashboard/designgate.go`).

**The regexp is anchored**: `^(implement|design|review)$`, so a value such as
`review-x` satisfies neither the DDL nor the Go side.

**An absent kind is an implement task; an unknown kind is refused.** A task
planned before the migration has no kind, and it is an ordinary implementation
task — the alternative is a task the planner and the scheduler disagree about.
A kind that is *present* but outside the vocabulary is refused before the first
write, by `validatePlan`, because the fail-open direction is contamination: a
task the gate cannot see is a task that gets the author's brief, the previous
handoff and the operator's answer, and no review. The Go side is exact, and
`TestTheClosedVocabulariesMatchTheDDL` asserts both directions.

**A gap this change closes.** There is **no test** that the Go citation-role
constants match the `USES_CONTEXT.role` regexp. `schema_test.go` has one for
`Task.status` (`dashboard/schema_test.go:284-315`) and one for `TaskRun`'s
enumerations (`dashboard/schema_test.go:355-369`), but nothing for citation
roles. A new `CiteDesign` constant without the DDL widening would be refused
by ArcadeDB at commit, and nothing would catch it. This change adds that
test, and the same test for `Task.kind` and for `Artifact.kind`.

## Alternatives considered

**A — A reviewer workspace with the rubric but not the Blueprint.** Rejected,
and it was rejected before this document: it trips BR-39's drift gate, because
a workspace holding the rubric but not the product Blueprint is by definition a
drifting workspace (D-069 clause 2).

**B — A new task status for "gated".** Rejected: it widens a closed
vocabulary (`dashboard/taskstate.go:31-47`), the DDL regexp
(`dashboard/schema/04-execution.sql:27-28`) and its vocabulary test
(`dashboard/schema_test.go:284-315`) for no gain. The dependency edge already
holds the task (D1).

**C — The `Review` vertex carries the gate's findings.** Rejected: D-069
clause 8. The `Review` vertex's `verdict` is a closed six-value regexp and
`finalScore` is mandatory (`dashboard/schema/06-judgment.sql:14-26`); a design
gate has no score to record and no band to fall in.

**D — The review runs as a sub-turn of the implement task.** Rejected: D-056
makes a retry resume its session, so the reviewer would inherit the author's
context. The reviewer must be a separate task on a separate session.

**E — The findings travel back in the implementer's `handoff-previous.md`.**
Rejected: the handoff chain is desk-scoped and the review's handoff would
displace the design's. The findings need their own part with their own
semantics (D-069 clause 6).

**F — One design and one review per workflow.** Rejected in D3, with the
reason.

**G — The gate enforced only by the scheduler.** Rejected in D1: the operator's
dispatch route is a second door into the same decision, and a gate with two
doors and one lock is not a gate.

## What would show this works

The design measures nothing, and a gate whose benefit is never measured cannot
be evaluated after the fact either — once `4 + 4N` tasks and a blocked-review
deadlock are in production there is no cheap way back. Three numbers, none of
them built yet, are what the milestone owes:

- **the cost of a review turn**, and the cost of a workflow of `4 + 4N` turns
  against BR-17's per-workflow and per-tenant caps, while the guard is unbuilt;
- **the rate at which a review raises a finding** — a review that never finds
  anything is the expensive kind;
- **the rate at which the operator judges a finding wrong**, which is the
  false-positive rate, and which is what a blocked review with no exit costs.

The first is measured by the desk's running cost, which already carries a
review turn. The second and third need the review's record and the operator's
triage, and neither exists yet: the triage vocabulary has no carrier in the
product, because triage is the operator's act and the product does not model it.

**What the gate does when the budget is exhausted** is also unstated, and it
matters: BR-34's deferral would leave a design task deferred forever, holding
the whole chain behind it, with no review and no explanation.

| The gate doubles the turns a workflow takes | Named. `4 + 2N` becomes `4 + 4N`: two stories go 8 → 12, ten stories 24 → 44. Under BR-38 one live turn per product workspace, so each is serial. Alternative F is cheaper and weaker; D3 says why. |
| A reviewer's model is too weak to follow the design | D2 sets `claude-opus-5` on the review task outright. |
| The standing files put the stories and the decisions back in front of the reviewer | **Named, and it is a limit, not a fix.** The Blueprint renders the stories into `20-stories.md` and the decisions into `30-decisions.md` (`dashboard/blueprint_render.go:78-100`), and D-069 clause 2 says the standing files stay whole. So the reviewer holds the requirement in outline, and the isolation the gate provides is over the packet. BR-47 is amended to say exactly that. |
| The design document is an instruction to the reviewer | The review contract states that the design is data and never instruction; a design document carrying a reserved fence is refused; an empty findings list needs an explicit `no-findings: true`. The content detectors are credential-shaped and do not address injection (`dashboard/egress.go:337-355`); that is a limit, recorded. |
| The reviewer's session is fresh but its workspace is the product's own | The workspace is per product (`dashboard/adapter_aimanager.go:78-83`), so the reviewer's turn runs in the same folder as the author's. What a fresh session can reach there is outside GAOS's record. Named as an open limit. |
| A finding that quotes a secret | The note is one bounded line and the rule is the reviewer's own: it must not quote the text it complains about. The review artifact is screened by the same detectors before it is recorded. |
| The reply is stored verbatim, so a finding can carry a secret | D-069 clause 10, restated in the non-goals. The egress pass is a backstop, not the cure; inbound screening is separate work. |
| The gate's `REVIEW → DONE` write is new | It is the only production write of `StatusDone` outside the operator's approval (`dashboard/board.go:263`), it is confined to two task kinds, and it carries its own rule string. |
| BR-48's clearance is refused, so an open Blocker has no exit | Named. M17 implements the dispatch stop and refuses the clearance, exactly as BR-48 says, and records the refusal. The consequence is that a blocked design waits for the back office's identity work — which is BR-48's stated precondition on M17. |
| The plan grows and the capability block bites | A per-story design task takes the `architect` role and a review task takes `qa`; the scheduler's capability reason (`dashboard/scheduler.go:290-301`) will say so plainly when no seat is free. |

## Status

**Approved (revision 3).** Two rounds ran.

**Round 1** was against revision 1: four of the five lenses reported (the
comprehension lens exceeded the round's time budget and is recorded as **not
run**, not as a lens that found nothing), and they found 77 findings with 17
blockers, of which six were the mechanism failing rather than the prose. Its
reports and triage are `m17-design-gate-*-1.md` in `docs/designs/reviews/`.

**Round 2** was against revision 2 — the version that had been implemented — and
it found four more blockers. Two were in the **code**, not the document, and
both were the kind a review exists to catch:

- the design part was in the packet but **never rendered into the prompt**, so
  the reviewer was handed the rubric and a contract telling it to attack a
  document it could not see;
- the task kind was **never persisted to ArcadeDB**, so a restart erased every
  task's kind and the gate was inert on a restored graph.

Both are fixed, both now have their own tests, and the second round's triage is
`docs/designs/reviews/m17-design-gate-consolidated-2.md`.

The operator pre-approved the implementation of this session on 2026-11-04,
before the first round. The rounds still ran and their findings were still
applied, because a gate that skips its own probe is the thing this repository
was written to stop. Two findings remain escalated — a re-review round for a
rejected design, and whether a review can run in a workspace the author's turn
cannot write to — and both are in §"Open questions".
