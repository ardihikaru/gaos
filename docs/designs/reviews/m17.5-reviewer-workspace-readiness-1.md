# Design review — M17.5, the reviewer's own workspace

**Target:** `docs/designs/m17.5-reviewer-workspace.md` (revision 1)
**Lens:** Readiness (the zero-decision rule — if the implementer would have to ask "which one did they mean?", the document is not ready)
**Round:** 1 · **Date:** 2026-11-04
**Read:** the design document, the rubric (`.claude/rules/rule-index.md`, `.claude/rules/qa-test-plan.md`, `.claude/rules/agent-workspace.md`) and the domain sources the index names. Every `file:line` claim was re-derived from the tree.

*(The lens's findings are reproduced here; the supporting evidence is condensed.)*

### The QA case count is written two ways - Severity: Blocker
- Affected scope: the counts table, the arithmetic, and the registers table.
- Finding: the counts table moves QA cases 381 → 390, the arithmetic says "380 + 9 = **389**", and the registers table writes "three hundred and ninety" into the register page but "three hundred and eighty-nine" into the ToC and the validator. The rubric requires all four mirrors to agree, and the validator greps the register and the ToC for the string, so the plan as written fails phase 3's own exit condition.
- Recommendation: fix the arithmetic to `381 + 9 = 390` and use "three hundred and ninety" in all four places, plus the QA rule's mirror.

### The phase tables do not cover the change list - Severity: Major
- Finding: `dashboard/store_conformance_test.go` is listed as modified but no phase assigns it; phase 2's summary says seven modified files while its table lists six. Phase 2's exit is "go test ./... passes, including the conformance suite for both stores", and the new `TaskRun.workspace` round-trip has to be added to that suite, so an implementer following the phase tables literally cannot reach phase 2's exit condition.
- Recommendation: add the conformance file to phase 2's table with its change, and correct the phase-2 count.

### The store's way to the reviewer workspace id is unspecified, and its file sits in phase 2 - Severity: Major
- Finding: the store must learn the reviewer's id from the adapter, but the design never says that the `WorkspaceGateway` interface gains a method nor names one. Phase 1 names `ReviewWorkspaceFor` on the adapter and creates the new file, while D9 places `WorkspaceCopy`/`ProductWorkspace` in a phase-2 file. An implementer must therefore choose: add the method to the interface (touching a phase-2 file in phase 1), declare a private interface in the new file, or move the record types into the new file — three different phase-1 diffs.
- Recommendation: name the seam and its home, say where the record types live, and put those files in phase 1's list.

### `clearFor`'s new parameter breaks two test files that are not in the change list - Severity: Major
- Finding: `clearFor` is called in the runner, the board, `questions_test.go` and `designgate_test.go`; adding a parameter breaks the two test files' compilation, and neither appears in any phase table or in the change list. Phase 2's exit therefore cannot pass.
- Recommendation: add both test files to phase 2 and to the change list, and give `clearFor`'s new signature exactly.

### D-069 clause 1 is never amended - Severity: Major
- Finding: D-069 clause 1 states "The reviewer's **workspace** is the product's own workspace … the workspace is not a boundary" — the exact ruling this change reverses. The register change is specified only as "D-071 added"; nothing says D-069's row is edited or that D-071 supersedes clause 1, so the register of record would carry both rulings at once.
- Recommendation: state the decision-log edit precisely — amend D-069's clause 1 and its summary line, or have D-071 say explicitly that it supersedes clause 1 — and name which text changes.

### The refusal's rule, reason and release are not decided - Severity: Major
- Finding: the mechanism says a failed preparation is refused and TC-386 asserts "the rule, the reason", but no rule value and no reason text is fixed. The Goals forbid new rule vocabulary, so the implementer must pick one of the three existing rules. The release path is equally open: a BR-39 block is released by `releaseDriftLocked` after a sync, and the plan never says what releases a block raised by a failed reviewer preparation.
- Recommendation: fix the rule, the reason format and the release condition, and write them into the decision and into TC-386.

### What the reviewer's drift does to the record and to the desk is undecided - Severity: Major
- Finding: D9 says `SyncBlueprint` records the reviewer copy, but the per-review reset is never said to update that copy, so the record can keep a digest the folder no longer has. D5 says the drift is recorded "against that workspace's copy" but never says whether the desk is still blocked after a reviewer's turn drifts the reviewer's folder, nor whether the next reset clears that block.
- Recommendation: state whether the reset writes the reviewer's copy into the record, whether a reviewer's drift blocks the desk, and what releases it.

### The QA register is updated in a later phase and its required content is unspecified - Severity: Major
- Finding: the QA rule requires the register to be updated in the same change as the test, one row per new top-level `func Test…`, and scenario prose with positive *and* negative cases and the exact quoted assertion strings. No phase creates the `#go-reviewer-workspace` h3 the header names, and the nine rows' quoted strings are never stated. TC-382…TC-390 do not exist today, so "to `Implemented`" is a creation, not a flip.
- Recommendation: name the h3 id and the nine scenario sentences with their quoted strings.

### The live probe changes a script that no phase owns - Severity: Major
- Finding: the acceptance script is in neither a phase table nor the change list, and the nine allocated ids leave none for its three checks, although a changed script needs its own register rows.
- Recommendation: add the file to a phase and allocate its case ids, or move the probe into its own milestone and say so.

### The published graph page the plan says it amends is not in the change list - Severity: Major
- Finding: the Risks row promises that the graph's "one workspace per product" page is amended, but that page appears in neither phase 3's table nor the register files, and `pustaka check ./docs` will not notice a stale claim there.
- Recommendation: add the page to phase 3 and to the change list with the exact amended sentence.

### The count mirrors are incomplete, and one named string does not exist - Severity: Major
- Finding: the ToC carries "Seventy decisions GAOS has actually made", not "Seventy-one entries"; the same ToC also carries the package split "two hundred and forty-two dashboard and twenty-two pustaka unit tests", which the four-place list never moves and nothing asserts. The validator row likewise names three strings where the file asserts more.
- Recommendation: enumerate every string that moves, per file, with its exact new value.

### D8 does not say what is truncated - Severity: Major
- Finding: D8 defines the id and then truncates "a tenant and product that overflow it" without saying whether the truncated value is the reviewer id or the product id, and without saying whether the product's own id is truncated at all.
- Recommendation: give the algorithm literally, and say the product's own id is left unchanged.

### The record's `Clone` is not mentioned - Severity: Major
- Finding: D9 enumerates the call sites that stay unchanged because `Holds`/`setHolds` are promoted, but not `ProductWorkspace.Clone`, which today deep-copies one `Others` map. With two copies, an unchanged `Clone` leaves the reviewer's per-vendor map shared between the live master and every snapshot.
- Recommendation: say that `WorkspaceCopy` gets its own `Clone` and that `ProductWorkspace.Clone` deep-copies both maps.

### What the manifest and the prune cover is not stated - Severity: Major
- Finding: the guarantee rests on "the reviewer's manifest is checked against the published file set" and "the prune removed it", but the repository does not say what the worker's manifest lists or what prune deletes: the manifest is documented as "path, bytes, sha256" and the allowlist as a write boundary for the provisioning API, while Claude Code runs with full permissions in the folder. If a file the model wrote is not in the manifest, the manifest check passes while the folder still holds it.
- Recommendation: state what the manifest lists and what prune deletes, and make the probe assert on the folder's file set (or narrow the guarantee to the managed files).

### A wrong line reference for the `TaskRun.provider` precedent - Severity: Nit
- Finding: both citations say `dashboard/schema/13-vendors.sql:15`; that file has 11 lines and the statement is at line 11.
- Recommendation: correct the line reference, and note that the precedent carries a regexp while the new one deliberately does not.

### Phase 1's exit runs two of the three phase-1 tests - Severity: Nit
- Finding: the exit command names two tests, not the third.
- Recommendation: name all three, or state which phase the third lands in.

### D7 does not name the adapter field and the wiring it removes - Severity: Nit
- Finding: D7 says "the field, the env read and the branch in `WorkspaceFor` go", but the adapter's own field and the wiring that set it are not named; both must go with the env read or the override lingers as dead state.
- Recommendation: name all four removals with their file:line.

### The gateway id-grammar citation points at the prefix setting - Severity: Nit
- Finding: `:344-345` is the `WORKSPACE_PROVISION_PREFIX` row; the grammar is at `:368`.
- Recommendation: cite `:368` for the grammar and `:344-345` for the prefix.

### OQ-27 is quoted in a shortened form that drops the half D6 answers - Severity: Nit
- Finding: the document quotes OQ-27 as "Where does a product's actual code live inside its workspace?"; the register's title is "Where does the product's code live, and how many turns per workspace?" — and the second half is what D6's amended BR-38 answers.
- Recommendation: quote OQ-27 in full and state which half remains open.

### Phase 2's exit claims the conformance suite runs against both stores - Severity: Nit
- Finding: `go test ./...` runs the ArcadeDB half of the conformance suite only when `GAOS_ARCADE_TEST_URL` names a reachable database, so the exit condition promises more than the command gives.
- Recommendation: state the ArcadeDB precondition in the exit condition.
