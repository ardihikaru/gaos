### The QA case count is 389 in two files and 390 in two others - Severity: Blocker
- Affected scope: the counts table, the arithmetic, and the registers table.
- Finding and rationale: the document states 381 → **390** in the counts table, but the arithmetic sentence reads *"Nine new register rows → 380 + 9 = **389**"*. The wrong number then propagates into two mirrors: the register page and the QA rule are to say "three hundred and ninety", while the ToC and the validator are to say "three hundred and eighty-nine". The validator checks both files with the *same* expected string, so one of them fails by construction and phase 3's exit criterion — "`./deploy/check-workspace.sh` passes" — cannot hold. The document also omits the mirrors the validator asserts: the README's case count, its two test counts and its version.
- Recommendation: make it 390 everywhere, fix the sentence to "381 + 9 = **390**", and enumerate every string that moves, including `deploy/check-workspace.sh:141-144`.

### The reset does not prune unless the digest already differs - Severity: Major
- Affected scope: D3, especially the steps that claim the folder holds exactly these files.
- Finding and rationale: D3 states the reset *"rewrites the files **with prune**, so the folder holds exactly these files"* and concludes *"no earlier review's leftover (the prune removed it)"*. But `SyncWorkspace` writes **only** when the reported digest already differs; on a matching digest it performs no write and therefore no prune. Whether a leftover changes the reported digest depends on whether the worker's manifest lists files outside the published set — which the repository does not document. The guarantee the whole design rests on is therefore conditional on an undocumented property of an upstream system, and the design states it as fact.
- Recommendation: make the reviewer's reset prune unconditionally, or state the manifest's scope as an explicit assumption and say what happens when it is false. Add the leftover-file case to the verification plan.

### The author's folder is one string operation away from the reviewer's own id - Severity: Major
- Affected scope: D1, D8 and the Risks table.
- Finding and rationale: the reviewer id is the product id **plus `-review`**, and the folder is `root/<id>`. A reviewer in `root/gaos-t-p-review` can reach `root/gaos-t-p` by removing one suffix — no packet needed. The design's risk row names the gap accurately (*"the gateway documents a write boundary … but no read boundary between sibling folders … It is not a sandbox"*) but then offers as mitigation *"the author's folder is never named in the reviewer's packet"* — which the id scheme itself invalidates, since the folder name is derivable from the reviewer's own. Claude Code runs with full permissions in the workspace, and the reviewer's model is one `Read` away from the author's files.
- Recommendation: derive the reviewer id from a value the reviewer cannot invert, or narrow the claim to what the code supports — *"the reviewer's packet and standing files hold none of the author's files"* — and drop the implication that the author's folder is unreachable. The live probe's canary should be planted at a path derivable from the reviewer's own id.

### The change list omits files the design breaks, and files it promises - Severity: Major
- Finding and rationale: six files are missing, and each omission is checkable: `dashboard/workspace_test.go` asserts one `WorkspaceProvisioned` and one `BlueprintSynced`, and D9 syncs both workspaces with the same events, so the first sync emits two of each and the test fails; `dashboard/designgate_test.go` and `dashboard/questions_test.go` call `s.clearFor(d, attempt)`, and phase 2 changes that signature, so the package will not compile; `deploy/acceptance/live-aim-run.sh` gains three checks but is in no phase and no change row; and `pustaka/docs/architecture/gateway.html` and `pustaka/docs/architecture/graph.html` both assert the thing this change breaks.
- Recommendation: add all six to the phases and the change list, and give the live probe's three checks their own rows (or amend TC-300…TC-303 with the exact quoted strings).

### The change list is not generated by the phases, and two published counts do not follow - Severity: Major
- Finding and rationale: the phase-2 table lists six files while the count column says seven, and the reconciliation sentence cannot be derived from the tables. The 11th modified file in the enumeration appears in the change list but in **no phase**, so the totals only reconcile if a file no phase touches is counted as touched. Separately, the scoreboard row is specified as `4 / 4 / 0 / 0 / 0`, but the design defines three tasks and three phases; the convention is Sub = sub-milestones, ✅ = tasks, so it should be `3 / 3 / 0 / 0 / 0`, and the "Next" column is not specified at all.
- Recommendation: fix the phase-2 count, put the missing file in phase 2, and correct the scoreboard row with its "Next" cell.

### D5 fixes the digest attribution but leaves the desk blocked with a false reason - Severity: Major
- Finding and rationale: D5's stated purpose is that *"the review would punish the author for the reviewer's behaviour"*. D5 changes only the digest attribution. But `checkAfterTurn` also **blocks the desk unconditionally** and emits a `DispatchRefused` with rule `observed-drift` — a path D5's bullets do not touch. After D5 the next dispatch is not refused, yet the desk stays blocked with the reason *"the next dispatch is refused until the Blueprint is synced (BR-39)"* — now a false statement — until an unrelated sync releases it. Half the punishment the design promises to remove survives, and nothing in the document says so.
- Recommendation: decide explicitly what a reviewer's observed drift does to the desk, scope the block if it must not touch the author's desk, say what releases it, and add it to D5 and to TC-387.

### The conformance table's published case count must move with the table - Severity: Major
- Finding and rationale: the change list includes `dashboard/store_conformance_test.go` — *"the run record's workspace round-trips"*. `storeContract` holds exactly forty-two cases today, and the register quotes that number in TC-124, TC-125 and in the scenario prose. The phase-3 row for the register says only "TC-382…TC-390 to `Implemented`; the counts", which does not reach these three strings.
- Recommendation: state whether the round-trip is a new conformance case. If it is, "forty-two" → "forty-three" in TC-124, TC-125 and the prose; if it is folded into an existing case, say so, so the count is known not to move.

### `TaskRun.provider` is at line 11, and it carries a regexp - Severity: Nit

The reasoning for the omission is sound; only the wording needs fixing.

### The amended BR-49 says the packet carries no contract; the frozen packet carries one - Severity: Nit
- Finding and rationale: the amended BR-49 asserts *"The reviewer's packet carries exactly two kinds"* and the diagram says *"packet = design + rules"*. The frozen review packet carries three kinds: the contract part is added unconditionally, outside the review guards. The wording is inherited from D-069 clause 1 and T-184, so this design does not introduce the error — but it elevates it into a published rule. The rendered *prompt* does drop the contract part and re-render it at the end, which is where the two-kind statement is true.
- Recommendation: say "the rendered prompt carries exactly two kinds", or correct the rule text to match the frozen packet.

### The id grammar is cited to the prefix row, and the truncation applies to one id only - Severity: Nit
- Finding and rationale: the prefix row is cited for the grammar, which is at `:368-369`. Separately, D8 truncates the *reviewer* id while the product's own id keeps the untruncated derivation; for a tenant and product that overflow the cap the two ids of one product are derived by different rules and only one is legal.
- Recommendation: cite the grammar's own row, and either apply the same truncation to `WorkspaceFor` or say in D8 that the product id is assumed to fit and where that is enforced.

### The standing file set is cited to the renderers, not to the paths - Severity: Nit
