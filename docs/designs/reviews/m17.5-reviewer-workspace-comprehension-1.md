# Design review — M17.5, the reviewer's own workspace

**Target:** `docs/designs/m17.5-reviewer-workspace.md` (revision 1)
**Lens:** Comprehension (can a naive reader follow it, and say it back?)
**Round:** 1 · **Date:** 2026-11-04
**Read:** the design document, the rubric (`.claude/rules/rule-index.md`,
`.claude/rules/qa-test-plan.md`, `.claude/rules/agent-workspace.md`) and the domain sources the
index names. Every `file:line` claim was re-derived from the tree.

---

## What this proposes

M17.5 gives every product a second folder — a **reviewer workspace** — so that a review turn runs
somewhere that holds the product's published Blueprint and nothing else, instead of in the author's
own folder. Nine decisions (D1–D9), one new schema file, three phases, a 26-file change list, nine
new Go tests (TC-382…TC-390), and three checks added to the live acceptance probe.

## How the existing system works, per this document

The workspace id is derived per product and every turn names that folder; the task's kind is never
consulted, so a review turn opens its session in the author's folder. The packet is already shaped
per kind, and M17 gave the reviewer a fresh session. The workspace record is a JSON blob on the
product; the drift gate is per product; after a turn `checkAfterTurn` re-reads the folder's digest
and the worker's observed context. The gateway provisions a workspace by id, admits only
`CLAUDE.md` and `.claude/rules/*.md`, and documents no workspace-count cap. D-069 clause 1 ruled
that the isolation boundary is the packet; BR-49 says the same; OQ-27 is still open.

### The QA case count is stated two ways, and they differ - Severity: Blocker
- Affected scope: the counts table, the arithmetic, and the registers table.
- Finding: the counts table says `QA cases | 381 | **390**`; four lines later the arithmetic says "Nine new register rows → 380 + 9 = **389**"; the registers table then gives the register page "three hundred and ninety cases" but the ToC and the validator "three hundred and eighty-nine". The baseline is checkable on disk — the register holds 381 rows with a maximum of `TC-381`, so 381 + 9 = **390** and the "380" base is the error. The two versions have different consequences: the validator `prose_check`s the register page and the ToC against one expected string each, so as written it asserts "three hundred and eighty-nine" against a page that says "three hundred and ninety".
- Recommendation: state 390 in every place — the counts table, the arithmetic ("381 + 9 = 390"), the register page, the ToC, the validator and the README — and drop the 389 form entirely.

### The implementation plan's scoreboard row, its lede and its totals are not reconciled - Severity: Major
- Affected scope: the registers table's implementation-plan row.
- Finding: the design says the row "becomes `4 / 4 / 0 / 0 / 0`", but the real row is `4 | 5 | 0 | 0 | 0` for M17, the totals row is `75 | 99 | 18 | 66 | 5`, and the lede reads "Eighteen modules, seventy-five sub-modules". "4 / 4 / 0 / 0 / 0" reconciles with none of them: as M17's row it lowers ✅ from 5 to 4 while M17.5 adds three ✅ tasks; as a new M17.5 row it should be Sub 3 / ✅ 3; as the totals row it should be 78 / 102. The design also never mentions the lede or the totals row.
- Recommendation: say which row changes and give the resulting cells for that row, for the totals row and for the lede's counts.

### The phase tables and the change list do not reconcile - Severity: Major
- Affected scope: the phase-2 table and the change-list totals.
- Finding: the change list is "generated by the phases above", but phase 2's table lists six files while the change list says seven, and explains the totals as "6 + 7 = 13 touches resolve to 11 distinct files". The seventh is `dashboard/store_conformance_test.go`, which the data-model section requires and which appears in no phase table. Separately, `deploy/acceptance/live-aim-run.sh`, which the live-probe section says gains three checks, appears in no phase table and in no file list, so the file total is one short.
- Recommendation: put `store_conformance_test.go` in the phase that owns the property and the acceptance script in the phase that owns the probe, then re-derive the numbers.

### The live probe's three new assertions get no register row - Severity: Major
- Affected scope: the counts table and the live-probe section.
- Finding: the counts table gives all nine new rows to the nine Go tests, leaving the probe's three checks unregistered. The QA rule triggers the register on a changed automation — "`deploy/acceptance/*.sh` … anything else in `deploy/` that asserts or verifies" — and the register already maps `live-aim-run.sh` to TC-300…TC-303. Either the probe needs its own rows (which would make the count 393) or the design has to say the three checks are folded into the existing rows and are amended.
- Recommendation: say which, and make the count, the TC range and the "next free number" line agree with that answer.

### The refusal's rule id is never decided - Severity: Major
- Affected scope: the mechanism diagram and the verification-plan row for the refusal.
- Finding: the diagram says "failure → refuseDispatch: DispatchRefused, the desk blocked, no turn, no spend" and the test is to assert "the rule", but no rule string is named anywhere. The existing vocabulary is three constants — `RuleBlueprintDrift`, `RuleEgressBlueprint`, `RuleObservedDrift` — and the design's own goal is "no new rule vocabulary". The implementer must pick one of the three, and there are two different failures to cover: the screen refusing the published files, and the gateway refusing the sync.
- Recommendation: name the rule for each failure and say which event carries it.

### The live probe's positive control has no mechanism - Severity: Major
- Affected scope: the live-probe section.
- Finding: "The same checks with the separation deliberately disabled: the canary **must** be reachable and the manifest check **must** fail" — the document never says how the separation is disabled, and D7 retires `GAOS_AIM_WORKSPACE`, so after this change no shipped knob puts a review turn in the author's folder. The positive control is the half of the probe that makes the other half meaningful, and a reader has no way to write it.
- Recommendation: name the switch the probe uses and say which half of the probe it flips.

### D5 does not deliver what its own rationale says it delivers - Severity: Major
- Affected scope: D5 and the goals.
- Finding: D5's rationale is that "**Without this, a reviewer's turn would mark the author's workspace drifted** and refuse the author's next dispatch — the review would punish the author for the reviewer's behaviour." What D5 actually changes is *where* the drifted digest is recorded. The desk block is a separate statement in the same function and is unconditional: it blocks the product's desk and emits `DispatchRefused` with rule `observed-drift`, whichever workspace the drift is attributed to. So a reviewer that rewrites its own `CLAUDE.md` still blocks the author's desk — exactly the punishment the sentence says D5 removes.
- Recommendation: state the intended behaviour in one sentence — either "the reviewer's drift still blocks the product's desk, with a reason naming the reviewer's workspace", or "and the desk is not blocked for a reviewer's drift" plus the code change that achieves it — and align the rationale sentence with it.

### The ToC's decision-count string is not the string the ToC holds - Severity: Major
- Affected scope: the registers table's ToC row.
- Finding: the row gives `toc/product.js` the exact new string "Seventy-one entries", but that file's decision entry reads "Seventy decisions GAOS has actually made…"; "Seventy entries" is the decision log's own lede, which the `decision-log.html` row already covers. Following the table literally leaves the ToC's decision count unmoved or changes it to the wrong wording.
- Recommendation: give `toc/product.js` the string it actually holds — "Seventy-one decisions" — and keep "Seventy-one entries" for `decision-log.html`.

### Three `file:line` citations do not point at what they claim - Severity: Nit
- Affected scope: the `TaskRun.provider` precedent, the gateway id grammar, and the validator's assertions.
- Finding: `dashboard/schema/13-vendors.sql` is 11 lines long and the statement is at line 11, not 15; the id grammar `^[a-z0-9][a-z0-9._-]{0,62}$` is at `gateway.html:368`, while `:344-345` is the prefix setting; the validator's count assertions run to line 144, not 141.

### "desk" is used as an unexplained synonym for "product" - Severity: Nit
- Finding: the document says "product" throughout and switches to "desk" without ever saying the two are the same thing — in the code the desk *is* the product (`p.DeskID`).
- Recommendation: say once — "the desk (the product; the code's `DeskID`)" — and use one term after it.

### BR-32 and BR-39 are used without a pointer to where they live - Severity: Nit
- Finding: BR-32 (the egress screen) and BR-39 (the drift rule) are used five times as load-bearing references but live in the BRD's gateway section, not the design-review section the header links.
- Recommendation: link them to the gateway section the first time each is used.

### `prepareReviewWorkspace(ctx, deskID)` cannot tell a review from an implement turn - Severity: Nit
- Finding: the signature takes only the desk id, but the kind is what makes a turn a review — D4 has `freezePacketFor` resolve it and put it on the packet. Nothing says who decides to call the reset.
- Recommendation: say that the caller checks the packet's kind before preparing the workspace.

### The local decision labels collide with the decision log's ids - Severity: Nit
- Finding: the document uses `D1`…`D9` for its own decisions and `D-071` for the product's entry in the same breath; the log already contains D-001…D-070, so "D1" and "D9" read like log ids.
- Recommendation: label them `M1`…`M9`, or state once that these are the document's own labels, distinct from the log's.
