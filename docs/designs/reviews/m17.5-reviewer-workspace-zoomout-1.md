### The file total still cannot be derived from the change list - Severity: Major
- Affected scope: the change list's summary rows, its derivation, and the enumeration headed "The eleven modified code and test files".
- Finding: the phase tables are declared the generator, but they disagree with each other and with the prose: phase 2's table lists eight rows while its summary says nine; the enumeration is headed "eleven" and lists twelve; the totals say thirteen modified and twenty-eight files, while the tables yield twelve modified and twenty-seven. The `clearFor(ctx, …)` signature change the design itself specifies forces edits to `dashboard/questions_test.go` and `dashboard/designgate_test.go`, and neither is in any table or list — so the true touch set is at least twenty-nine.
- Recommendation: fix the summary table from the phase tables, head the enumeration with its real count, add the two test files the signature change breaks, and state one total derived from that list.

### D9's second workspace record is state no decision reads - Severity: Major
- Affected scope: D9, D3, and the non-goal "no change to the gate's own logic".
- Finding: the design makes the reset the reviewer's drift check and leaves `blueprintGate` reading only the product's copy. D5 then writes the drifted digest into "that workspace's copy" — a second full `WorkspaceCopy` with a per-vendor `Others` map, a `ProductWorkspace` refactor, a persisted-JSON shape change for every product, and a `SyncBlueprint` that now syncs two workspaces. Nothing reads the reviewer copy's `Holds`.
- Recommendation: keep the reviewer workspace's identity and last synced digest, or nothing beyond the run's recorded id; drop the refactor and "SyncBlueprint syncs both" — `SyncWorkspace` provisions the id on demand, so the reset alone keeps the reviewer's copy in step.

### The reset duplicates a sync path the product already has - Severity: Major
- Affected scope: D3's steps 2-3 and D9.
- Finding: "Screen them, exactly as `SyncBlueprint` does" is duplication by admission: `SyncBlueprint` already screens the published files and loops the policy's vendors through `SyncWorkspace`. D3 adds a second copy of that block and D9 makes the first copy run twice. The document's own D4 principle — one derivation, in one place, so two sides cannot disagree — applies verbatim to the sync path.
- Recommendation: extract one helper — screen the published files and sync them to a given workspace id for the policy's vendors — and call it from both.

### D7 retires an operator override this change does not need - Severity: Major
- Affected scope: D7 and D1.
- Finding: the reviewer id is derived from tenant and product "whatever the override does", so retiring `GAOS_AIM_WORKSPACE` is not required by the goal — it is a separate cleanup bundled in. The workspace id is documented as "derived once and never renamed" because transcripts are keyed by it, so removing the override changes the author's workspace id for any deployment that set it and breaks in-flight resumable sessions.
- Recommendation: split D7 into its own change with a stack-wide scan, or keep the override and state explicitly that the reviewer id is independent of it.

### Three published pages still assert "one product, one workspace" - Severity: Major
- Affected scope: phase 3 and the Risks table.
- Finding: the change makes two workspaces per product, and the published record still says one: `brd.html:708`, `gateway.html:68-70` and `graph.html:259`. Phase 3 amends only the three BRD rule rows; `gateway.html` is in no phase, and `graph.html` is promised in Risks but appears in no phase table or list. The BRD's §7.6 bullet is not a rule row, so it is not touched either.
- Recommendation: add `gateway.html` and `graph.html` to phase 3, and amend `brd.html:708-711` alongside the three rules.

### The length cap covers only the reviewer id - Severity: Nit
- Finding: the product's own id derivation has no cap, so the same overflow that D8 handles for `…-review` still produces an illegal id for the author's workspace. Two id derivations with different rules is the divergence the document elsewhere refuses.
- Recommendation: put the format and the 63-character rule in one shared derivation helper used by both ids.

### D4's rule reads as if `workspace_id` is sent on a resumed session - Severity: Nit
- Finding: the cited lines branch — a resumed turn sends `session_id` only, and the documented request shape pairs `workspace_id` with `new_session`. As written, the rule could be implemented as sending both.
- Recommendation: state the rule the way the code is shaped — the workspace id is set only on the new-session branch.

### The after-turn refusal text promises an operator sync the reset makes unnecessary - Severity: Nit
- Finding: for a reviewer's drift the message still reads "the next dispatch is refused until the Blueprint is synced (BR-39)", but the author's dispatch is not refused, while the reviewer's own next reset prunes the drift without any operator sync.
- Recommendation: say in D5 what the reviewer's drift message says and what releases the desk.

### The register rows the live probe changes are not in the plan - Severity: Nit
- Finding: the probe's three new checks, and the review turn they require, change what TC-300…TC-303 assert; the register's scenario prose and the exact quoted `ok`/`FAIL` strings must move with the script.
- Recommendation: name TC-300…TC-303 in phase 3 as amended rows, with their new scenario strings.

### Several `file:line` claims no longer resolve - Severity: Nit
- Finding: the document promises "every claim carries a file and a line", and the cited locations matched the pre-implementation tree — but the tree moved during the review, so the citations now point elsewhere (`blueprintGate` 256→303, `checkAfterTurn` 408→451, `SyncBlueprint` 144→170, `safeID` 70→68, `WorkspaceFor` 76→80). Phase 1 also assigns the id derivation to two files.
- Recommendation: refresh every line reference against the tree the change lands on, and put the reviewer's id derivation in one file only.
