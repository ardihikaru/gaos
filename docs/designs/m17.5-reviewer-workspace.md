## What this document is

M17 built the platform design gate: a design task writes a design, a review task attacks it, and
only then does an implementation task run. It gave the reviewer a **fresh session** and a
**two-part packet** — the design artifact and the rubric, and nothing else
(`dashboard/store_mem.go:1436-1453`).

It did **not** give the reviewer a different **workspace**.

This document specifies that gap's closure: every product gets a second workspace, its own
**reviewer workspace**, holding the product's published Blueprint byte-identical, reset
immediately before every review turn. The reviewer's working root then holds the standing files
and nothing else — no author file, no earlier review's leftover, and a different transcript key
from the author's.

Every claim carries a file and a line. Where D-069 already decided something, this document
implements it and says where. Where it needed a decision D-069 did not make, the decision is
under **The decisions**, and each names the alternative it rejected.

## The problem

### What the code does

| what | where | what it means |
|---|---|---|
| the workspace id is derived per product | `dashboard/adapter_aimanager.go:76-83` — `gaos-<tenant>-<product>`, or the `GAOS_AIM_WORKSPACE` override | one folder per product: the **author's** folder |
| the turn always names that folder | `dashboard/adapter_aimanager.go:156-160` — `req.NewSession, req.WorkspaceID = true, a.WorkspaceFor(p.DeskID)` | **the task's kind is never consulted.** A review task opens its session in the author's folder |
| the packet *is* shaped per kind | `dashboard/store_mem.go:1316-1453` — `freezePacketFor` | the packet was already right. The workspace was the hole |
| the drift gate is per product | `dashboard/workspace.go:256-291` — `blueprintGate` | one workspace, one digest, one gate |
| the after-turn drift check is per product | `dashboard/workspace.go:408-469` — `checkAfterTurn` reads `m.Workspace.ID` | a **review** turn's drift would be written against the *product's* workspace record, and would block the author |
| the workspace record | `dashboard/model.go:359-361`, `dashboard/workspace.go:23-43` — `ProductWorkspace`, persisted as JSON (`dashboard/store_arcade.go:545`) | a second copy is a **JSON field**, not a DDL change |
| the run record | `dashboard/model.go:756-791`, upserted at `dashboard/store_arcade.go:780-806` | one property follows the `TaskRun.provider` precedent (`dashboard/schema/13-vendors.sql:11`) |

### Why the author's files are reachable from a review

- A workspace **is a folder on the worker** that Claude Code runs in
  (`pustaka/docs/product/brd.html:708-711`), and Claude Code runs there **with full
  permissions** (`pustaka/docs/product/blueprint.html:201-204`): the author's turn can leave
  files there.
- `ai-claude-cli` **keys stored transcripts by the workspace id**
  (`pustaka/docs/architecture/gateway.html:68-70`), so the author's session transcript shares the
  reviewer's key.
- The review's turn runs in that same folder (`dashboard/adapter_aimanager.go:159`), so the
  reviewer can open what the author left.

### What the product already says about it

- **D-069 clause 1** (`pustaka/docs/product/decision-log.html`): *"The reviewer's **workspace** is
  the product's own workspace, holding the published Blueprint whole; the workspace is not a
  boundary."*
- **BR-49** (`pustaka/docs/product/brd.html:1323`): *"The isolation boundary is the packet, not the
  workspace."*
- **M17's own record** (`docs/designs/m17-design-gate.md`): the risk row *"The reviewer's session
  is fresh but its workspace is the product's own"*, and the open question *"Can a review run in a
  workspace the author's turn cannot write to?"* — held in *"the gateway's workspace model"*.

### The gateway's model, which is what was missing

The gap was not closed because the mechanism was unknown. It is known, and it admits the fix:

- a workspace id is `^[a-z0-9][a-z0-9._-]{0,62}$` with a configurable prefix, `gaos-`
  (`pustaka/docs/architecture/gateway.html:368-369`) — a second id per product is admissible;
- the worker creates a workspace by id and rewrites its files
  (`pustaka/docs/architecture/gateway.html:351-365`), and GAOS already speaks all of it
  (`dashboard/aimanager_admin.go:85` `Provision`, `:104` `Files`, `:124` `PutFiles`);
- the allowlist admits exactly `CLAUDE.md` and `^\.claude/rules/[a-z0-9][a-z0-9._-]{0,80}\.md$`
  (`pustaka/docs/architecture/gateway.html:370-373`), so a second workspace can hold the published
  Blueprint whole **and nothing else**;
- `workspace_id` on the chat request is already a field GAOS sends
  (`dashboard/aimanager.go:86`);
- **no workspace-count cap is documented** (`pustaka/docs/architecture/gateway.html:313-325`).

### Why this must be built now

OQ-27 (`pustaka/docs/product/open-questions.html`) is open: *"Where does a product's actual code
live inside its workspace?"* — the provisioning API writes instruction files only, so today the
product's code does not live in the workspace and the author's footprint there is its turn's
writes and the transcript key. The moment OQ-27 is answered by mounting a checkout into the
product's folder, the separation becomes the load-bearing control. Building it now is cheap;
building it after OQ-27 is a migration.

## Goals

- A review turn runs in a workspace that holds **the published Blueprint and nothing else** — no
  author file, no earlier review's leftover.
- The reviewer workspace is **its own root with its own initial context** (`CLAUDE.md` and
  `.claude/rules/*.md`, its own copy), per product, derived and never shared.
- The reviewer keeps the **fresh session** and the **two-part packet** M17 gave it. Nothing about
  the packet changes.
- The isolation is **provable**: the reviewer's manifest is checked against the published file set
  before the turn, and the workspace the run used is recorded so the drift check afterwards
  examines the right folder.
- A product's **author's workspace is never marked drifted by a reviewer's turn**, and the
  author's files are never pruned by the reviewer's reset.
- **No new task status, no new agent role, no new event type, no new rule vocabulary.** One new
  optional property on `TaskRun`.

## Non-goals

- **The standing layer is unchanged.** The reviewer workspace holds the whole published
  Blueprint, so it still carries the product's stories and decisions. That is D-069 clause 2's
  ruling and BR-47's existing wording; this change does not reopen it.
- **No inbound screening** of replies (D-069 clause 10), no change to the egress pass's policy, no
  change to the `Review` vertex, no change to the gate's own logic (`dashboard/designgate.go`).
- **No change to any packet's contents.** The packet was already right.
- **The gateway is not changed.** ai-manager and ai-claude-cli are upstream; every route used here
  is documented and already exists.
- **The product's code does not move into the workspace.** OQ-27 stays open; this change narrows
  it.
- **No concurrency change.** One live turn per product, as today.

## The decisions

Nine decisions D-068 and D-069 did not make. (The labels `D1`…`D9` below are this document's
own, and are not decision-log ids: the log's run `D-001`…`D-071`.)

### D1 — One reviewer workspace per product

The id is `gaos-<tenant>-<product>-review`: the product's own workspace id with `-review`
appended.

**Per product, not per review task.** A per-task workspace would be the strongest separation — no
review ever sees a previous review's leftovers — but the reset (D3) already gives exactly that,
at the price of one folder per product instead of one per review task, and one workspace record
per product instead of one per task. The graph's model is "one workspace per product"
(`pustaka/docs/architecture/graph.html:259`), and this keeps it.

**Derived per product, never from the shared override.** `GAOS_AIM_WORKSPACE`
(`dashboard/modelconfig.go:60`, `:103`) collapses every product onto one folder and one initial
context — the thing the operator's rule forbids. The reviewer id is therefore derived from the
tenant and the product, so it is per product whatever the override does. D7 retires the override.

*Rejected:* a reviewer workspace per review task. More folders, more provisioning, and a
per-task workspace record, for a guarantee the reset already provides. *Rejected:* a reviewer
workspace shared by every product. It would put one product's standing files in another's
review.

### D2 — The reviewer workspace holds the published Blueprint, whole

The same file set, byte for byte, as the product's workspace: `CLAUDE.md` plus
`.claude/rules/*.md` — the index, `00-gaos-contract.md`, `10-brd.md`, `20-stories.md`,
`30-decisions.md`, the `4x`–`6x` policies, `70-knowledge-sources.md`
(`dashboard/blueprint_render.go:15-120`).

Same bytes ⇒ the same `BlueprintDigest` (`dashboard/blueprint.go:238-246`) ⇒ the digest check
that guards the product's workspace guards the reviewer's, unchanged.

**The standing files stay whole, and that is D-069 clause 2's ruling, not a preference.** A
workspace holding the rubric but not the Blueprint is a drifting workspace under BR-39
(`pustaka/docs/product/decision-log.html`, D-069 clause 2). The reviewer's root is therefore a
*second copy of the same standing layer*, never a reduced one.

*Rejected:* a reviewer workspace holding only the rubric. It is drift by definition, and the
dispatch would be refused.

### D3 — The reviewer workspace is reset before every review turn

`prepareReviewWorkspace(ctx, deskID)`:

1. take the published version's files (`m.Blueprint.Latest()`);
2. **screen them**, exactly as `SyncBlueprint` does (`dashboard/workspace.go:172-186`) — the sync
   is a dispatch path and BR-32 applies;
3. for every vendor the product's policy uses (`dashboard/vendors.go:95`), call
   `gw.SyncWorkspace(ctx, vendor, reviewerID, files)` (`dashboard/workspace.go:112-142`): provision
   if the worker has never heard of the id, otherwise rewrite the files **with prune**, so the
   folder holds exactly these files;
4. the returned digest must equal the published version's digest — `SyncWorkspace` already
   refuses to return a mismatch (`dashboard/workspace.go:138-140`).

Because the reset prunes, the reviewer's folder carries the standing files and nothing else: no
author file (it is in the other folder) and no earlier review's leftover (the prune removed it).

**The reset is also the reviewer's drift check.** BR-39 asks that a workspace whose files do not
match the pinned version refuses dispatch; for the reviewer's workspace, the reset establishes
that match before the turn rather than observing it afterwards.

*Rejected:* relying on `SyncBlueprint` alone to keep the reviewer's workspace in step. It would
leave a previous review's writes in the folder until the operator happened to publish and sync —
and the digest the gate compares would be stale in between.

### D4 — The workspace id travels on the packet

**`Packet.WorkspaceID`** is new (`dashboard/egress.go:73-105`). **`Packet.Workspace` keeps its
meaning**: it is the *path* an adapter would run in, from the CLI era
(`dashboard/store_mem.go:1035`, `dashboard/egress.go:97`). The new field is an id.

- `freezePacketFor` sets it when the task's kind is `review` and the adapter is a
  `WorkspaceGateway` (`dashboard/store_mem.go:1316-1329` already resolves the kind there).
- It is **not part of the digest**, for the reason `SessionID`, `Vendor`, `Model` and `Kind` are
  not: they say where the turn runs, not what the model is given (`dashboard/egress.go:81-103`).
- `AIMAdapter.turn` sends `req.WorkspaceID = p.WorkspaceID` when it is set and falls back to
  `a.WorkspaceFor(p.DeskID)` otherwise (`dashboard/adapter_aimanager.go:156-160`).

**Why on the packet and not derived twice.** The store owns the drift gate and the adapter owns
the request. If each derived the id, the two could disagree — and a disagreement is a review that
silently ran in the author's folder. One derivation, in the place where the kind is already
known, is the whole point.

*Rejected:* deriving it in the adapter from `p.Kind`. Same information, two derivations, and the
drift gate could not see which folder the turn would use.

### D5 — Drift is attributed to the workspace the run used

**`TaskRun.workspace`** — one new optional property (`dashboard/schema/15-reviewer-workspace.sql`).
It follows the `TaskRun.provider` precedent exactly (`dashboard/schema/13-vendors.sql:11`): a
property written only when present (`dashboard/store_arcade.go:786-795`), so a CLI run's row
carries nothing it never had. It is a plain `STRING` — a workspace id is not a closed vocabulary,
so no DDL regexp and no vocabulary test.

`checkAfterTurn` (`dashboard/workspace.go:408-469`) then:

- reads the run's workspace and compares **that** workspace's manifest digest with the pinned
  Blueprint version, instead of always the product's;
- records the drift against **that** workspace's copy in the product's workspace record;
- runs the observed-context check against the pinned version either way
  (`dashboard/workspace.go:341-397`), so a reviewer that rewrote `CLAUDE.md` is caught.

**Without this, a reviewer's turn would mark the author's workspace drifted** and refuse the
author's next dispatch — the review would punish the author for the reviewer's behaviour. What
D5 changes is *where* the drifted digest is recorded: the author's workspace record stays
exactly as the author's turns left it. The desk is still blocked by a reviewer's drift, with a
reason that names the reviewer's workspace — the block is the existing BR-39 behaviour and it
stays.

A run recorded before the migration carries no workspace: it means the product's workspace, as
today.

### D6 — One live turn per product

BR-38's text moves from *"a product's workspace"* to *"a product"*: the product now has two
folders, and the rule is one live turn across both. The implementation already serialises per
desk — the scheduler's graph lease holds one live turn per product
(`dashboard/scheduler.go:212-225`), and the board's route
refuses a second live turn for the product (`dashboard/board.go:339-344`). **No code changes**;
the rule text changes so that it keeps matching the code.

### D7 — Retire the shared-workspace override

`GAOS_AIM_WORKSPACE` collapses every product onto one folder and one initial context, which is
exactly what the operator's rule forbids ("each product needs its own workspace root, its own
initial context"). Four things go: the env read (`dashboard/modelconfig.go:103`), the config field
(`:60`), the adapter's own field (`dashboard/adapter_aimanager.go:33-34`) and the wiring that set
it (`dashboard/modelconfig.go:207`) — and with them the branch in `WorkspaceFor`. No stack sets it:
a repository-wide search for the name matches only the code and this document.

It is set in no stack — `deploy/stacks/dashboard.env.example` does not carry it — so retiring it
changes no deployment. The comment already calls it vestigial ("one shared workspace, until
M14.4").

### D8 — The id obeys the gateway's grammar

`gaos-` + `safeID(tenant)` + `-` + `safeID(product)` + `-review`
(`dashboard/adapter_aimanager.go:70-74` is `safeID`). The result is lowercase and holds only
`[a-z0-9._-]`, and it starts with `g`, so it satisfies `^[a-z0-9][a-z0-9._-]{0,62}$`.

**Length.** The gateway's id is at most 63 characters. The algorithm is literal, and one
derivation serves both ids (`dashboard/adapter_aimanager.go`):

```
full := "gaos-" + safeID(tenant) + "-" + safeID(product) + suffix   // suffix is "" or "-review"
if len(full) > 63 { id = full[:56] + "-" + hex(sha256(full))[:6] } else { id = full }
```

The truncated id is 63 characters, unique (the digest is of the *full* id) and legal. The
product's own id is truncated the same way — the cap is the gateway's, not the reviewer's — so the
two derivations cannot drift apart in their format or their length.

### D9 — The record carries both workspaces

`ProductWorkspace` gains a second copy. The shape:

```go
// WorkspaceCopy is one workspace's record: its id and what each vendor's
// copy of it holds.
type WorkspaceCopy struct {
	ID            string
	ProvisionedAt int64
	SyncedVersion int
	SyncedDigest  string
	SyncedAt      int64
	Others        map[string]WorkspaceSync
}

// ProductWorkspace is the product's workspaces: the one its own turns run in,
// and the one its reviews run in (M17.5, D-071).
type ProductWorkspace struct {
	WorkspaceCopy            // the product's own workspace
	Review       WorkspaceCopy // the product's reviewer workspace
}
```

The product's fields keep their names and their places, so the JSON already in the database still
decodes (`dashboard/store_arcade.go:545`, `:1191-1193`); the reviewer copy is a new key.

`Holds` and `setHolds` move to `WorkspaceCopy` and are promoted, so every existing call site
(`dashboard/vendors.go:203`, `:404`, `dashboard/workspace.go:275`, `:454-456`) is unchanged.

`SyncBlueprint` (`dashboard/workspace.go:144-254`) syncs **both** workspaces: the product's and
the reviewer's, per vendor, with the same events (`WorkspaceProvisioned`, `BlueprintSynced` — no
new event type) and the reviewer copy recorded beside the product's. The events name the
workspace they are about.

## The mechanism, in one page

```
    a review task reaches READY
        │
        ├─ blueprintGate(desk)         the PRODUCT's workspace holds the published
        │                              Blueprint (unchanged, BR-39)
        │
        ├─ clearFor(ctx, dispatch, attempt)
        │    ├─ freezePacketFor        kind=review → packet = design + rules
        │    │                         WorkspaceID = gaos-<tenant>-<product>-review
        │    ├─ Screen                BR-32, unchanged
        │    └─ prepareReviewWorkspace
        │         ├─ screen the published files        (BR-32)
        │         ├─ per vendor: provision + prune + verify the digest
        │         └─ failure → refuseDispatch: DispatchRefused, the desk blocked,
        │                       no turn, no spend.  The screen's refusal carries rule
        │                       egress-blueprint (dashboard/workspace.go:96); a failed
        │                       sync carries blueprint-drift (dashboard/workspace.go:94)
        │
        └─ superviseRun
             ├─ startRun              TaskRun.workspace = the reviewer's workspace
             ├─ ad.Dispatch           ChatRequest.workspace_id = the reviewer's workspace
             └─ checkAfterTurn        the reviewer's digest, not the product's
```

| the turn | its packet | its workspace | its reply |
|---|---|---|---|
| `des` (design) | the ordinary packet | the product's | a `gaos-handoff` block **and** a `gaos-design` block |
| `rev` (review) | **exactly** the design and the rules | **the product's reviewer workspace** | a `gaos-handoff` block **and** a `gaos-review` block |
| `imp` (implement) | the ordinary packet **plus** the design and the findings | the product's | a `gaos-handoff` block |

**The frozen packet and the rendered prompt are two different objects, and the isolation is now
over both.** M17 made the prompt carry the design and the rubric and nothing else
(`dashboard/adapter_aimanager.go:99-109` drops the contract part and re-renders it at the end).
This change adds the workspace: the prompt is minimal **and** it is delivered to a root that holds
nothing of the author's.

## The data model

**New file `dashboard/schema/15-reviewer-workspace.sql`**, the next free number
(`14-design-gate.sql` is M17's). `schemaFiles()` sorts by filename and applies in order
(`dashboard/schema_embed.go:112-127`), so a `15-*.sql` runs last — which is what a
`CREATE PROPERTY` wants.

```sql
CREATE PROPERTY TaskRun.workspace IF NOT EXISTS STRING;
```

One statement, one optional property, no regexp and therefore no vocabulary test: a workspace id
is not a closed vocabulary. The property round-trips through the store conformance suite, which
runs against both stores (`dashboard/store_conformance_test.go`).

**Nothing else in the data model moves.** `Task.kind`, `Artifact.kind` and the citation roles
stay as M17 left them (`dashboard/schema/14-design-gate.sql`). The workspace *record* is JSON, not
DDL (D9).

### The live probe

`deploy/acceptance/live-aim-run.sh` is the script that spends real money against a real gateway.
This change adds three checks to it. **They amend the existing live-run rows
(TC-300…TC-303) rather than adding new ones** — the register counts cases, and a case is a
scenario, not an assertion — so the case count moves by the nine Go tests and by nothing else:

1. **The manifest check.** After a review turn, ask the gateway for the reviewer's manifest and
   compare it with the published file set: the same paths, the same digests, **nothing else**. The
   author's canary file is absent.
2. **The canary check.** Plant a canary file on the author's side of the product's workspace, run
   the review, and assert the canary reached neither the review's prompt nor its artifact. The
   claim is precisely *"the canary did not reach the reviewer's record"* — not "the file was not
   read".
3. **The positive control.** The *identical* check, run against the product's own workspace —
   the folder the canary is planted in. It **must** fail: the canary is present, and the check
   says so. A probe that cannot fail is indistinguishable from a clean run. (Nothing has to be
   switched off to run it, because the check is a comparison and the author's folder is the
   comparison's other half.)

## Alternatives considered

**A — Keep one workspace and rely on the packet.** Rejected: this is what D-069 clause 1 decided
and M17 recorded as a limit. The author's files are in the folder the reviewer runs in; a fresh
session and a minimal packet do not change the folder.

**B — Prune the product's workspace before a review and restore it afterwards.** Rejected: it
deletes the author's own work from the folder the author works in, and a review that fails
mid-way leaves the product's workspace pruned. It destroys the thing it claims to protect.

**C — A reviewer workspace per review task.** Rejected in D1: the reset gives the same guarantee
for one folder per product.

**D — A reduced standing layer for the reviewer: the rubric without the stories and the
decisions.** Rejected: it is drift under BR-39 (D-069 clause 2) and the dispatch would be refused.

**E — Screen the reviewer's prompt for the author's paths.** Rejected: the author does not put
paths in the prompt; the reviewer goes and opens them. Screening the prompt does not touch the
folder.

## What would show this works

- **The reviewer's manifest holds exactly the published file set.** Checked before every review
  turn and again by the live probe. This is the positive form of the guarantee: not "the author
  was not quoted" but "the author's file is not in the reviewer's folder".
- **The author's folder is never pruned by a review**, and the product's workspace record is
  never marked drifted by a reviewer's turn.
- **The cost of a reviewer's reset** — two admin calls per vendor per review dispatch — measured
  against the review turn's own cost, which is already metered (D8 of the M17 design).
- **The rate at which a reviewer finds something in the author's folder.** If it is ever above
  zero, the separation has a hole and the probe is the thing that will say so.

## Risks

| Risk | Handling |
|---|---|
| The two folders are **siblings under one managed root**; the gateway documents a write boundary (the allowlist) but no read boundary between sibling folders | **named, not hidden.** The guarantee is structural: the reviewer's working root and standing files hold none of the author's files, and the author's folder is never named in the reviewer's packet. It is not a sandbox. The probe's positive control is what tells the difference |
| The transcript's **physical location is not documented** — only that it is keyed by the workspace id | a distinct id means a distinct key; the claim is stated no stronger than that |
| The standing files still carry the product's **stories and decisions** | unchanged by design (D2); BR-47 says so in its new wording |
| The reset **costs two admin calls per vendor per review dispatch** | a review dispatch is rare and already spends a model turn; the calls sit in the dispatch path, outside the store's lock |
| A reviewer that writes into its own folder **drifts it** | the next reset prunes it; the standing files' integrity is caught after the turn by the observed-context check |
| A reviewer's turn marks the **product's** workspace drifted — the bug D5 fixes | the run's workspace is recorded and the drift is attributed to it; the test at TC-387 is the regression |
| **Two workspaces per product** may exceed the worker's folder budget | no cap is documented (`pustaka/docs/architecture/gateway.html:313-325`); the live probe proves one product's pair |
| The graph's "one workspace per product" (`pustaka/docs/architecture/graph.html:259`) now has an exception | the record carries two copies; the published page is amended with the change |
