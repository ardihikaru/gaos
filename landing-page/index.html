Product and task management for AI coding agents

GAOS stores each product's requirements, user stories, decisions and policies in a graph. It plans the work as tasks on a kanban board and sends each task to an agent one turn at a time, in a workspace that already holds the product's rules. State is kept in the graph and an append-only event stream, so an orchestrator that stops mid-task rebuilds from them.

What GAOS does today

The features below are implemented and covered by tests. Planned work that is not built yet is listed separately.

A kanban board per product

Each product has one board with nine columns: Backlog, Ready, Working, Needs you, Review and Done, plus Blocked, Failed and Canceled. The columns are computed from task status in the graph; the board stores no state of its own. Moving a card is a request that the task state machine can refuse.

Read more

Versioned Blueprint

A product's requirements, technical and coding policies, and reference repositories are published as one versioned unit and synced into the product's workspace as the agent's rules. A dispatch is refused when the workspace no longer matches the published version.

Read more

Readiness scoring

Each product record is scored out of 100 by rules a machine can check. Below 45 the planner refuses to plan and returns the list of what is missing.

Read more

Design gate

A planned story starts with a design task. A reviewer without access to the author's context reads the design, and the implementation task starts only after the review passes. A blocked design returns to its author and is reviewed again.

Read more

Operator inbox

When an agent or an external client asks a question, the task waits in Needs you until a person answers. Each answer records where it came from.

Timeline and replay

Changes are written as events to an append-only stream, and the timeline replays a product's history from that stream. If the orchestrator stops in the middle of an attempt, it rebuilds its state from the graph.

Machine API and QA sync

QA tools and other clients connect through a REST API with bearer tokens. GAOS keeps a test catalog per product, syncs it with the QA tools, and calls a webhook when an operator answers a client's question. The Integrations view shows the live state of each connection and never displays a secret.

  • Result scoring engineCombines five weighted dimensions of an agent's result into one score, with a safety limit that stops the work regardless of the total.Planned
  • Retry guardsStop and ask for a decision when an attempt fails the same way twice.Planned
  • Budget guardRefuses to dispatch once a product reaches its spending cap. It does not stop an attempt that is already in progress.Planned

The Blueprint is written into the workspace, and every attempt records its version

  • One versioned unit. Business requirements, technical and coding policies, and the repositories whose patterns the agent follows.
  • Loaded on every turn. It is written as CLAUDE.md and .claude/rules, so the agent loads it on every turn, including a resumed one.
  • A published version does not change. A dispatch is refused until the workspace holds the published version, and each attempt records the version it ran under.

From a product record to a recorded attempt, in four steps

Each step writes to the graph. The label above a step names the record it writes.

  1. Product

    Describe the product

    Record the problem, the goals, the scope, the domain rules, and the user stories with their acceptance criteria.

  2. readiness score

    Pass the readiness gate

    The record is scored out of 100. The planner accepts a score of 45 or above.

  3. Task

    Plan the tasks

    The planner turns stories into tasks. Each task covers one concern and has at least one acceptance criterion, and its dependencies are checked for cycles on every write.

  4. TaskRun, Event

    Run each task through the gateway

    ai-manager runs one turn in the product's workspace under the published Blueprint. A worker such as ai-claude-cli does the work, and GAOS records the attempt and its events.

Three layers, each with one responsibility

01

GAOS

Holds the product record, the tasks and the Blueprint, and decides what to dispatch. GAOS runs no model tool itself.

02

ai-manager

The gateway. It runs every model turn in the workspace provisioned for the product.

03

Worker

An agent such as ai-claude-cli that carries out the task in that workspace.

Model turns are off by default. Set GAOS_MODEL_MODE=aimanager and point GAOS_AIM_URL at an ai-manager gateway to turn them on.

You pay your own model provider. GAOS is never in that billing path.

Run it locally

The local stack needs Docker and publishes one port.

$ git clone https://github.com/ardihikaru/gaos.git$ cd gaos$ docker compose up -d

Then open http://localhost:8083/:
